## S1: ใบรับรองใบเดียวแทนหลายธุรกรรม

### ปัญหา

airlock (`BridgeAirlock`) ปล่อยการโอนเข้า ZETAPHY ก็ต่อเมื่อ "เลน" อิสระสองเลนยืนยันตรงกัน เลนหนึ่งคือ Hyperlane
อีกเลนอาจเป็น runner ของ Neuro (`NeuroLane`) ซึ่งตอนนี้ **runner แต่ละคนส่งธุรกรรมของตัวเอง** เพื่อโหวต
runner สามคน = สามธุรกรรมต่อการโอนหนึ่งครั้ง

### `SaphanAggLane` ทำอะไร

ผู้ยืนยัน (คณะกรรมการไม่เกิน 32 คน) แต่ละคนถือกุญแจ **ML-DSA-44** (ลายเซ็นหลังควอนตัม) เซ็นนอกเชน แล้วใครก็ได้นำ
**ใบรับรองใบเดียว** ขึ้นเชน:

- สมาชิกสร้าง Merkle tree ของการโอนที่เห็นตรงกัน แต่ละคนเซ็น digest ของ root
- `certify(root, certificate)`: ตรวจครั้งเดียว: t รายการ [กุญแจ 1312 ไบต์ | ลายเซ็น 2420 ไบต์] เรียงตาม hash ของกุญแจ
  ทุกกุญแจต้องเป็นสมาชิก ทุกลายเซ็นตรวจด้วย precompile 0x…0900
- `attest` / `attestMany`: การโอนแต่ละรายการพร้อมเส้นทาง Merkle ไปยัง airlock
- การโอนรายการเดียว: root = leaf ไม่มีเส้นทาง: `certifyAndAttest` ในการเรียกครั้งเดียว

รายละเอียด:

- **digest** ผูกกับ chain id, ที่อยู่ของเลน, epoch และ root ใบรับรองจึงใช้ซ้ำข้ามเชน ข้ามเลน หรือหลังเปลี่ยนคณะกรรมการไม่ได้
- **กุญแจเรียงตาม hash** สมาชิกคนเดียวนับสองครั้งไม่ได้ และต้องมีพอดี `threshold` รายการ
- **เปลี่ยนคณะกรรมการ** ได้เฉพาะ governance (`ZetaphyTimelock`) ภายในขอบเขต: ผู้เซ็นอย่างน้อย 2 คน มากกว่าครึ่ง
  สมาชิกไม่เกิน 32 คน การเปลี่ยนเพิ่ม **epoch** และ root เก่าทั้งหมดใช้ไม่ได้อีก
- **ยังเป็นเพียงเลนเดียว** กติกาของ airlock ไม่เปลี่ยน คณะกรรมการลำพังสร้างเงินไม่ได้: Hyperlane ต้องยืนยันด้วย
  แล้วยังมี quarantine, veto, การทำเครื่องหมาย, ธงของ Neuro และเพดานรายวันของ guard ผู้พิทักษ์ (guardian) ยังถอดเลนได้ทันที

## S6: คำสั่งที่ปิดผนึกด้วย ML-KEM

### ปัญหา

intent (`SaphanIntents`, PR 5) เป็นข้อมูลสาธารณะทันทีที่เปิด ใครเห็นก็ชิงทำก่อนได้

### `SaphanSealedOrders` ทำอะไร

1. solver ประกาศกุญแจเข้ารหัส `setSolverKey` (X-Wing = ML-KEM-768 + X25519, 1216 ไบต์)
2. ผู้ใช้ปิดผนึกคำสั่งพร้อม salt สุ่มด้วยกุญแจนั้น แล้ว `commit(...)` พร้อมฝากโทเคนไว้ (จากเชนอื่นใช้ depositAndCall ได้)
3. solver อ่าน event ถอดรหัส ตรวจ commitment แล้ว `reveal(id, order, salt)` ภายในเวลาที่กำหนด คำสั่งจะเปิดเป็น intent ปกติ
   ใน SaphanIntents หรือถ้าจ่ายบน ZETAPHY ใช้ `revealAndFillLocal` เปิดเผย เปิด และจ่าย ในธุรกรรมเดียว
4. ไม่มีใครเปิดเผยทันเวลา: ใครก็เรียก `refund(id)` ได้ แล้ว `refundTo` ถอนเงินคืนเอง (`claim`)

- **สิ่งที่ซ่อน**: เชนปลายทาง ผู้รับ จำนวนขั้นต่ำ และกำหนดเวลา **สิ่งที่เปิดเผย**: โทเคน จำนวน `refundTo` และ solver ที่เลือก
  ciphertext ทุกอันยาวเท่ากัน (1424 ไบต์)
- **commitment ผูกข้อความจริง**: solver แก้ช่องใดไม่ได้เลย และคำสั่งต้องใช้เงินที่ฝากพอดี salt 32 ไบต์กันการเดา
- **การเข้ารหัส**: X-Wing ตัวเดียวกับ encrypted mempool (`@noble/post-quantum` ซึ่งมีอยู่แล้ว) ปลอดภัยตราบที่ ML-KEM-768
  หรือ X25519 อย่างใดอย่างหนึ่งยังแข็งแรง ใช้ AES-256-GCM และผูก ciphertext กับเชน สัญญา solver และ commitment
- เฉพาะ solver ที่เลือกเท่านั้นเปิดเผยได้ ภายในช่วง 1 นาทีถึง 1 วัน (ค่าคงที่) ไม่มีผู้ดูแล ไม่มีอะไรให้ governance ปรับ
- คำสั่งที่ SaphanIntents ปฏิเสธ (หมดเวลา ผู้รับมีความเสี่ยงสูง) เปิดเผยไม่ได้ จึงคืนเงินหลังหมดเวลาแบบเดียวกัน

gas ที่วัดได้: `commit` ราว 321,000, `reveal` ราว 362,000 (รวมการเปิด intent)

### ข้อจำกัดของ S6

- สัญญา **ตรวจไม่ได้** ว่า ciphertext มีคำสั่งตรงกับ commitment จริง ผู้ใช้ที่ใส่ขยะก็แค่ล็อกเงินตัวเองจนหมดเวลา
- solver ที่ไม่เปิดเผยทำให้ผู้ใช้เสียเวลา ไม่เสียเงิน ไม่มีเงินค้ำประกันของ solver (เพราะผู้ใช้อาจจงใจใส่ขยะเพื่อกลั่นแกล้ง)
- หลังเปิดเผยแบบข้ามเชน คำสั่งเป็น intent สาธารณะ solver อื่นอาจจ่ายก่อนบนเชนปลายทางได้ ผู้ใช้ไม่เสียหาย (ได้รับเงิน)
- solver เห็นคำสั่งก่อนคนอื่น เลือก solver ที่ไว้ใจได้ หรือกลุ่ม solver ที่ใช้กุญแจร่วมกัน
- เก็บ seed ลับของกุญแจไว้จนกว่าทุกคำสั่งที่ผนึกด้วยกุญแจนั้นจะถูกเปิดเผยหรือคืนเงินแล้ว

## การ deploy (ยังไม่ได้ทำ)

`SaphanAggLane(airlock, ZetaphyTimelock, hash ของกุญแจคณะกรรมการ, threshold)` บน ZETAPHY แล้ว governance ของ airlock
เพิ่มเป็นเลน (ผ่าน timelock) และ `SaphanSealedOrders(SaphanIntents)` บน ZETAPHY แล้ว solver เรียก `setSolverKey`
ยังไม่มีหน้าจอใน hub (มีแค่ CLI และสัญญา)

## บันทึกการ audit

audit แบบเร็ว (slither + aderyn) ไม่พบข้อระดับ High ในสัญญาใหม่ทั้งสอง เหลือระดับ Medium สองข้อ ตรวจแล้วไม่เป็นอันตราย:
`incorrect-equality` ที่ `key == bytes32(0)` (ตรวจว่ายังไม่ได้ลงทะเบียนกุญแจ ไม่ใช่ยอดเงิน) และ `unused-return`
ของ view ของ ThreatRegistry (ใช้แค่ค่า `held`)
