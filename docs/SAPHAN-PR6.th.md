## S2: คุณสมบัติที่เครื่องตรวจให้

สี่ข้อของเส้นทางหนึ่ง (lockbox บนเชนต้นทาง; airlock, guard, โทเคน และ outbox บน ZETAPHY):

1. **lockbox ไม่เคยปล่อยเกินที่ถูกล็อก** ยอดในสัญญาเท่ากับ `locked` = ยอดล็อก - ยอดที่จ่ายออกพอดี
2. **ทุกเหรียญที่บริดจ์มีของหนุน** supply บน ZETAPHY + ยอดที่กำลังเดินทางกลับ (เผาแล้ว ยังไม่จ่าย) <= locked
   ส่วนต่างเท่ากับยอดล็อกที่ ZETAPHY ยังไม่ได้สร้างโทเคนพอดี
3. **แต่ละข้อความปล่อยได้ครั้งเดียว** ส่งข้อความเดิมซ้ำ เคลมซ้ำ หรือ mint ซ้ำ ถูกปฏิเสธทั้งหมด
   lane ที่โกหกเพียงตัวเดียว mint อะไรไม่ได้ (ต้องมี 2 lane อิสระเห็นตรงกัน)
4. **วงเงินรายวันไม่แตก** ต่อวัน (UTC): ยอดจ่าย <= วงเงินของ lockbox, ยอด mint <= วงเงินของ guard สำหรับเส้นทางนั้น

ตรวจด้วยสามเครื่องมือ แต่ละตัวมีจุดแข็งต่างกัน:

- **Foundry invariant** (`audit/invariants/saphan/SaphanRoute.inv.t.sol`): สุ่มลำดับการล็อก การยืนยันทั้งจริงและโกหก
  การปล่อย การเผา การส่งข้อความแบบสลับลำดับและซ้ำ การเคลม การ veto การหยุด และเวลา บนสัญญาจริง ทั้งสองเชนใน EVM เดียว
  `cd zetaphy-network && forge test --match-contract Saphan` และ pipeline ตรวจสอบ (`audit/run.sh` ขั้น invariants) รันให้ด้วย
- **Halmos** (`audit/invariants/saphan/SaphanSymbolic.t.sol` ฟังก์ชัน `check_*`): พิสูจน์สำหรับ *ทุก* ค่าอินพุตของสถานการณ์เล็ก:
  ล็อกสองครั้งและปล่อยสองครั้งด้วยจำนวนใดก็ได้ ไม่จ่ายเกินที่ล็อกหรือเกินวงเงินรายวัน และแต่ละรายการจ่ายครั้งเดียว;
  กฎแบ่งตามสัดส่วนของ escape hatch / การกู้คืน ไม่จ่ายเกินพูล
- **เทสต์ JS ในชุดเทสต์ปกติ** (`test/saphaninvariants.test.js`): ตรวจสี่ข้อเดียวกันหลังทุกขั้นของลำดับสุ่มที่กำหนด seed
  ดังนั้น `node --test test/*.test.js` จับการถดถอยได้โดยไม่ต้องมี Foundry

ผลอยู่ใน `audit/invariants.md` (หัวข้อ "Saphan route")

## S7: ถอน BTC แบบมองโลกในแง่ดี (ต้นแบบ)

ปัญหา: การส่ง BTC กลับจาก ZETAPHY ต้องมีกุญแจบน Bitcoin แนวคิดของ BitVM2: **operator** จ่าย BTC ของตัวเองให้ผู้ใช้ก่อน
แล้วค่อยขอเงินคืน ใครก็พิสูจน์ได้ถ้า operator โกหก และขอแค่มีผู้เฝ้าที่ซื่อสัตย์คนเดียวก็พอ

```
 ผู้ถือ                          ZETAPHY: SaphanBtcWithdrawals                   Bitcoin
 request(amount, btcScript) ─▶  เก็บ BTC ที่บริดจ์ไว้
                                                         operator จ่ายเข้า btcScript ≥ sats พร้อม
                                                         OP_RETURN "ZTPHYW" || id || operator
 operator ── claim(id, txid, vout) ─▶ เปิดช่วงท้าทาย (เช่น 1 วัน) ล็อกเงินค้ำส่วนหนึ่ง
 ใครก็ได้ ── challenge(id) + เงินค้ำ ─▶ operator ต้อง prove() การจ่ายด้วย SPV ภายในเวลาที่กำหนด
   พิสูจน์ได้     ─▶ operator ได้เงินที่เก็บไว้ + เงินค้ำของผู้ท้าทาย
   พิสูจน์ไม่ได้  ─▶ slash(id): ผู้ถือได้เงินคืน + ครึ่งหนึ่งของเงินค้ำ operator; ผู้ท้าทายได้เงินค้ำคืน + อีกครึ่ง
 ไม่มีใครท้าทาย  ─▶ finalize(id) หลังหมดช่วง: operator ได้เงินที่เก็บไว้
```

- OP_RETURN ผูกการจ่ายกับ **การถอนรายการเดียวและ operator คนเดียว** ไม่มีใครเคลมการจ่ายของคนอื่นได้
  และการจ่ายหนึ่งครั้งใช้ได้กับการถอนรายการเดียว
- ทุกการเคลมที่ยังเปิดอยู่ล็อกเงินค้ำของ operator ไว้ จึงถอนเงินค้ำที่อาจเสียไม่ได้
- จ่ายแบบผู้รับมาดึงเอง (`withdraw()`) ค่าทุกอย่างกำหนดตอน deploy ไม่มีเจ้าของ ไม่มีแอดมิน ไม่มีปุ่มหยุด

**ที่ยังขาด (เหตุที่เป็นต้นแบบ):** ใน BitVM2 เงินคืนมาจาก UTXO บน Bitcoin ผ่านธุรกรรมที่ลงนามไว้ล่วงหน้า และขั้นพิสูจน์ความผิด
รันเป็นสคริปต์ Bitcoin (ตัวตรวจ SNARK ที่แบ่งเป็นชิ้น) ที่นี่เกมทั้งหมดรันบน ZETAPHY และขั้นพิสูจน์ความผิดถูกย่อเป็น
"พิสูจน์การจ่ายด้วย SPV หรือเสียเงินค้ำ" การตรวจ SPV ใช้ `BtcLightClient` ที่มีอยู่แล้ว (proof of work และจำนวนการยืนยัน)

## S9: สภาพคล่องที่ปรับตามการใช้งาน

วงเงินปล่อยรายวันของเส้นทางควรสูงเมื่อมีคนใช้ และต่ำเมื่อไม่มีคนใช้ (วงเงินต่ำจำกัดสิ่งที่ผู้โจมตีเอาไปได้ในหนึ่งวัน)
`src/saphanliquidity.js` คำนวณวงเงินถัดไปจากยอดปล่อยที่เห็น:

- เปอร์เซ็นไทล์ที่ 90 ของยอดรายวัน 7 วันล่าสุด คูณ 1.5 เผื่อไว้
- **คำแนะนำจาก LLM** (ขึ้น / ลง / คงไว้ พร้อมตัวคูณ) ปรับได้ไม่เกิน 20 % อย่างอื่นถูกเพิกเฉย
- แล้วตามกรอบของ governance: ไม่ต่ำกว่า `min` ไม่สูงกว่า `max` เปลี่ยนได้ไม่เกิน `maxStepBps` ต่อครั้ง

อินพุตเดียวกันให้คำตอบเดียวกันทุกเครื่อง และสัญญาเก็บแฮชของอินพุตไว้ ใครก็คำนวณข้อเสนอซ้ำได้

`SaphanLiquidityBounds` (หนึ่งตัวต่อเชนต้นทาง governance = ZetaphyTimelock ของเชนนั้น) เก็บกรอบและเป้าหมายของแต่ละเส้นทาง
ผู้ปรับสมดุล (กุญแจที่ governance แต่งตั้ง) ขยับเป้าหมายทีละขั้นที่จำกัดไว้ **บนเชนทำได้แค่ลดความเสี่ยง**: สัญญาเป็น guardian
ของ lockbox และ `applyDown` ลดวงเงินรายวันของ lockbox ลงมาที่เป้าหมาย การเพิ่มวงเงินต้องผ่าน timelock ของ lockbox
(`raiseProposal` พิมพ์คำสั่ง `schedule()` ให้) และ governance ไม่จำเป็นต้องรับ `liquidity plan` รันนโยบายจากไฟล์ยอดใช้งาน

## S10: ขั้นตอนการกู้คืน

เมื่อเส้นทางมีปัญหา `node scripts/saphan.js recovery plan --state state.json` บอกทุกขั้นและขั้นถัดไป:

1. **หยุด**: guardian หยุด lockbox และ guard (เหมือนเดิม)
2. **สำรวจยอด**: `recovery read` เก็บ event (การโอน token(X) บน ZETAPHY จนถึงบล็อกที่เกิดเหตุ, การปล่อยที่เข้าคิวแต่ยังไม่จ่าย,
   การล็อกที่ไม่เคยถูก mint) แล้ว `recovery snapshot --events events.json --exclude 0x…` แปลงเป็นหนึ่งบรรทัดต่อที่อยู่และ
   Merkle root เป็น **ต้นไม้เดียวกับ escape hatch** (leaf เดียวกัน proof เดียวกัน) ใครก็สร้างใหม่และตรวจได้
   การตัดที่อยู่ออก (เช่น ผู้โจมตี) เป็นการตัดสินใจที่เปิดเผยอยู่ในไฟล์
3. **เคลม**: governance deploy `SaphanRecoveryClaims` แล้วผ่าน timelock (ช่วงรอคือเวลาที่ทุกคนใช้ตรวจ root) เรียก
   `start(root, total)` ครั้งเดียว (`recovery start` พิมพ์คำสั่งให้) ใครก็เติมเงินได้ (ประกัน, คลัง, เงินที่กู้คืนมา)
   แต่ละที่อยู่เคลมบรรทัดของตัวเองครั้งเดียว (`recovery proof --account 0x…`): ได้เต็มเมื่อพูลพอ ไม่พอก็แบ่งตามสัดส่วน
   พูลถูกตรึงตอน `start` ลำดับการเคลมจึงไม่เปลี่ยนส่วนของใคร หมดช่วงเคลมแล้ว `sweep()` ส่งที่เหลือไปพูลประกัน
4. **เปิดต่อ**: governance ยกเลิกการหยุดเมื่อแก้ต้นเหตุแล้ว

## F: โอนแบบส่วนตัว

`SaphanPrivacyPool` ให้ผู้ถือโทเคนที่บริดจ์มา ตัดความเชื่อมโยงระหว่างที่อยู่ที่บริดจ์เข้ากับที่อยู่ที่ใช้เหรียญ หนึ่งพูลต่อโทเคนและจำนวน
(เช่น 0.01 sepETH):

- **ฝาก**: สร้างโน้ตลับแบบออฟไลน์ ฝาก commitment ของมันพร้อมจำนวนเท่าที่พูลกำหนดพอดี
- **ถอน**: ทีหลัง จากที่อยู่ใดก็ได้ (หรือผ่าน relayer ที่ได้ค่าธรรมเนียม) ด้วย zero-knowledge proof ว่า "หนึ่งในเงินฝากของพูลเป็นของฉัน"
  เปิดเผยแค่ nullifier (โน้ตแต่ละใบใช้ได้ครั้งเดียว) และผูกกับผู้รับและค่าธรรมเนียม (คัดลอก proof ไปเปลี่ยนผู้รับไม่ได้)

proof เป็น **ของจริง**: ใช้วงจร private identity และตัวตรวจ Groth16 เดิม (zetaphy-network/zkid, docs/future/zk-identity.md)
โดยไม่แก้ **แต่ trusted setup เป็นแบบ DEV**: เครื่องเดียวสร้างกุญแจ ใครที่รันมันอาจปลอม proof และดูดทุกพูลได้
mainnet ต้องมีพิธี multi-party แบบเปิดก่อน นอกจากนี้ กลุ่มที่ซ่อนตัวได้มีแค่เงินฝากของพูลนั้น (บน testnet มีน้อย)
และการฝากกับเวลาเป็นข้อมูลเปิด proof ที่ใช้เทสต์สร้างจาก `zkid/privacy-fixture.js` ด้วยไฟล์ prover ของ hub

## G: ซ่อมตัวเอง

`src/saphanheal.js` เป็นตัวเฝ้าที่มี `tick()` หนึ่งครั้งต่อเส้นทาง:

- **ข้อความค้าง**: การปล่อยที่ outbox ส่งแล้วแต่ lockbox ไม่เคยบันทึก หรือการล็อกที่ lane ไม่เคยได้รับ นานเกิน 30 นาที:
  ส่งซ้ำ (การส่งของ Hyperlane ซ้ำได้อย่างปลอดภัย และสัญญาปฏิเสธข้อความซ้ำ การส่งซ้ำจึงมีแต่ช่วย) โดยเว้นระยะเพิ่มขึ้น ไม่เกิน 3 ครั้ง
- **heartbeat**: ไม่ได้ยินจาก ZETAPHY 20 ชั่วโมง: ส่งหนึ่งครั้ง (ก่อน escape hatch 14 วันจะเปิดอีกนาน)
- **ความผิดปกติ**: หนุนไม่พอ (`reserves()` ต่ำกว่า 99.5 %), mint พุ่ง (10 เท่าของค่าปกติรายชั่วโมง) หรือข้อความยังค้างหลังส่งซ้ำครบ:
  **สั่ง CircuitBreaker ของเส้นทาง** พร้อมหลักฐานที่แฮชแล้ว (เป็นการยืนยันของ runner ตัวนี้ องค์ประชุมของ runner เป็นผู้ตัดสิน)

มันไม่เคยย้ายเงิน และไม่เคยยกเลิกการหยุด ข้อผิดพลาดในการอ่านหรือการกระทำถูกบันทึก ไม่ทำให้ล่ม
`node scripts/saphan.js heal once` รันหนึ่งรอบกับเส้นทางที่ deploy แล้ว ถ้าไม่ใส่ `--act yes` จะบอกแค่ว่าจะทำอะไร

1. ออนไลน์ครั้งเดียว: approve `SaphanOfflineTransfers` สำหรับโทเคนของเส้นทางบน ZETAPHY
2. ออฟไลน์: `node scripts/saphan.js offline sign --contract 0x… --outbox 0x… --to 0x… --amount <wei> --fee <wei>`
   พิมพ์ข้อความ `ZSPH1:…` (ใส่ใน QR code ได้)
3. ใครก็ได้ที่ออนไลน์: `offline check` (ลายเซ็น, เส้นตาย, เส้นทางที่รู้จัก) แล้ว `offline relay`: สัญญาดึงจำนวน + ค่าธรรมเนียม
   จากผู้ลงนาม จ่ายค่าธรรมเนียมให้ผู้ส่งต่อ และส่งจำนวนนั้นผ่าน outbox ของเส้นทาง จากนั้นเป็นการโอนปกติ:
   วงเงินและการหยุดของ guard, ช่วงรอ veto และวงเงินรายวันของ lockbox ใช้ทั้งหมด

ผู้ส่งต่อเปลี่ยนสิ่งที่ลงนามแล้วไม่ได้ (เส้นทาง, ผู้รับ, จำนวน, ค่าธรรมเนียม) แต่ละ nonce ใช้ได้ครั้งเดียว `cancel(nonce)` ยกเลิกได้
ทำได้ทิศทางเดียว (ZETAPHY -> เชนต้นทาง): การล็อกเหรียญหลักบนเชนต้นทางต้องเป็นธุรกรรมของผู้ส่งเอง

## ที่ยังไม่เสร็จ

- S7 ยังเป็นต้นแบบจนกว่าจะมี peg-out จริงบน Bitcoin และผ่านการตรวจสอบ
- พูลความเป็นส่วนตัวต้องมี trusted setup แบบหลายฝ่ายก่อนจะปกป้องอะไรที่มีค่าได้
- สัญญาสภาพคล่องลดวงเงินได้เองเท่านั้น การเพิ่มยังเป็นหน้าที่ของ timelock ของแต่ละเชน (ตั้งใจให้เป็นแบบนี้)
- เชนใหม่ต้อง deploy เส้นทาง (workflow saphan-route) และตรวจที่อยู่บนเชนก่อน
- หน้าจอใน hub สำหรับฟีเจอร์เหล่านี้ไม่อยู่ใน PR นี้ (มีสัญญาและ CLI)
