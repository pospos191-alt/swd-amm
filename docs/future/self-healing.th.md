# ระบบซ่อมตัวเอง: หยุดการโจมตีที่กำลังเกิดขึ้น เฉพาะจุดและในเวลาจำกัด

**ต้นแบบบนเทสต์เน็ต** ไม่ใช่เงินจริง และสัญญายังไม่ผ่านการตรวจสอบ (audit)

ถ้า Neuro เห็นว่ามีคนกำลังโจมตีโปรโตคอลไหนอยู่ เชนควรหยุดความเสียหายได้ภายในไม่กี่วินาที ไม่ใช่รอเป็นชั่วโมงให้คนถือมัลติซิกตื่นมากด
แต่ก็ต้องไม่มีใครถือกุญแจ "หยุดทุกอย่าง" ไว้ในมือ ต้นแบบนี้ทำได้ทั้งสองอย่าง แต่เฉพาะกับโปรโตคอลที่**สมัครใจเข้าร่วม**เท่านั้น
การตัดวงจรแต่ละครั้งมีลักษณะดังนี้

- **เฉพาะจุด** หยุดเฉพาะฟังก์ชันที่โปรโตคอลระบุไว้ และเฉพาะฟังก์ชันที่หลักฐานชี้ว่าเกี่ยวข้อง
- **มีกำหนดเวลา** หมดอายุเองเสมอ
- **ย้อนกลับได้** ธรรมาภิบาลของโปรโตคอลเองสั่งยุติได้ทันที และ timelock ของเชนยับยั้ง (veto) ได้
- **อนุมัติไว้ล่วงหน้า** ขอบเขตทุกอย่างโปรโตคอลเลือกเองตั้งแต่ตอนสมัคร
- **ใช้ในทางที่ผิดแล้วต้องจ่าย** ผู้รันที่ลงนามตัดวงจรผิดเสียเงินค้ำประกัน และเงินนั้นชดเชยให้โปรโตคอล

| ส่วน | อยู่ที่ |
|---|---|
| `CircuitBreaker` นโยบาย ผู้รันที่วางเงินค้ำประกัน การตัดวงจร เพดานเงินไหลออก การเคลม และการริบเงินค้ำประกัน | `zetaphy-network/contracts/CircuitBreaker.sol` |
| `CircuitBreakable` สิ่งที่โปรโตคอลต้องเพิ่ม (`whenNotTripped(selector)`, `_outflow`, การพักการจ่าย) | `zetaphy-network/contracts/CircuitBreakable.sol` |
| ตัวตรวจจับ: log, trace, z-score, reentrancy, การสแกน bytecode, ราคาออราเคิลเบี่ยง | `zetaphy-network/src/selfheal/detect.js` |
| ผู้รันแต่ละคน: คำนวณซ้ำแล้วลงนาม การรวบรวมลายเซ็น k จาก n (จำลอง) | `zetaphy-network/src/selfheal/peers.js` |
| ลูปตรวจจับ: อ่านทีละบล็อก เสนอ รวบรวมลายเซ็น แล้วส่ง `tripWithSignatures` | `zetaphy-network/src/selfheal/loop.js` |
| เดโมครบวงจร (vault ถูกดูดเงินหลายบล็อก เทียบปิดกับเปิด) | `zetaphy-network/scripts/selfheal-demo.js`, `test/helpers/selfhealdemo.js` |
| การทดสอบ | `zetaphy-network/test/selfheal.test.js`, `selfheal-detect.test.js`, `selfheal-e2e.test.js` |
| การ์ด "ระบบซ่อมตัวเอง" ในฮับ (แท็บ On-chain AI อ่านอย่างเดียว) | `zetaphy-hub/aichain.js` |

## 1. โปรโตคอลเข้าร่วมอย่างไร

สัญญาของโปรโตคอลเรียก `CircuitBreaker.register(policy)` เอง แปลว่าธรรมาภิบาลของโปรโตคอลเป็นคนตัดสินใจ
นโยบายนี้คือทุกอย่างที่การตัดวงจรทำกับโปรโตคอลได้

| ฟิลด์ | ความหมาย | ขอบเขต (ค่าคงที่) |
|---|---|---|
| `governance` | ธรรมาภิบาลของโปรโตคอลเอง: ปลดการตัดวงจร เปลี่ยนนโยบาย ออกจากระบบ ยกเลิกการจ่ายที่พักไว้ และเคลมว่าตัดผิด | ห้ามเป็น 0 |
| `selectors` | ฟังก์ชันที่ยอมให้หยุดได้ | ไม่เกิน 16 |
| `invariantMask` | ฟังก์ชันไหนบ้างที่หยุดเมื่อตัดวงจรเพราะเกินเพดาน | ต้องอยู่ใน `selectors` |
| `assets`, `caps`, `window` | เพดานเงินไหลออกต่อช่วงเวลา แยกตามสินทรัพย์ (0 = เหรียญหลักของเชน) | ไม่เกิน 8 สินทรัพย์ ช่วงเวลา 1 นาทีถึง 1 วัน |
| `tripCapBps`, `holdAbove` | ระหว่างตัดวงจร เพดานลดเหลือ `tripCapBps` และการจ่ายครั้งเดียวที่เกิน `holdAbove` จะถูก**พักไว้** | ไม่เกิน 100% |
| `holdReview` | การจ่ายที่พักไว้ต้องรอนานเท่าไรก่อนที่ใครก็จ่ายต่อได้ | ไม่เกิน 7 วัน |
| `maxPause` | การตัดวงจรแต่ละครั้งนานเท่าไร | 10 นาทีถึง 3 วัน |
| `quorum` | ต้องมีผู้รันที่วางเงินค้ำประกันกี่คนลงนามหลักฐานชุดเดียวกัน | `minQuorum` ถึง 16 |

การเปลี่ยนนโยบายหรือการออกจากระบบต้องรอ `POLICY_DELAY` (2 วัน) และทำไม่ได้ระหว่างที่ตัดวงจรอยู่
ผู้โจมตีที่ยึดธรรมาภิบาลได้จึงคลายตัวตัดวงจรกลางการโจมตีไม่ได้

ฝั่งสัญญาเพิ่มแค่สามอย่าง (ดู `HealVault` ใน `test/helpers/SelfHealKit.sol`)

```solidity
contract Vault is CircuitBreakable {
    constructor(ICircuitBreaker b) CircuitBreakable(b) {}
    function withdrawAll() external whenNotTripped(this.withdrawAll.selector) {
        uint256 amount = balances[msg.sender];
        bool pay = _outflow(address(0), msg.sender, amount); // แจ้งเงินไหลออก ถ้าได้ false แปลว่าพักไว้
        if (pay) _payOut(address(0), msg.sender, amount);
        balances[msg.sender] = 0;
    }
    function _payOut(address, address to, uint256 amount) internal override { /* โอน */ }
}
```

ถ้า `_outflow` คืนค่า false การจ่ายนั้นจะถูก**พักไว้** เงินยังอยู่ในโปรโตคอล ธุรกรรมไม่ revert และการจ่ายถูกบันทึกไว้ใน `held`
ที่ไม่ revert เพราะถ้า revert การตัดวงจรที่ธุรกรรมเดียวกันเพิ่งทำให้เกิดจะถูกย้อนไปด้วย
พอการตัดวงจรจบและพ้น `holdReview` แล้ว ใครก็เรียก `releaseHeld` จ่ายต่อได้ (นับกับเพดานใหม่อีกรอบ)
หรือธรรมาภิบาลของโปรโตคอลจะยกเลิกด้วย `cancelHeld` ก็ได้ แล้วเงินก็อยู่ในโปรโตคอลต่อไป

## 2. ตัดวงจรได้สองทาง ไม่มีทางอื่น

1. **หลักฐานจากผู้รัน (k จาก n)** ผู้รันที่มีสิทธิ์อย่างน้อย `quorum` คนที่ไม่ซ้ำกันลงนาม digest เดียวกัน

   `{chainId, breaker, protocol, epoch, fromBlock, toBlock, evidenceHash, detectorId, mask}`

   ลงนามได้สองแบบ
   - ลายเซ็น ECDSA ที่รวบรวมนอกเชน แล้วใครก็ส่งเข้า `tripWithSignatures` ได้ ผู้ลงนามต้องเรียงจากน้อยไปมากเคร่งครัด
     คนเดียวจึงนับซ้ำไม่ได้
   - ผู้รันแต่ละคนส่ง `attest()` เองคนละหนึ่งธุรกรรม ใช้ได้กับบัญชีทุกชนิด ผู้รันที่ใช้บัญชี ML-DSA
     จึงยืนยันแบบทนควอนตัมผ่าน `MsgEVMCall` ได้

   **มีสิทธิ์** แปลว่าครบทุกข้อนี้
   - เป็นผู้รัน NeuroJobs ที่ยังทำงานอยู่และมีเงินค้ำประกัน
   - มีคำตัดสินที่ได้รับการยอมรับอย่างน้อย `minAgreed` ครั้ง
   - วาง**เงินค้ำประกันผู้พิทักษ์**ไว้ที่สัญญานี้

   การริบเงินค้ำประกันเกิดที่สัญญานี้ เพราะเงินค้ำประกันของ NeuroJobs ถูกริบจากภายนอกไม่ได้
   ตอนนับครบองค์ประชุม สัญญาตรวจผู้ยืนยันทุกคนซ้ำอีกรอบ ใครหมดสิทธิ์ไปแล้วจะไม่ถูกนับ

   หลักฐานต้อง**สด**
   - ช่วงบล็อกจบไม่เกิน 64 บล็อกที่แล้ว
   - ยาวไม่เกิน 256 บล็อก
   - เริ่มหลังช่วงของการตัดวงจรครั้งก่อน
   - แฮชต้องไม่เคยใช้มาก่อน

   `epoch` เพิ่มขึ้นทุกครั้งที่ตัดวงจร ลายเซ็นเก่าจึงใช้ไม่ได้อีก และ `mask` ต้องอยู่ในฟังก์ชันที่นโยบายระบุไว้

2. **เงื่อนไขบนเชน (invariant)** ตัวตัดวงจรเห็นเองว่าการจ่ายครั้งหนึ่งจะทำให้เกินเพดานของช่วงเวลานั้น (`recordOutflow`)
   จึงตัดวงจรด้วย `invariantMask` และพักการจ่ายนั้นไว้ โดยไม่ต้องใช้ผู้รันเลย

ตัดวงจรติดกันได้ไม่เกิน `MAX_STREAK` (3) ครั้ง "ติดกัน" แปลว่าแต่ละครั้งเริ่มภายใน `maxPause` นับจากที่ครั้งก่อนจบ
หลังจากนั้นธรรมาภิบาลของโปรโตคอลต้องสั่ง `rearm` ก่อน ผู้รันจึงต่อการตัดวงจรเพื่อขังโปรโตคอลไว้ตลอดไปไม่ได้
ถ้าเงียบไปนาน `maxPause` ตัวนับจะเริ่มใหม่

## 3. ตัดวงจรแล้วเกิดอะไร และจบอย่างไร

- `isPaused(protocol, selector)` เป็นจริงเฉพาะฟังก์ชันใน mask ของการตัดวงจร และเฉพาะช่วงที่
  `block.timestamp < until` (`start + maxPause`) ฟังก์ชันอื่นใช้ได้ตามปกติ ในเดโม ฝากเงินกับ `withdraw`
  ที่เขียนถูกยังใช้ได้ ขณะที่ `withdrawAll` หยุด
- เงินยังไหลออกได้ แต่เพดานลดเหลือ `tripCapBps` และการจ่ายก้อนใหญ่ถูกพักไว้
- การตัดวงจรจบได้สามแบบ
  - จบเองที่ `until` (เกิดขึ้นเสมอ)
  - ธรรมาภิบาลของโปรโตคอลสั่งจบก่อน (`release`)
  - timelock ของเชนสั่งจบก่อน (`veto`)
- **ไม่มีกุญแจแอดมิน** ธรรมาภิบาลของเชนคือ ZetaphyTimelock ซึ่งทำได้แค่
  - ตั้งพารามิเตอร์ที่มีขอบเขต (เงินค้ำประกัน เงินค้ำการเคลม `minQuorum` ≥ 2, `minAgreed` และสัดส่วนที่ริบได้ไม่เกิน 50%)
  - veto การตัดวงจร
  - ตัดสินการเคลมว่าตัดผิด

  timelock **ไม่มีฟังก์ชันไหนที่หยุดอะไรได้เลย**

## 4. ตัดวงจรผิด: ริบเงินค้ำประกันและชดเชย

- ภายใน `CLAIM_WINDOW` (7 วัน) หลังการตัดวงจรโดยผู้รัน ธรรมาภิบาลของโปรโตคอลเรียก `claimFalse(id)` ได้ โดยวางเงินค้ำการเคลม
- timelock ตัดสินด้วย `resolveClaim`
  - **พิสูจน์ได้ว่าตัดผิด** ผู้ลงนามแต่ละคนเสีย `slashBps` (ค่าเริ่มต้น 50%) ของเงินค้ำประกัน
    80% ของเงินที่ริบได้ทั้งหมดไปที่ธรรมาภิบาลของโปรโตคอล พร้อมคืนเงินค้ำการเคลม ส่วนที่เหลือถูกเผา
    ผู้ที่เงินค้ำประกันเหลือต่ำกว่าเกณฑ์จะหมดสิทธิ์จนกว่าจะเติมเงิน
  - **ปฏิเสธการเคลม** เงินค้ำการเคลมแบ่งให้ผู้ลงนาม การเคลมมั่วๆ จึงมีต้นทุนเหมือนกัน
- **ไม่มีการตัดสินภายใน 14 วัน** ใครก็เรียก `expireClaim` ได้ เงินค้ำการเคลมคืนเจ้าของ และไม่มีใครถูกริบ
- ผู้ลงนามถอนตัวไม่ได้ ตราบที่การตัดวงจรที่ตัวเองลงนามยังถูกเคลมได้หรือยังรอตัดสินอยู่ (`lockedUntil`, `openClaims`)
  จึงลงนามมั่วแล้วหนีไม่ได้

## 5. ตัวตรวจจับ (นอกเชน ผลลัพธ์ตายตัว)

ผู้รันที่สุจริตทุกคนต้องคำนวณ**หลักฐานชุดเดียวกัน**จากเชนได้ เพื่อให้ k คนลงนามแฮชเดียวกัน
`evaluate(cfg, data, from, to)` จึงเป็นฟังก์ชันบริสุทธิ์ที่อ่านแค่ log, โค้ด และ (ถ้าตั้งไว้) call trace ในช่วงบล็อกนั้น
บวกช่วงย้อนหลังที่ตายตัว 40 บล็อก หลักฐานเป็น JSON แบบ canonical ที่แฮชด้วย sha256 เหมือนแฮชรายงานของ Neuro
ในหลักฐานมี

- ปริมาณเงินไหลออกต่อบล็อก
- ค่าฐาน (baseline)
- ผู้รับเงิน
- สัญญาณที่พบ

| สัญญาณ | อ่านจากอะไร |
|---|---|
| `volume` | เงินไหลออกของบล็อกสูงผิดปกติตาม z-score (z ≥ 3 โดยส่วนเบี่ยงเบนมาตรฐานไม่ต่ำกว่า 25% ของค่าเฉลี่ย) เทียบกับช่วงย้อนหลัง โดยนับบล็อกที่ไม่มีอะไรเป็น 0 และต้องเกินขั้นต่ำแบบตายตัวด้วย |
| `burst` | reentrancy จาก log: จ่ายให้ผู้รับคนเดียวตั้งแต่ 3 ครั้งในธุรกรรมเดียว |
| `trace` | reentrancy จาก call trace (`callTracer`): โปรโตคอลเรียกออกไป แล้วภายในการเรียกนั้นมีการเรียกกลับเข้าโปรโตคอลอีก (ใช้เฉพาะเมื่อ watch config ตั้ง `traces` ไว้ เพื่อให้ผู้รันทุกคนใช้ข้อมูลเดียวกัน) |
| `callback` | สแกน bytecode ด้วย Neuro (`zetaphy-neuro/src/bytecode.js`): โค้ดของผู้รับมี selector ของฟังก์ชันที่หยุดได้ของโปรโตคอลอยู่ |
| `fresh` | ผู้รับเป็นสัญญาที่ไม่เคยได้รับเงินในช่วงย้อนหลัง |
| `oracle` | ราคาจากฟีดที่ตั้งไว้เบี่ยงจากค่ามัธยฐานของช่วงย้อนหลังตั้งแต่ 20% |

เงินไหลออกอ่านจากอีเวนต์ที่โปรโตคอลตั้งไว้ และจาก `Transfer` ของ ERC-20 ที่ออกจากโปรโตคอล (ใช้ `decodeLogs` ของ Neuro)

**เกณฑ์ตัดวงจร** ต้องมี `volume` **และ**สัญญาณยืนยันอีกอย่าง คือ `burst`, `trace` หรือ `oracle`
อีกทางหนึ่งคือรูปแบบที่ไม่รู้จักแต่รุนแรงมาก: z ≥ 30 และอย่างน้อย 100 เหรียญ จ่ายให้สัญญา `fresh` ที่มี `callback`
ถ้ามีแค่ปริมาณสูงผิดปกติอย่างเดียว เช่นวาฬถอนเงินก้อนใหญ่ จะถูกบันทึกเป็นการแจ้งเตือนเท่านั้น ไม่ตัดวงจร

**mask** หยุดเฉพาะฟังก์ชันที่อีเวนต์เงินไหลออกของบล็อกผิดปกตินั้นพาเงินออกไป

**ลูป** (`loop.js`) อ่านทุกบล็อกใหม่ เมื่อบล็อกไหนผิดปกติสำหรับโปรโตคอลที่ยังไม่ถูกตัดวงจร ลูปจะ

1. สร้างข้อเสนอ
2. ส่งข้อเสนอให้ผู้รันคนอื่น ผู้รันแต่ละคน**คำนวณหลักฐานซ้ำเอง**จากมุมมองของตัวเองต่อเชน
   และลงนามเฉพาะเมื่อผลของตัวเองผิดปกติ ได้แฮชและ mask ตรงกัน (`peers.js`)
3. ตรวจลายเซ็นทุกอัน
4. ส่ง `tripWithSignatures` เมื่อได้ครบองค์ประชุม

การแลกเปลี่ยนระหว่างผู้รันในต้นแบบนี้จำลองไว้ในหน่วยความจำ ถ้าใช้งานจริงจะส่งผ่านช่องทางสื่อสารที่ผู้รันมีอยู่แล้ว

## 6. ตัวเลขจากเดโม (เชนในหน่วยความจำ `node scripts/selfheal-demo.js 200 7`)

สภาพแวดล้อม

- vault ที่มีบั๊ก reentrancy แบบตำรา (`withdrawAll` จ่ายเงินก่อนแล้วค่อยล้างยอด) ถือเงินอยู่ราว 4,600 เหรียญ
- เริ่มด้วยการใช้งานปกติ 200 บล็อก: ผู้ใช้ 10 คนฝากถอนครั้งละ 1–20 เหรียญ กระเป๋าแบบสัญญาอัจฉริยะหนึ่งใบ
  และวาฬที่ถอนและฝากครั้งละ 120 เหรียญเป็นระยะ
- จากนั้นผู้โจมตี deploy สัญญา ทุกบล็อกฝาก 10 แล้วเรียกกลับเข้ามาซ้ำ 9 ครั้ง ได้เงินบล็อกละ 100 เหรียญ
  หลังการโจมตีแต่ละครั้งมีผู้ใช้สุจริตถอนเงินตามมา
- บล็อกจำลองห่างกัน 5 วินาที

| รอบ | เสียไป | บล็อกโจมตีที่ผ่าน | ตัดวงจรด้วย | เวลาที่ใช้ตรวจจับ | ตัดวงจรผิด (ช่วงใช้งานปกติ) | ผู้ใช้สุจริตถอนสำเร็จ |
|---|---|---|---|---|---|---|
| ปิดระบบซ่อมตัวเอง | 4,490 (vault หมดเกลี้ยง) | 50 | – | – | – | 50/50 |
| เปิด หลักฐานจากผู้รัน (3 จาก 5) | **90** | 1 | ผู้รัน | **1 บล็อก** (ตัดวงจรในบล็อกถัดจากบล็อกผิดปกติแรก ราว 5 วินาที) | **0** (สแกน 214 บล็อก z-score เตือน 3 ครั้ง ไม่ตัดวงจรเลย) | 60/60 |

ลองอีก seed หนึ่ง (`200 11`) ได้ภาพเดียวกัน: ปิดระบบเสีย 2,820 แบบผู้รันเสีย 90 มีการเตือนจาก z-score อย่างเดียว 7 ครั้ง
และตัดวงจรผิด 0 ครั้ง

ตารางนี้บอกอะไร

- **แบบหลักฐานจากผู้รันรักษาเงินไว้ได้** 4,400 จาก 4,490 (98%) มีแค่บล็อกโจมตีแรกที่ผ่าน และหยุดแค่ `withdrawAll`
- ถ้าใช้ตัวเฝ้าดูแบบ z-score อย่างเดียว จะแจ้งเตือน 3 ครั้งในช่วงใช้งานปกติ แต่เกณฑ์ที่ต้องมีสัญญาณยืนยัน
  ทำให้ไม่มีครั้งไหนกลายเป็นการตัดวงจร
- แบบเพดานบนเชนไม่ต้องใช้ผู้รันเลย และจำกัดความเสียหายต่อช่วงเวลาได้ แต่ดีได้เท่าที่ตั้งค่าไว้
  ถ้าตั้งเพดานต่ำกว่าการใช้งานปกติก็ตัดวงจรผิด เพดานจึงต้องให้โปรโตคอลอนุมัติเอง
  และการตัดวงจรแบบนี้ไม่มีใครถูกริบเงินค้ำประกัน เพราะไม่มีใครลงนาม

**การก่อกวน** (`test/selfheal-e2e.test.js`)

- **ผู้รันส่วนน้อยที่สมคบกัน** (2 จาก 5 องค์ประชุม 3) เสนอหลักฐานที่แต่งขึ้น ผู้รันสุจริต 3 คนปฏิเสธ
  ("มุมมองของฉันต่อเชนไม่พบความผิดปกติ") และสัญญาปฏิเสธลายเซ็น 2 อันด้วย `NoQuorum`
  การใส่ลายเซ็นซ้ำถูกปฏิเสธ (`NotSorted`) การเติมลายเซ็นของคนนอกก็เช่นกัน (`BadSignature` หรือ `NotEligible`)
  ผู้เสนอที่แอบแก้ mask ของความผิดปกติจริงก็ถูกปฏิเสธ เพราะผู้รันสุจริตคำนวณ mask ซ้ำเอง
- **ผู้รันที่สมคบกันจนครบองค์ประชุม** (3 จาก 5) ตัดวงจรโปรโตคอลที่ปกติดีได้หนึ่งครั้ง แต่ถึงอย่างนั้น
  - การตัดวงจรยังเฉพาะจุด: ฝากเงินได้ตามปกติ
  - ธรรมาภิบาลของโปรโตคอลปลดได้ทันที
  - พอพิสูจน์ได้ว่าตัดผิด ผู้สมคบแต่ละคนเสียเงินค้ำประกันครึ่งหนึ่ง (5 จาก 10 เหรียญ)
  - โปรโตคอลได้ 80% ของ 15 เหรียญที่ริบมา พร้อมเงินค้ำการเคลมคืน
  - ผู้สมคบหมดสิทธิ์ลงนาม

## 7. ภัยที่คิดไว้

| ภัย | อะไรกันไว้ |
|---|---|
| กุญแจดอกเดียวหยุดโปรโตคอลได้ | ไม่มีกุญแจแบบนั้น การตัดวงจรโดยผู้รันต้องมีผู้รันที่มีสิทธิ์และวางเงินค้ำประกันครบ `quorum` (≥ `minQuorum` ≥ 2) และธรรมาภิบาลไม่มีฟังก์ชันหยุด |
| ผู้รันขังโปรโตคอลไว้ไม่ปล่อย | การตัดวงจรทุกครั้งหมดอายุ (ไม่เกิน 3 วัน ตาม `maxPause` ที่โปรโตคอลตั้งเอง) ทุกครั้งต้องใช้หลักฐานใหม่ (ช่วงบล็อกหลังครั้งก่อน แฮชใหม่ epoch ใหม่) ติดกันได้ไม่เกิน `MAX_STREAK` ครั้ง จากนั้นโปรโตคอลต้อง rearm เอง |
| ผู้รันตัดวงจรโปรโตคอลที่ปกติดี (ก่อกวน กรรโชก หรือเปิดชอร์ตรอ) | ต้องสมคบกันครบองค์ประชุม การตัดวงจรเฉพาะจุด (ฟังก์ชันที่ระบุไว้เท่านั้น) โปรโตคอลปลดได้ทันที ผู้ลงนามทุกคนเสียเงินค้ำประกันซึ่งไปชดเชยโปรโตคอล และถอนตัวไม่ได้จนกว่าช่วงเคลมจะจบ |
| ผู้โจมตีชิงทำก่อนหรือถ่วงการตัดวงจร | ตัวตรวจจับตัดวงจรในบล็อกถัดจากบล็อกผิดปกติแรก เพดานบนเชนไม่ต้องรอขั้นตอนนอกเชน และการพักการจ่ายทำให้เงินก้อนหลังๆ ของผู้โจมตียังอยู่ในโปรโตคอล |
| ผู้โจมตีซอยการดูดเงินให้ต่ำกว่าเกณฑ์ตรวจจับ | เพดานต่อช่วงเวลาบังคับบนเชนเสมอไม่ว่าตัวตรวจจับจะเห็นอะไร และลดเหลือ `tripCapBps` ระหว่างตัดวงจร |
| ผู้โจมตียึดธรรมาภิบาลของโปรโตคอลได้ | ปลดการตัดวงจรได้ แต่คลายนโยบายหรือออกจากระบบระหว่างตัดวงจรไม่ได้ และนอกช่วงนั้นก็ต้องรอ 2 วัน ส่วนการยับยั้งเพิ่มเติมมีแค่ veto ของ timelock |
| เอาลายเซ็นเก่ามาใช้ซ้ำ | digest ผูกกับ chain id, ตัวตัดวงจร, โปรโตคอล, epoch, ช่วงบล็อก และแฮชหลักฐาน แฮชที่ใช้แล้วถูกปฏิเสธ |
| ดัดแปลงลายเซ็น (malleability) | รับเฉพาะ low-s และ v เป็น 27 หรือ 28 ผู้ลงนามต้องเรียงจากน้อยไปมากเคร่งครัด |
| บั๊กในตัวตัดวงจรทำให้โปรโตคอลพัง | `whenNotTripped` แค่อ่าน `isPaused` โปรโตคอลที่ deploy ด้วยที่อยู่ตัวตัดวงจรเป็น 0 จะไม่ถูกแตะเลย และการตัดวงจรหมดอายุเสมอ |

## 8. ทำไมต้องสมัครใจและเฉพาะจุด

ปุ่มหยุดทั้งเชนคือเครื่องมือเซ็นเซอร์ พอมีขึ้นมาแล้ว สักวันต้องมีคนถูกขอให้กดใช้
และการกดหยุดทั้งเชนเพื่อช่วยโปรโตคอลเดียว ก็ทำให้ผู้ใช้สุจริตของทุกโปรโตคอลใช้งานไม่ได้ไปด้วย

ในระบบนี้ สัญญาที่ไม่ได้ลงทะเบียนจะไม่โดนอะไรเลย สัญญาที่ลงทะเบียนแล้วกำหนดเองล่วงหน้าว่า

- ฟังก์ชันไหนหยุดได้
- หยุดได้นานแค่ไหน
- ไว้ใจผู้รันกี่คน
- ให้เงินออกได้เท่าไรต่อช่วงเวลา

โปรโตคอลจึงยอมรับความเสี่ยงที่จะถูกตัดวงจรผิดโดยรู้ตัว โดยความเสี่ยงนั้นมีขอบเขตและได้รับการชดเชย
แลกกับการเสียแค่หนึ่งบล็อกของการโจมตีแทนที่จะเสียทั้งคลัง การหยุดเฉพาะจุดยังทำให้การตัดวงจรผิดเสียหายน้อยลงด้วย
ในเดโม ผู้ใช้ยังฝากถอนได้ตามปกติระหว่างที่ `withdrawAll` หยุด

## 9. เทียบกับระบบอื่น

| | ใครตัดสินใจ | ผลที่เกิด | มีขอบเขต / หมดอายุ | ต้นทุนของการใช้ผิด |
|---|---|---|---|---|
| **Forta** (บอตตรวจจับ + Firewall) | บอตแจ้งเตือน แล้วกุญแจของโปรโตคอลเองหรือกฎ firewall เป็นตัวลงมือ | แล้วแต่ฟังก์ชันหยุดของโปรโตคอล ส่วน Forta Firewall คัดกรองธุรกรรมก่อนรันบน rollup ที่รองรับ | แล้วแต่โปรโตคอล | stake ของบอต (เพื่อคุณภาพการแจ้งเตือน) ไม่ได้ผูกกับการหยุดผิด |
| **Hypernative** | ตรวจจับด้วย ML แล้วโปรโตคอลอนุญาตให้ตอบสนองอัตโนมัติไว้ล่วงหน้า (มักเป็นการหยุดผ่านมัลติซิกหรือโมดูล guardian) | ส่วนใหญ่หยุดทั้งโปรโตคอล | แล้วแต่โปรโตคอล | ไม่มีบนเชน |
| **Hexagate** (Chainalysis) | จำลองธุรกรรมล่วงหน้าและตรวจจับด้วย ML แล้วกุญแจ guardian ของโปรโตคอลสั่งหยุดหรือบล็อก | หยุดทั้งหมดหรือบล็อกธุรกรรม | แล้วแต่โปรโตคอล | ไม่มีบนเชน |
| **ตัวตัดวงจรระดับเชน** (เช่น ERC-7265 ที่จำกัดอัตราเงินไหลออกของโทเคน หรือตัวตัดวงจรสะพานที่ validator รัน อย่างข้อ #31 ของ ZETAPHY) | เพดานอัตราบนเชน หรือ validator เสียงข้างมากพิเศษ | หน่วงหรือล็อกการถอนที่เกินอัตรา หรือหยุดสะพาน | ERC-7265: ชำระหลังช่วงผ่อนผัน ส่วน #31: จนกว่าธรรมาภิบาลจะ unpause | ไม่มี (เพดานอัตรา) หรือ stake ของ validator |
| **ต้นแบบนี้** | ผู้รัน Neuro k จาก n คนที่วางเงินค้ำประกันและคำนวณหลักฐานเดียวกันได้ หรือเพดานบนเชน | หยุดเฉพาะฟังก์ชันที่ระบุไว้และเกี่ยวข้อง ลดเพดาน และพักการจ่ายก้อนใหญ่ | หมดอายุเสมอ (≤ `maxPause`) โปรโตคอลปลดเองได้ และ timelock veto ได้ | เงินค้ำประกันที่ถูกริบ ซึ่งจ่ายให้โปรโตคอล |

สิ่งที่ใหม่ในต้นแบบนี้

- การตัดวงจร**กระจายอำนาจและตรวจสอบย้อนได้** มาจากองค์ประชุมของผู้รันที่วางเงินค้ำประกันและต้องทำหลักฐานซ้ำได้
  ไม่ใช่กุญแจของผู้ให้บริการรายเดียว
- **ถูกจำกัดด้วยนโยบายของโปรโตคอลเอง**
- **คนที่ตัดวงจรผิดเป็นคนจ่าย**

แนวคิดเพดานอัตราแบบ ERC-7265 ใส่ไว้ในโหมด invariant ด้วย เหมาะเป็นด่านสำรองที่ไม่ต้องพึ่งตัวตรวจจับ

## 10. ข้อจำกัด (ต้นแบบ)

- การแลกเปลี่ยนระหว่างผู้รันจำลองอยู่ในโปรเซสเดียว ของจริงต้องมีช่องทางสื่อสารและการหมุนเวียนผู้เสนอ
  ยังไม่มีแรงจูงใจให้รวบรวมลายเซ็น และยังไม่มีใครได้ค่าตอบแทนเมื่อตัดวงจรถูก
- ตัวตรวจจับเป็นแบบฮิวริสติก การโจมตีรูปแบบใหม่ที่ไม่มีลักษณะ reentrancy ไม่มีราคาออราเคิลขยับ
  และไม่มีเงินก้อนผิดปกติสุดขีดจ่ายให้สัญญาใหม่ที่เรียกกลับ จะถูกจับได้ด้วยเพดานเงินไหลออกเท่านั้น
  การดูดเงินช้าๆ ที่ต่ำกว่าเพดานต่อช่วงเวลาจับไม่ได้
- หลักฐานต้องทำซ้ำได้ในผู้รันทุกคน ตัวตรวจจับจึงใช้ข้อมูล mempool ส่วนตัวหรือ ML ที่ผลไม่ตายตัวไม่ได้
  ถ้าจะใช้โมเดลของ Neuro ต้องตรึงรุ่นไว้ด้วย `ModelEpochs`
- timelock เป็นผู้ตัดสินการเคลมว่าตัดผิด ซึ่งช้า (ตามระยะหน่วงของ timelock) และมีเรื่องการเมือง
  การตัดสินด้วยการเล่นซ้ำแบบที่ผู้รันของ HackInsurance ทำจะดีกว่า

  - digest ที่คำนวณในเครื่องตรงกับของสัญญา
  - สิทธิ์ตาม NeuroJobs
  - การยืนยันบนเชน
  - หลักฐานต้องสด
  - ผลแบบเฉพาะจุด
  - หมดอายุ ปลด และ veto
  - streak
  - ธรรมาภิบาลไม่มีอำนาจหยุด
  - การตัดวงจรเพราะเกินเพดานและการพักการจ่าย
  - การริบเงินค้ำประกันและการชดเชย

  และโหมดเพดานอย่างเดียวพร้อมความเสี่ยงจากการตั้งค่า
