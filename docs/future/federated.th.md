## หัวข้อ 6: federated learning

### ทำไมเทรน "หัว" ไม่ใช่ต้นไม้

โมเดลของ Neuro (`ml/model.json`) คือ gradient-boosted trees 160 ต้น ต้นไม้นำมาเฉลี่ยข้ามไคลเอนต์ไม่ได้
จึงเทรน **หัว logistic regression** ขนาดเล็กบนต้นไม้ที่ตรึงไว้:

```
phi(x) = [ 1, margin_gbdt(x), clamp(x_j, -8, 8) ของฟีเจอร์ที่ตั้งชื่อ 28 ตัว ]   (เลือกได้: + ค่าใบของต้นไม้แต่ละต้น)
z(x)   = margin_gbdt(x) + theta . phi(x)
p      = sigmoid(calib.a * z + calib.b)
```

- `theta = 0` คือโมเดลที่ commit อยู่พอดีทุกบิต (ทดสอบแล้ว) หัวที่ commit ไว้ `ml/fl/head.json` จึงไม่เปลี่ยนอะไรจนกว่า
  การโหวตจะรับหัวที่เทรนแล้ว
- ฟีเจอร์ 28 ตัวคือกฎ, กลเม็ดของเจ้าของ, ผลจำลองซื้อขาย และข้อมูลตลาด (`DEFAULT_HEAD_FEATURES`) ซึ่งเป็นจุดที่กลโกงแบบใหม่โผล่ก่อน
- `leaves: true` เพิ่มน้ำหนักหนึ่งตัวต่อต้นไม้ (แบบ "หัวบนฟีเจอร์ใบของต้นไม้") ทำและทดสอบแล้วแต่ปิดไว้เป็นค่าเริ่มต้น
  เพราะสัญญาณรบกวนเพื่อความเป็นส่วนตัวใส่ทุกพิกัดเท่ากัน มิติยิ่งมาก สัญญาณต่อสัญญาณรบกวนยิ่งต่ำ (ในการจำลอง AUC 0.786 เทียบ 0.800)
- **ขอบเขตความเชื่อถือ (trust region)**: `||theta|| <= maxNorm` (4) ไม่ว่าการอัปเดตจะเป็นอย่างไร หัวขยับคะแนนได้ไม่เกิน
  `maxNorm x ||phi(x)||` logit จากต้นไม้ที่ governance อนุมัติ
- หัวเป็นเพียงคำแนะนำเหมือนต้นไม้: `combine.js` ยังไม่เคยลดระดับที่กฎตัดสิน และโมเดลยังไม่อยู่ใน verdict ของเครือข่ายหรือ reportHash

### เบราว์เซอร์ทำอะไร

1. เก็บเวกเตอร์ฟีเจอร์ของโทเคนที่สแกนและป้ายกำกับที่ **ผู้ใช้ยืนยันหลังรู้ผล** ไว้ในเครื่อง ("ขายไม่ได้" = 1, "ซื้อขายปกติหลายสัปดาห์" = 0)
2. เทรนในเครื่อง 10 รอบ เริ่มจากหัวปัจจุบัน
3. **ตัด (clip)** การเปลี่ยนแปลงให้ norm L2 ไม่เกิน `C = 1` แล้วบวกสัญญาณรบกวนเกาส์เซียน `N(0, (zC)^2)` ทุกพิกัด `z = 2`
   สุ่มจาก `crypto.getRandomValues` เท่านั้น (ตัวสุ่มแบบมี seed จะทำให้การรับประกันเป็นโมฆะ)
4. ตรวจงบความเป็นส่วนตัว (`PrivacyLedger`): หนึ่งการอัปเดตต่อรอบ และปฏิเสธเมื่อ epsilon รวมจะเกินงบ (ค่าเริ่มต้น 16)
5. เข้ารหัสเป็นไบต์ (`encodeUpdate`, fixed-point เหมือนกันทุกแพลตฟอร์ม) แล้วส่งทางใดทางหนึ่ง:
   - **บนเชน แบบ commit-reveal** (`FederatedRounds.sol`): ไม่มีใครปรับการอัปเดตของตนตามของคนอื่นในรอบเดียวกันได้
     ผู้ส่งอยู่ในค่า commitment จึงลอกไม่ได้ ลายเซ็นธุรกรรมคือลายเซ็นของการอัปเดต
   - **นอกเชน ซองที่ลงลายเซ็น** (`zetaphy-network/src/fl.js`): EIP-191 `personal_sign` แล้วส่งให้ runner หรือ commit ไว้ใน
     `zetaphy-neuro/ml/fl/inbox/round-N/` ผู้รวมผลตรวจลายเซ็นทุกฉบับ

ไคลเอนต์ทั้งหมดรันใน Chromium เป็น ES module ธรรมดาภายใต้ CSP เข้มงวด (`ml/test/fl.browser.e2e.js`)

### ความเป็นส่วนตัว: epsilon หมายถึงอะไร

Differential privacy แบบ **ในเครื่อง (local)** ระดับ **ผู้ใช้**: ใส่สัญญาณรบกวนบนอุปกรณ์ จึงไม่ต้องเชื่อใจผู้รวมผล runner หรือใครที่อ่านเชน
กลไกเกาส์เซียนให้ `rho = 2 / z^2` (zCDP) ต่อรอบที่ส่ง, บวกกันข้ามรอบ, `epsilon = rho + 2 sqrt(rho ln(1/delta))`, `delta = 1e-5`
ไม่อ้างการขยายผลจากการสุ่มตัวอย่างหรือการสับเปลี่ยน

| z | epsilon ต่อรอบ | จำนวนรอบภายใน epsilon 16 | ภายใน epsilon 8 |
|---:|---:|---:|---:|
| 1 | 11.60 | 1 | 0 |
| **2 (ค่าเริ่มต้น)** | **5.30** | **6** | 2 |
| 3 | 3.42 | 15 | 4 |
| 4 | 2.52 | 27 | 8 |

พูดตรง ๆ: epsilon 5.3 ต่อรอบเป็นการรับประกันที่อ่อนเมื่อเทียบมาตรฐาน DP แบบรวมศูนย์ ซึ่งเป็นปกติของ local DP
มันจำกัดสิ่งที่การอัปเดตหนึ่งฉบับเปิดเผยเกี่ยวกับป้ายกำกับของผู้ใช้ แต่ไม่ซ่อน *ว่า* address นั้นเข้าร่วม (ธุรกรรมและลายเซ็นเป็นสาธารณะ)
ผู้ที่ต้องการไม่ให้เชื่อมโยงได้ควรใช้ address ใหม่ทุกรอบ

### การรวมผลและการวางยา (poisoning)

1. **ตรวจรูปร่าง** ทุกการอัปเดต: แฮชของหัว, รอบ, ขนาด, clip, z; ทุกพิกัดไม่เกิน `C + 6zC` และ norm ไม่เกิน `C + zC (sqrt(d) + 6)`
   ผู้ส่งที่ส่งสองฉบับเสียทั้งสอง ผลจึงไม่ขึ้นกับลำดับที่มาถึง
2. **Trimmed mean รายพิกัด** (ตัดข้างละ 20%; มี median และค่าเฉลี่ยธรรมดาด้วย) ถ้าผู้โจมตีไม่เกิน 20% ทุกพิกัดของผลจะอยู่ระหว่างค่าต่ำสุดและสูงสุด
   ของการอัปเดต *สุจริต* (ทดสอบแล้ว) แต่เมื่อมีสัญญาณรบกวน ช่วงนี้กว้าง ขอบเขตนี้อย่างเดียวจึงอ่อน
3. **ด่านตรวจ canary** ก่อนเสนอสิ่งใด: เทียบกับต้นไม้ล้วน (theta = 0 ไม่ใช่รอบก่อน จึงค่อย ๆ ลดทีละนิดไม่ได้) การหลบเลี่ยงของ red team ที่โมเดลจับได้
   ต้องยังอยู่ระดับ medium ขึ้นไป, recall ลดได้ไม่เกิน 1 จุด, การแจ้งเตือนผิดเพิ่มได้ไม่เกิน 10 จุด
4. **Trust region** และต้องมีการอัปเดตที่ใช้ได้อย่างน้อย 20 ฉบับต่อรอบ

สิ่งที่แสดงและไม่แสดง:
- เบราว์เซอร์สุจริตแก้การเปลี่ยนแปลงได้มาก (AUC +0.06, ความแม่นยำ +0.10) ทั้งที่เปิดสัญญาณรบกวน

- ด่านยังปฏิเสธรอบสุจริตจำนวนมาก เพราะโลกที่เปลี่ยนไปทำให้คะแนนบนแถวของโลกเดิมสูงขึ้นจริง ค่าความคลาดเคลื่อนที่ยอมได้เป็นนโยบายให้ governance เลือก
- ผู้โจมตีที่เล็งเฉพาะรูปแบบที่ไม่มีใน canary ถูกจำกัดด้วย trust region ไม่ใช่ถูกหยุด
- ผู้ใช้ในการจำลองเข้าร่วมได้ถึง 9 รอบ (epsilon 18.9); เบราว์เซอร์จริงหยุดที่งบ (6 รอบที่ z = 2, epsilon 16)

### ผู้รวมผลและ governance

```bash
node zetaphy-network/scripts/fl-aggregate.js --round 3 --inbox zetaphy-neuro/ml/fl/inbox \
  [--rpc https://… --rounds 0xFederatedRounds] [--rows held-out.jsonl] --out out/fl \
  [--registry 0xModelEpochs --gov-bech32 zetaphy1… --activation 1234000 --uri https://…/manifest.json]
```

ได้ `head.json`, `manifest.json`, `decision.json`, `body.md` และ (ถ้ามี `--registry`) `proposal.json` (MsgEVMCall จากโมดูล gov ไปยัง
`ModelEpochs.schedule`) ใครก็รันซ้ำได้และได้ผลเหมือนกันทุกไบต์ งานรายสัปดาห์ `.github/workflows/neuro-fl.yml` (พฤหัสบดี 05:43 UTC)
รันกับรอบที่จบล่าสุดและเปิด pull request เมื่อผ่านด่าน แต่ PR ไม่ใช่การตัดสิน: manifest จะมีผลเมื่อการโหวตบันทึกแฮชใน ModelEpochs เท่านั้น

โมเดลต้นไม้ใหม่จากการเทรนรายสัปดาห์ (`neuro-ml.yml`) จะรีเซ็ตหัวเป็น theta = 0 และเขียน manifest ใหม่ (`node ml/fl/manifest.js`)

### ข้อจำกัดและสิ่งที่ยังเหลือ (หัวข้อ 6)

- **ยังไม่มีหน้าจอในเบราว์เซอร์**: ยังไม่มีปุ่มให้ผู้ใช้ใส่ผลลัพธ์หรือส่งการอัปเดต ไลบรารีพร้อมและรันใน Chromium แล้ว
  หน้าจอ (ปุ่มป้ายหลังสแกน, "แชร์การอัปเดตแบบส่วนตัว" พร้อมแสดง epsilon, ครบ 8 ภาษา, CSP เข้มงวด) คือขั้นถัดไป
- **ยังไม่มีป้ายจริง** จึงไม่อ้างความแม่นยำในโลกจริง ตัวเลขทั้งหมดมาจากสถานการณ์สังเคราะห์
- **ไม่มีการป้องกัน Sybil**: หนึ่ง address หนึ่งการอัปเดตต่อรอบ แต่ใครก็สร้างหลาย address ได้ ทางเลือก: บังคับลงทะเบียน NeuroIdentity, มัดจำเล็กน้อยที่คืนได้, หรือถ่วงน้ำหนักตาม stake ของ runner
- **ไม่มี secure aggregation**: การอัปเดตแต่ละฉบับเป็นสาธารณะ สัญญาณรบกวนจึงต้องอยู่ในเครื่องและใหญ่
- **ยังไม่ deploy สัญญา**: ทดสอบบน EVM ในหน่วยความจำเท่านั้น workflow ไม่ทำอะไรจนกว่าจะตั้งตัวแปรของ repository
- คุณภาพป้าย: ผู้ใช้อาจใส่ผิดหรือจงใจใส่ผิด ด่านและ trust region จำกัดความเสียหาย แต่ไม่ได้ทำให้ป้ายถูกต้อง

## หัวข้อ 35: เวอร์ชันโมเดลผูกกับความสูงบล็อก

### สัญญา (`zetaphy-network/contracts/ModelEpochs.sol`)

| คำสั่ง | ใคร | กฎ |
|---|---|---|
| `schedule(hash, activation, uri)` | governance | `hash != 0`; `activation % epochLength == 0`; `activation >= block.number + minDelay` (minDelay >= 1); มากกว่าเวอร์ชันล่าสุด; uri ยาว 1-256 |
| `cancelLast()` | governance หรือ guardian | เฉพาะเวอร์ชันล่าสุด และเฉพาะเมื่อ `activation > block.number` |
| `versionAt(h)` | ทุกคน | เวอร์ชันสุดท้ายที่ `activation <= h`; `found = false` ก่อนเวอร์ชันแรก |
| `current()` | ทุกคน | `versionAt(block.number)` |

`hash` คือ sha256 ของไบต์ไฟล์ manifest (`zetaphy-neuro/ml/manifest.json`) ซึ่งระบุ sha256 ของไฟล์โมเดลและหัว
manifest ที่ commit อยู่ (โมเดล `nml-b4c35477f7b1`, หัวศูนย์ `nfh-ec54f839dc2d`) มี sha256
`0xc8e6eb9ced9494e6773d0850d434c8dd436a5d76ba67f59ff0d29a8e8c1d9549`

**เหตุผลว่าคำตอบเป็นที่สุด**: ที่บล็อก `b`, `schedule` ต้องการ `activation > b` และ `cancelLast` ต้องการ `activation > b`
ดังนั้นไม่มีธุรกรรมในบล็อก `h` หรือหลังจากนั้นเปลี่ยนเวอร์ชันที่ `activation <= h` ได้ `versionAt(h)` บนสถานะหลังบล็อก `h-1`
จึงเท่ากับบนสถานะใด ๆ ที่หลังกว่า (ทดสอบใน `test/modelepochs.test.js`)

### การเลือกใน JS: `zetaphy-neuro/ml/fl/registry.js`

- `selectVersion(versions, height)`: binary search หา `activation <= height` ตัวสุดท้าย ทดสอบเทียบการไล่ทีละตัวและเทียบ `versionAt` ของสัญญา
- `loadForHeight(...)`: เลือก, ดึง manifest, ตรวจ sha256 กับ registry, ดึงโมเดลและหัวพร้อมตรวจแฮช ไม่ตรงเมื่อใดก็ throw:
  เบราว์เซอร์ที่ตรวจไม่ได้จะกลับไปใช้กฎล้วน ไม่ใช้โมเดลอื่น
- `zetaphy-network/src/modelepochs.js`: `readVersions`, `versionForHeight` (ตรวจไขว้กับสัญญา), `onChain(...)`, `scheduleProposal(...)`

ความสูงที่ใช้: ความสูงของบล็อกที่ **กำหนดคำถาม** สแกนสดในเบราว์เซอร์ใช้บล็อกล่าสุดที่อ่าน, งานของเครือข่ายใช้บล็อกของธุรกรรมคำขอ
ทุก runner ของงานนั้นจึงเลือกเวอร์ชันเดียวกันไม่ว่าจะรันช้าแค่ไหน, การตรวจรายงานเก่าใช้ความสูงที่บันทึกไว้กับรายงาน

### ฝั่งโหนด (ใน patch ของเชน: `zetaphy-chain/setup-node.sh` ไฟล์ `evmd/zetaphy_modelat.go`)

registry เป็นสัญญา EVM โหนดจึงเก็บแค่ที่อยู่ของมัน แล้วอ่านจากสัญญา

1. **ที่อยู่ของ registry**: ค่า 20 ไบต์ใน store `zetaphypq` (คีย์ `0x30` อยู่กับค่าตั้ง v5 อื่น ๆ) ตั้งได้ทาง governance เท่านั้น
   ผ่าน `MsgSetFuture{kind: "model-epochs", data: {"address":"0x…"}}`:
   ```bash
   bash zetaphy-chain/gov.sh model-epochs 0xModelEpochs   # - คือเอาออก (ไม่มีโมเดลในฉันทามติ)
   ```
   เชนปฏิเสธที่อยู่ที่ไม่มีสัญญา และค่านี้อยู่ใน genesis export ด้วย (`neuro.model_epochs` ในสเปกเดิมคือค่านี้
   เพราะเชนไม่มีโมดูล neuro และ v5 เก็บค่าตั้งทั้งหมดใน store `zetaphypq`) แนะนำ `governance` = address EVM ของโมดูล gov
   `0x7b5Fe22B5446f7C62Ea27B8BD71CeF94e03f3dF2`, `epochLength = 14400`, `minDelay >= epochLength`
2. **การค้นหา**: `app.ModelVersionAt(ctx, h)` คืน `ModelVersion{Found, Index, Hash, Activation, URI}` และ error
   เป็นการเรียก `versionAt(h)` แบบอ่านอย่างเดียวบน cache context ที่ไม่เขียนกลับ (gas 200,000, `from` = address ของโมดูล `neuro`)
   ไม่ตั้ง registry, ไม่มีโค้ด, revert หรือ gas หมด, คำตอบผิดรูปแบบหรือยาวเกิน 4 KiB, หรือ registry ผิดกฎของตัวเอง
   (แฮชเป็นศูนย์, activation เกิน `h`, uri ว่างหรือยาวเกิน 256 ไบต์) = `Found = false` พร้อมเหตุผลใน error
   เมื่อเรียกขณะประมวลผลบล็อก `h` สถานะคือหลังบล็อก `h-1` ซึ่งเป็นคำตอบที่เป็นที่สุด
3. **ความแน่นอน**: โค้ดฉันทามติเทียบ **แฮชเท่านั้น** ไม่ดาวน์โหลดไฟล์ในเส้นทางฉันทามติ validator ที่ยังไม่มีไฟล์ที่ตรวจแล้ว **งดออกเสียง**
   VerifyVoteExtension ต้องปฏิเสธ extension ที่แฮชโมเดลไม่ตรง `ModelVersionAt(h).Hash` กฎนี้ผูกกับสิ่งแรกที่นำผลโมเดลเข้าฉันทามติ
   ซึ่งตอนนี้ยังไม่มี
4. **Query**: อ่านสถานะหลัง `height - 1` (โหนด archive สำหรับความสูงเก่า) และคืน
   `{height, stateHeight, registry, found, index, hash, activation, uri, error}`:
   - `zetaphyd q neuro model-at <height>` (`gov.sh model-at <height>`)
   - JSON-RPC `zetaphy_modelAt(height)` บน endpoint EVM สาธารณะ (8545) เช่นเดียวกับ `zetaphy_faucet`
   - `modelEpochs()` บน AI precompile `0x…0902` คืนที่อยู่ registry ให้สัญญาเรียก `versionAt` เองได้

   query อ่านที่อยู่ registry จาก store แล้วเรียก `versionAt` ผ่าน `EthCall` ของโมดูล EVM ที่ความสูงนั้น
   การทดสอบตรวจว่าทางนี้ตรงกับ keeper ทุกความสูง เบราว์เซอร์และ runner ยังใช้ `eth_call` ที่ `blockTag = height - 1` ได้คำตอบเดียวกัน
   ไม่ได้เพิ่มบริการ `zetaphy.neuro.v1.Query/ModelAt` แยก เพราะ query อื่นของ ZETAPHY เป็น JSON-RPC และ CLI และ `EthCall` มีอยู่แล้ว
5. **ดึงไฟล์นอกฉันทามติ**: ไม่มี daemon runner หรือเบราว์เซอร์เรียก `zetaphy_modelAt` (หรือ `eth_call`)
   แล้ว `loadForHeight` ดึง manifest และไฟล์พร้อมตรวจ sha256 ทุกไฟล์ ล่วงหน้าอย่างน้อยหนึ่ง epoch
6. **การทดสอบ** (`TestFutureModelAt` บน bytecode จริงของ `ModelEpochs`): ไม่ตั้ง registry, ปฏิเสธที่อยู่ที่ไม่ใช่สัญญา/ผู้ส่งที่ไม่ใช่ gov/ฟิลด์ JSON ที่ไม่รู้จัก,
   registry ว่าง, เวอร์ชันที่ 20 และ 30 (ไม่พบที่ 11 และ 19, ตัวแรกที่ 20 และ 29, ตัวที่สองที่ 30 ขึ้นไป) โดยทาง query ตรงกับ keeper,
   ความแน่นอน (เรียกซ้ำ 20 ครั้งได้ผลเดิม ไม่เปลี่ยนบัญชี/nonce/event, แอปที่สอง replay ได้ผลเดียวกัน),
   ความเป็นที่สุด (ที่ความสูง 21 `cancelLast` ลบได้แค่เวอร์ชันที่ 30 คำตอบสำหรับความสูง <= 21 ไม่เปลี่ยน),
   registry ที่วนไม่จบ/ตอบขยะ/ผิดกฎ = ไม่พบ, การเอาออก, genesis export และคำสั่ง proposal

**สิ่งที่ยังเหลือ (ข้อ 35 ฝั่งโหนด)**
- ยังไม่มีส่วนใดของฉันทามติใช้โมเดล (`combine.js` กันไว้โดยตั้งใจ) กฎงดออกเสียง / VerifyVoteExtension ในข้อ 3 จึงยังไม่มีผู้เรียก
- ยังไม่ได้ทดสอบบน devnet หลาย validator ตามสเปก (3 validator, replay จาก genesis, vote extension ที่แฮชผิด)
  `zetaphy_modelAt` และ `q neuro model-at` ทดลองด้วยมือครั้งเดียวบน devnet โหนดเดียว (`scripts/devnet.sh`) กับ registry
  จำลองใน genesis (ตอบจากสถานะหลัง `height - 1` และปฏิเสธความสูง 1) ยังไม่ได้ลองกับ `ModelEpochs` จริงบนเชนจริง และยังไม่มีการทดสอบ devnet ใน CI
- ไม่มี sidecar ที่ดึงไฟล์ล่วงหน้า `loadForHeight` ดึงเมื่อใช้
- เชน v5 ที่รันอยู่: คีย์ใหม่, view และ query มากับไบนารีใหม่ registry จะยังไม่ถูกตั้ง (ไม่มีอะไรเปลี่ยน) จนกว่าจะโหวต
