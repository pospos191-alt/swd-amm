## 1. Export เป็นจำนวนเต็ม (`zetaphy-neuro/ml/onchain/`)

`node ml/onchain/export.js` แปลงโมเดลบนเชน `ml/onchain/model.json` (ปักแยกจาก `ml/model.json` ดูด้านบน) เป็นจำนวนเต็มแล้วอัดแน่น
(รูปแบบอธิบายใน `fixed.js`):

- สเกลเดียว S = 1e7 ฟีเจอร์ `X = round(x*S)` เป็น u32 (ฟีเจอร์ของ Neuro ไม่ติดลบ สูงสุด 429.49 ก่อนถูกตัด), threshold `T = round(t*S)`
  (ไปทางซ้ายเมื่อ `X <= T`), ใบ/ค่าฐาน `round(v*S)` เป็น int32
- margin `Z = ค่าฐาน + ผลรวมใบที่ไปถึง`; คะแนน `s = trunc(calibA * Z / S) + calibB` = **logit ที่ปรับเทียบแบบ Platt x 1e7**
  ดังนั้น `p = sigmoid(s / 1e7)` ระดับ low / medium / high เป็น threshold บน `s` (0 / 13,862,944 / 29,444,390)
- รูปแบบ "NSM1": header 24 ไบต์, จำนวนโหนดต่อต้น 1 ไบต์, แล้วโหนดละ 6 ไบต์แบบ pre-order (ลูกซ้าย = โหนดถัดไป) โมเดลปัจจุบัน
  3,072 โหนด **18,616 ไบต์** (JSON แบบทศนิยม 87 KB) keccak256 ของมันคือแฮชโมเดล **H** (`0x7c420111…a4132` ใน `model.fixed.json`)
- `ml/onchain/heldout.json` = ชุด held-out ของตัวฝึกเอง (390 แถว, scam 201, ไม่เคยใช้ฝึก) ตัดจาก corpus ที่สร้างใหม่
  (`npm run ml:corpus`; AUC ของโมเดลปัจจุบันบนชุดนี้ตรงกับ `metrics.json`: 0.9975)

### ความตรงกัน (ค่าคลาดเคลื่อนที่ยอมรับ)

บน held-out ทั้ง 390 แถว:

| เปรียบเทียบ | ผล | ค่าที่ test ยืนยัน |
|---|---|---|
| Solidity `NeuroScore.evaluate` กับ JS จำนวนเต็ม (`evalFixed`) | คะแนนและระดับ **เท่ากันทุกแถว** | ตรงทุกบิต |
| JS ทศนิยมกับ JS จำนวนเต็ม | \|p ต่าง\| สูงสุด 1.3e-7, \|logit ต่าง\| สูงสุด 8.6e-7 | \|dp\| <= 1e-6, \|dlogit\| <= 2e-5 |
| การตัดสิน (ระดับที่ถึง) | **เหมือนกันทั้ง 390 แถว** | ถ้าต่าง ต้องอยู่ห่าง threshold ของระดับไม่เกิน 1e-6 |

การปัดเศษเป็นฟังก์ชันเพิ่มทางเดียว แถวหนึ่งจะไปกิ่งต่างจากโมเดลทศนิยมได้ก็ต่อเมื่อฟีเจอร์ห่าง threshold ไม่เกิน 1/S = 1e-7
รุ่นแรกที่ใช้ S = 1e6 เจอกรณีนี้หนึ่งแถว (`g3_20` = 0.0779459 กับ threshold 0.0779458, logit คลาด 0.09, ระดับไม่เปลี่ยน) จึงเปลี่ยนเป็น 1e7

## 2. `NeuroScore` (`zetaphy-network/contracts/NeuroScore.sol`)

- **publishModel(bytes)** (ใครก็ได้): ตรวจรูปแบบ NSM1 แล้วเก็บเป็นโค้ดของสัญญาข้อมูล (ก้อนละ 24,575 ไบต์ โมเดลใหญ่กว่านั้นใช้หลายก้อน
  ทดสอบกับ 2 ก้อนแล้ว) การ publish ไม่เปิดใช้อะไร
- **activateModel(H, modelId, low, medium, high)**: governance เท่านั้น = `ZetaphyTimelock` (multisig เรียกตรงถูกปฏิเสธ)
  สัญญานี้คือทะเบียนโมเดล: ทุกการเปิดใช้เป็น `version` ที่มีเลขลำดับพร้อมแฮช, id, ระดับ และเวลา ใน repo ไม่มีทะเบียนโมเดลแยก
- **setFeeder(addr, bool)**: governance เท่านั้น feeder (ตัวส่งผลของ Neuro runner) ส่งเวกเตอร์ฟีเจอร์ของเหรียญด้วย
  **postFeatures(token, bytes)** สัญญารันโมเดลแล้วเก็บคะแนน ระดับ version และแฮชของเวกเตอร์ (ตัวเวกเตอร์อยู่ใน event `Scored`)
- **rescore(token, bytes)** (ใครก็ได้ ถ้ามี preimage) รันใหม่ภายใต้โมเดลปัจจุบัน **scoreOf(token)** ให้ `known = false` ถ้ายังไม่มีคะแนน
  หรือมีแต่จากโมเดลเก่า

แก๊ส (EVM ในหน่วยความจำ กฎ Cancun วัดโดย test): `evaluate` เฉลี่ย 126k สูงสุด 130k (เฉพาะการรัน), `postFeatures` ~205k ทั้งธุรกรรม,
`publishModel` ~6.05M (ครั้งเดียว), การตรวจใน router เมื่อเปิด ~+2.5k ต่อเหรียญที่ซื้อ

สิ่งที่ **ไม่ได้** พิสูจน์: ว่าฟีเจอร์ที่ส่งมาคือสิ่งที่ Neuro จะคำนวณได้จริงสำหรับเหรียญนั้น เชนพิสูจน์แค่ "คะแนนที่เก็บ = โมเดลปัจจุบัน(เวกเตอร์ที่ส่งมา)"
ต้องเชื่อ feeder เรื่องเวกเตอร์ (การดึงฟีเจอร์ต้องวิเคราะห์ bytecode และจำลองซื้อขาย แพงเกินจะรันใน EVM) ทางปิดช่องนี้คือให้ runner
2 ใน 3 เห็นตรงกันเรื่องเวกเตอร์ หรือพิสูจน์การดึงฟีเจอร์เอง (ยังไม่ได้ทำ)

## 3. การตรวจใน router ของ DEX (`zetaphy-dex`)

- `ZetaphyFactory.setNeuroScore(scorer, threshold)`: **governance เท่านั้น ค่าเริ่มต้นปิด** ที่อยู่ต้องตอบ `scoreOf` ได้ภายใน
  `SCORE_GAS` = 50,000 ตอนตั้งค่า `node cli.js set-neuro-score <NeuroScore> --min-p 0.8` แปลงความน่าจะเป็นเป็นหน่วยคะแนน
- router ปฏิเสธการซื้อ (ทุกแบบของ swap รวม multi-hop) ด้วย `TokenScoreTooHigh(token, score)` เมื่อเหรียญมีคะแนน **ปัจจุบัน** `>= threshold`
  เหรียญที่ไม่มีคะแนนหรือมีแค่จากโมเดลเก่าผ่านได้ การขายและสภาพคล่องไม่ถาม scorer ถ้า scorer ไม่ตอบหรือใช้แก๊สเกิน จะ **fail closed**
  (`ScoreUnavailable`) เฉพาะการซื้อ จนกว่า governance ตั้งเป็นศูนย์ ข้อความ error บนเว็บมีครบ 8 ภาษา
- ยังไม่ทำ: router ของ DLMM ยังมีแค่การตรวจ ThreatRegistry

## 4. การอัปเดตโมเดล

1. งาน `neuro-ml.yml` รายสัปดาห์ฝึกโมเดลผู้สมัครสำหรับ `ml/model.json` (เบราว์เซอร์และ runner) เท่านั้น **ไม่แตะ** `ml/onchain/`
   เพราะโมเดลบนเชนแต่ละตัวต้องมีวงจรและพิธีสาธารณะของตัวเอง (PR ที่แก้บันทึกพิธีห้ามแก้ไฟล์อื่น) จะย้ายเชนไปโมเดลใหม่: จัดพิธีใหม่
   สำหรับวงจรใหม่ก่อน แล้วรัน `node ml/onchain/export.js --promote --heldout` (คัดลอก `ml/model.json` ไปเป็น `ml/onchain/model.json`
   แล้ว export ใหม่) พร้อม verifier จากพิธีนั้น `ml/test/onchain.test.js` ไม่ยอมรับ export ที่แฮชไม่ตรงกับบันทึกพิธี
2. หลังคน merge: ใครก็ได้เรียก `NeuroScore.publishModel(bytes)`
3. governance ตั้งเวลาเปิดใช้ผ่าน timelock (`export.js` พิมพ์คำสั่ง `zetaphy timelock schedule ... activateModel ...` ให้) แล้ว execute หลังครบเวลา
   ทุกคนเห็น H ระหว่างรอและเทียบกับ PR ได้
4. คะแนนเก่าจะเป็น unknown จนกว่าจะ `rescore` หรือส่งใหม่

## 5. zkML (`zetaphy-neuro/ml/onchain/zk/`)

เครื่องมือ (ฟรี ผ่าน npm ไม่มีไบนารี native): **circom 2** ผ่าน `circom2` 0.2.23 (คอมไพเลอร์ทางการที่คอมไพล์เป็น WASM),
**snarkjs 0.7.6** (Groth16 บน BN254 ปักเวอร์ชันตายตัวใน `package.json` + lock), **circomlib 2.0.5**

วงจร (`gen-circuit.js` สร้างจากไบต์ที่อัดแน่น จึงเป็นโมเดล H พอดี): ข้อมูลลับคือฟีเจอร์ u32 133 ค่าและ `salt`; ค่าสาธารณะคือ `commitment`
(Poseidon), `margin` = Z + 2^40 และ H เป็นสองครึ่ง 128 บิต ใช้ 373 การเปรียบเทียบที่ไม่ซ้ำ และ 1,296 การคูณสำหรับเส้นทาง รวม
**21,689 constraints** ใส่ในไฟล์ phase 1 ขนาด power 15 (32,768) ได้

### Trusted setup: phase 1 สาธารณะ + phase 2 หลายฝ่าย

Groth16 ต้องมี setup ที่ค่าสุ่มลับ ("toxic waste") ต้องถูกทำลาย ใครรู้ค่านั้นจะทำ proof ปลอมให้ผ่านได้ setup มีสองช่วง และตอนนี้ทั้งสองช่วงเป็นแบบหลายฝ่าย:

- **Phase 1 (powers of tau ใช้ได้กับทุกวงจร)**: ไม่ได้ทำเอง `ceremony/phase1.json` ปักไฟล์ของ **Perpetual Powers of Tau** (BN254 ผู้ร่วมอิสระกว่า
  80 ราย ปี 2019-2023 ประสานโดยทีม PSE ของ Ethereum Foundation) contribution 0080 ที่ใส่ beacon ของ PSE แล้ว เตรียมสำหรับ phase 2 และตัดเหลือ
  power 15 โดย PSE: `ppot_0080_15.ptau` ขนาด 37,842,066 ไบต์ ตามที่ระบุใน README ของเขา PSE ไม่ได้เผยแพร่แฮชของไฟล์ที่ตัดแล้วแยกไฟล์
  จึงปักด้วย sha256 **และ** blake2b-512 ของไบต์ที่ดาวน์โหลดเมื่อ 2026-10-29 (`lib.js getPtau()` ลบและปฏิเสธไบต์อื่น) ใครก็ตรวจซ้ำได้ว่าไฟล์มี
  contribution สาธารณะและ beacon ครบด้วย `snarkjs powersoftau verify` (workflow `neuro-zk-ceremony` รันให้เมื่อสั่ง ด้วย input `verify_phase1`;
  ที่นี่รันเกิน 45 นาทีบนหนึ่งคอร์แล้วยังไม่จบ จึงยังไม่ได้ตรวจครบใน sandbox นี้) ไฟล์ Hermez ที่ README ของ snarkjs พิมพ์ blake2b ไว้ ตอบ HTTP 403
  จาก bucket จึงใส่ไว้เป็นทางเลือกเท่านั้น
- **Phase 2 (เฉพาะวงจรนี้)**: พิธีใน `ceremony/` ไม่มีเซิร์ฟเวอร์ของเรา:
  - `ceremony.js init` สร้างกุญแจตั้งต้นด้วย `groth16 setup` จากวงจรและ phase 1 ที่ปักไว้ ขั้นนี้ให้ผลเหมือนเดิมทุกครั้ง ตัวตรวจสร้างซ้ำได้ตรงทุกบิต
    (sha256 `4351818234f5…` 11,338,460 ไบต์) และผู้ร่วมคนแรกก็สร้างเองได้
  - **ผู้ร่วม** แต่ละคนเติมค่าสุ่มแล้วลืมมัน: ผ่าน command line (`ceremony.js contribute --name … --github …` ค่าสุ่ม = 64 ไบต์จาก CSPRNG ของ OS
    + ข้อความที่พิมพ์ ผสมด้วย `ceremony-core.js mixEntropy` ไม่ถูกเขียนลงที่ใด ส่งให้ snarkjs ในหน่วยความจำ ไม่ใช่บน command line) หรือใน
    **หน้าเบราว์เซอร์ `ceremony.html` ใน hub** (ค่าสุ่มจาก `crypto.getRandomValues` + ข้อความที่พิมพ์ + จังหวะกดแป้นและการเลื่อนเมาส์; ผู้ใช้เปิดบันทึกและ
    กุญแจล่าสุดเป็นไฟล์ แล้วดาวน์โหลดกุญแจใหม่ + บันทึกที่อัปเดต) CSP ของหน้านี้มี `connect-src 'none'` จึงส่งอะไรออกไปไม่ได้เลย และเป็นหน้าเดียวใน hub
    ที่อนุญาต `'wasm-unsafe-eval'` และ blob worker (snarkjs ต้องใช้ทั้งสองอย่าง) ผ่านกฎแยกใน `vercel.json` snarkjs ที่ vendor มาจากแพ็กเกจ npm
    ตัวเดียวกับที่ปักไว้ (`vendor/snarkjs.json` เก็บเวอร์ชัน integrity ของ tarball และ sha256; มี test เทียบ)
  - **บันทึก** `ceremony/transcript.json` (รูปแบบ `zetaphy-zk-ceremony/1`, `zetaphy-hub/ceremony-core.js` ใช้ร่วมกันระหว่างหน้าเว็บและ CLI): แฮชวงจร
    แฮชโมเดล sha256 ของ r1cs, phase 1 ที่ปักไว้, เวอร์ชัน snarkjs, กุญแจตั้งต้น แล้วหนึ่งรายการต่อหนึ่งขั้น: ชื่อ, ชื่อ GitHub, contribution hash ของ snarkjs
    (blake2b), sha256 และขนาดของกุญแจใหม่, URL ใน release และ `link_k = sha256(tag, link_{k-1}, k, type, name, github, contributionHash, zkeySha256[, beacon])`
    เริ่มจาก `link_0 = sha256(tag, แฮชวงจร, sha256 ของ phase 1, sha256 ของกุญแจตั้งต้น)` ทุกรายการผูกกับประวัติทั้งหมดก่อนหน้า จึงตัด สลับ เปลี่ยนชื่อ
    หรือแทนที่ขั้นใดไม่ได้
  - **ตัวตรวจ** (`ceremony.js verify`): สายโซ่แฮช; sha256 ของกุญแจ; สร้างกุญแจตั้งต้นซ้ำ; แล้ว `snarkjs zkey verify` เทียบกับวงจร (สร้างใหม่จาก
    โมเดลที่ commit) และ phase 1 ที่ปักไว้ ซึ่งตรวจ proof of knowledge ของทุก contribution คำนวณ beacon ซ้ำ และตรวจส่วนต่าง ๆ ของกุญแจ; สุดท้ายรายการ
    contribution ที่อยู่ในตัวกุญแจ (แฮช ชื่อ beacon) ต้องตรงกับบันทึกทีละรายการ
  - **Random beacon**: เมื่อมีผู้ร่วมพอ (`minContributions` = 3 ในบันทึกที่ commit) เจ้าของระบุบล็อกในอนาคตผ่าน PR (`declare-beacon --chain ethereum --block N`;
    ระบบปฏิเสธบล็อกที่ห่างไม่ถึง 300 บล็อก (~1 ชั่วโมง) หรือการประกาศที่ไม่ได้มาจากเจ้าของ) หลังบล็อก N ถูกขุด ใครก็รัน `finalize` ได้: แฮชของบล็อก
    วนซ้ำ 2^10 ครั้งถูกใส่เป็นขั้นสุดท้าย (`snarkjs zkey beacon`) การตรวจจะถาม RPC สาธารณะหาบล็อก N (ทุกตัวที่ตอบต้องตรงกัน) และปฏิเสธถ้าเวลาของบล็อก
    ไม่อยู่หลัง commit ที่ merge การประกาศ จะใช้บล็อกของ ZETAPHY ก็ได้ แต่ validator ของ ZETAPHY ดำเนินการโดยโปรเจกต์เอง บล็อกของ Ethereum
    จึงเป็นตัวเลือกที่ซื่อตรงกว่า
  - **การประสานงาน = GitHub**: แต่ละ contribution คือ PR ที่แก้แค่ `transcript.json` (เพิ่มหนึ่งรายการ) กุญแจเป็นไฟล์แนบ release ใน fork ของผู้ร่วม
    `.github/workflows/neuro-zk-ceremony.yml` (Actions ฟรี ไม่มี secret) ใช้เครื่องมือจาก branch ปลายทาง (ไม่เคยรันโค้ดของ PR) ดาวน์โหลดกุญแจจาก URL
    ในรายการ (จำกัดขนาด) และปฏิเสธ PR เว้นแต่รายการระบุผู้เปิด PR ไม่มีอะไรอื่นเปลี่ยน และการตรวจเต็มรูปแบบผ่าน หลัง merge จะตรวจทุกอย่างอีกครั้ง
    และคัดลอกกุญแจไปไว้ที่ release `zk-ceremony` ของ repository นี้
  - **ต้องการผู้ร่วมที่ซื่อสัตย์เพียงคนเดียว** ถ้าผู้เข้าร่วมคนใดคนหนึ่งทำลายค่าสุ่มของตัวเองจริง ๆ จะไม่มีใครปลอม proof ได้ แม้ผู้ร่วมคนอื่นทุกคนกับผู้ประสานงาน
    จะร่วมมือกัน ใครที่ไม่ไว้ใจคนอื่นก็แค่ร่วมเองหนึ่งครั้ง beacon มีไว้แค่กันไม่ให้ผู้ร่วมคนสุดท้ายเลือกกุญแจสุดท้ายได้
- **Export**: `ceremony.js export` ปฏิเสธกุญแจที่ยังไม่ final (ยังไม่มี beacon) และเขียน `NeuroScoreVerifier.sol` จากกุญแจสุดท้าย (`--check`
  เทียบกับไฟล์ที่ commit; CI ทำเมื่อพิธีจบแล้ว)

ตอนนี้สัญญา verifier ผูกกับโมเดล: `MODEL_HASH` (= H), `ZKEY_SHA256` และ `CEREMONY_LINK` (กุญแจมาจากไหน) และ `verifyModelProof(a, b, c, commitment, margin)`
ที่ใส่สองครึ่งของ H เอง ผู้เรียกจึงส่งค่าคงที่แฮชอื่นเข้ามาไม่ได้ `verifyProof` (จุดเรียกของ snarkjs) ยังอยู่

### ข้อจำกัด พูดตรง ๆ

- **พิธีสาธารณะยังไม่ได้จัด** บันทึกถูกตั้งต้นแล้ว (0 contribution) ยังไม่มีใครร่วม `NeuroScoreVerifier.sol` ที่ commit มาจาก**การซ้อมบนเครื่องเดียว**
  (ส่วนหัวของไฟล์บอกไว้ และ test บนเชนตรวจป้ายนี้) จึงยังใช้ได้แค่ testnet: คนที่รันการซ้อมปลอม proof ได้ จะใช้งานจริงได้หลังขั้น 6 ของหัวข้อ 6 เท่านั้น
  และต่อเมื่อมีผู้ร่วมที่ซื่อสัตย์อย่างน้อยหนึ่งคน
- การปัก phase 1 เป็นแฮชของไฟล์ที่ PSE ให้บริการวันนี้ ไม่ใช่แฮชที่ PSE เผยแพร่เอง และยังไม่ได้รัน `powersoftau verify` จนจบที่นี่ (มีงานใน workflow ให้สั่งรัน)
- **ขนาดวงจรเทียบกับขนาดโมเดล**: ประมาณ 34 constraints ต่อคู่ (ฟีเจอร์, threshold) ที่ไม่ซ้ำ, หนึ่งต่อโหนดภายใน, บวกค่าคงที่ ~5k (ตรวจช่วง 32 บิตของ 133
  ฟีเจอร์, Poseidon) โมเดลนี้ (160 ต้น ลึก <= 4, 3,072 โหนด) = 21.7k constraints; phase 1 power 15 รับได้ 32,768 จึงเพิ่มต้นไม้หรือการเปรียบเทียบได้ราว 50%
  ก่อนต้องใช้ไฟล์ใหญ่ขึ้น (power 16 = 72 MB, power 17 = 144 MB เวลาสร้าง proof และขนาดกุญแจราวสองเท่าต่อขั้น) และจัดพิธีใหม่ ต้นไม้ลึกขึ้นทำให้การคูณ
  ตามเส้นทางโตตามจำนวนโหนด neural network หรือต้นไม้นับพันต้องใช้ power 20+ และหลายนาทีต่อ proof ยังไม่ได้ลอง
- โมเดลใหม่ = วงจรใหม่ จึงต้องจัดพิธี phase 2 ใหม่และ verifier ใหม่ (phase 1 ใช้ซ้ำได้) การทำให้โมเดลเป็นข้อมูลลับพร้อม commitment จะเลี่ยงได้แต่วงจรใหญ่ขึ้นมาก ยังไม่ได้ทำ
- **ช่องโหว่ความเชื่อใจเดียวกับ NeuroScore**: proof บอกว่าใช้โมเดลถูกกับเวกเตอร์ที่ commit ไว้ ไม่ได้บอกว่าเวกเตอร์คือฟีเจอร์จริงของเหรียญ
- ยังไม่ได้เชื่อมกับ `NeuroScore` หรือ router: `verifyModelProof` คือจุดที่สัญญาให้คะแนนจะเรียก
- ยังไม่ได้วัดการ**สร้าง proof** ในเบราว์เซอร์ (วัดแค่การร่วมสุ่มในเบราว์เซอร์)

## 6. จัดพิธีกับผู้ร่วม N คน (ขั้นตอนสำหรับเจ้าของ)

1. `cd zetaphy-neuro/ml/onchain/zk && npm ci && node ceremony/ceremony.js status` (บันทึกตั้งต้นและ commit แล้ว) สั่งรัน workflow `Neuro zkML ceremony`
   ด้วยมือหนึ่งครั้ง: มันตรวจกุญแจตั้งต้นและนำ `neuro_score_0000.zkey` ขึ้น release `zk-ceremony`
2. ประกาศพิธีพร้อมหน้า hub (`/ceremony.html`) และคำสั่ง CLI กำหนดลำดับ (ทีละ PR: แต่ละ contribution ต่อจากกุญแจก่อนหน้า PR ที่สองบนฐานเดียวกันจะถูกปฏิเสธ
   และผู้เปิดต้องทำใหม่บนฐานล่าสุด)
3. ผู้ร่วมแต่ละคน: ดาวน์โหลดกุญแจล่าสุดจาก release `zk-ceremony` (หรือ URL ของรายการสุดท้าย) ร่วมสุ่ม (หน้าเว็บหรือ CLI) อัปโหลดกุญแจใหม่เป็นไฟล์แนบ release
   ใน fork ของตัวเอง แล้วเปิด PR พร้อมบันทึกใหม่ การตรวจต้องผ่านก่อน merge และ merge ตามลำดับ
4. เมื่อ merge ครบอย่างน้อย `minContributions` (ตั้งเป็น N ก่อนเริ่มถ้าต้องการมากกว่า) ให้ระบุบล็อก Ethereum ล่วงหน้าหลายชั่วโมงผ่าน PR (`declare-beacon`)
   และ merge ก่อนถึงบล็อกนั้น
5. หลังบล็อกนั้น: `node ceremony/ceremony.js finalize` (ดึงแฮชเอง) อัปโหลดกุญแจสุดท้ายขึ้น release `zk-ceremony` แล้วเปิด PR การตรวจจะตรวจ beacon และทั้งสายโซ่
6. `node ceremony/ceremony.js export --install`, `cd ../../../../zetaphy-network && npm run build && npm test` และ `node run.js --final --install`
   เพื่อได้ fixture ที่ทำด้วยกุญแจสุดท้าย แล้ว commit จากนั้น workflow `Neuro zkML` จะสร้าง proof ด้วยกุญแจสุดท้ายและตรวจว่า verifier ที่ commit
   คือไฟล์ที่ export จากกุญแจนั้นทุกไบต์
7. โมเดลใหม่ (H ใหม่) คือวงจรใหม่: จัด phase 2 ใหม่ (ใช้ phase 1 เดิม) ด้วย `init --force` บนบันทึกใหม่
