# ไฟร์วอลล์ invariant และกติกาใบรับรอง

ใช้บนเทสต์เน็ตเท่านั้น ไม่มีเงินจริงเข้าหรือออก และส่วนนี้ยังไม่ผ่านการตรวจสอบจากบริษัทภายนอก

หน้านี้อธิบายสองส่วนของชั้น SS ใน[เครือข่ายตรวจสอบแบบเปิด](audit-network.th.md)

- **SS1 ไฟร์วอลล์ invariant**: invariant ของสัญญาที่ได้รับการปกป้องทำหน้าที่เป็นเงื่อนไขหลังการทำงาน
  (post-condition) ระบบจะตรวจหลังทุกธุรกรรมที่ผ่านสัญญานั้น ธุรกรรมไหนทำให้ invariant ข้อใดเสีย
  ทั้งธุรกรรมจะถูกย้อนกลับ ผู้โจมตีที่เจอบั๊กจึงเอาผลจากบั๊กนั้นออกไปไม่ได้
- **SS2 ใบรับรองเป็นกติกาของเชน**: สัญญาที่ถือมูลค่าเกินเกณฑ์ต้องมีใบรับรองที่ยังใช้ได้จาก
  `AuditCertificate` ถ้าไม่มี (ไม่เคยได้ หมดอายุ ถูกเพิกถอน หรือโค้ดเปลี่ยนไป) เงินที่ไหลออกต่อวันจะถูกจำกัด

ทั้งสองส่วนเป็นแบบสมัครใจ โปรโตคอลเข้าร่วมด้วยการลงทะเบียนตัวเอง governance คือ `ZetaphyTimelock`
ซึ่งตั้งได้แค่พารามิเตอร์ที่มีขอบเขต และไม่มีคีย์แอดมินใหม่

| ส่วน | ที่อยู่ | สถานะ |
|---|---|---|
| ทะเบียน การตรวจ รายชื่อชั้นเชน กติกาใบรับรอง ชุด invariant ที่รับรองแล้ว | `zetaphy-network/contracts/InvariantFirewall.sol` | ใช้งานจริง มีเทสต์ |
| สิ่งที่โปรโตคอลต้องเพิ่ม: modifier `firewalled`, `_firewallOutflow`, `_firewallRegister` | `zetaphy-network/contracts/Firewalled.sol` | ใช้งานจริง มีเทสต์ |
| เทสต์ 12 ข้อ: หยุดการโจมตีได้, การตรวจแบบปิดเมื่อพลาด (fail-closed), ขอบเขตและการรอ, ทะเบียนชั้นเชน, กติกาใบรับรอง, การรับรองชุด invariant, `AuditCertificate` ตัวจริง, ทำงานคู่กับ `CircuitBreaker` | `zetaphy-network/test/firewall.test.js` และสัญญาทดสอบใน `test/helpers/FirewallKit.sol` | ใช้งานจริง |
| ตรวจระดับโหนดหลังทุกธุรกรรม EVM (อยู่ในโหนดที่แพตช์แล้ว ปิดไว้เป็นค่าเริ่มต้น) | แพตช์ใน `zetaphy-chain/setup-node.sh` (`evmd/zetaphy_firewall.go`, `zetaphy_firewall_core.go`) fork test ใน `zetaphy-chain/fork-tests/evmd/zetaphy_firewall*_test.go` | ใช้งานจริง คอมไพล์และผ่าน fork test แล้ว เปิดด้วยการอัปเกรดและการโหวต ([CHAIN-FIREWALL.th.md](../CHAIN-FIREWALL.th.md)) |

## SS1: invariant เป็นเงื่อนไขหลังการทำงาน (ชั้นสัญญา)

```
โปรโตคอล (สัญญาของตัวเอง) ── InvariantFirewall.register(protocolGovernance)
governance ของโปรโตคอล ───── addInvariant(protocol, checker, gasLimit, name)   มีผลทันที และต้องเป็นจริงตอนเพิ่ม
                               proposeRemoval / proposeOptOut                      รอ POLICY_DELAY (2 วัน)

ผู้ใช้ ── protocol.withdraw(…)  [firewalled]
           │  ตัวฟังก์ชันทำงาน (จ่ายเงิน ลงบัญชี เรียกออกไปข้างนอก หรืออาจถูกเรียกซ้อนกลับเข้ามา)
           ▼  การเรียกชั้นนอกสุดที่มี firewalled จบลง
         InvariantFirewall.enforce(protocol)  ── ทุก invariant: checker.holds(protocol) แบบ STATICCALL ภายในเพดานแก๊ส
           │  เป็นจริงทุกข้อ → ธุรกรรมทำงานต่อ
           ▼  มีข้อที่ไม่จริง → revert InvariantViolated(protocol, checker, name) และทั้งธุรกรรมถูกย้อนกลับ
```

**ตัวตรวจ invariant** คือสัญญาใดก็ได้ที่มีฟังก์ชัน `holds(address protocol) view returns (bool)` ตัวอย่างเช่น
"เงินในห้องนิรภัยต้องไม่น้อยกว่ายอดที่ติดค้างผู้ฝาก": `protocol.balance >= IVault(protocol).totalDeposits()`

**อะไรนับเป็นการละเมิด (ปิดเมื่อพลาด)** กรณีต่อไปนี้ทำให้ธุรกรรมถูกย้อนกลับ
- ตัวตรวจตอบ `false`
- ตัวตรวจ revert
- ตัวตรวจใช้แก๊สเกินเพดานของตัวเอง
- ตัวตรวจตอบสิ่งที่ไม่ใช่ 32 ไบต์ที่แทนค่า `true` พอดี เช่น ตอบ 64 ไบต์ ตอบ `2` หรือไม่ตอบอะไรเลย

ก่อนตรวจแต่ละข้อ ไฟร์วอลล์ดูก่อนว่ามีแก๊สพอจะให้ตัวตรวจได้ครบเพดานหรือไม่ (ตามกฎ 63/64 บวกส่วนเผื่อ)
ถ้าไม่พอจะ revert ด้วย `InsufficientGas` การส่งแก๊สให้น้อยจึงไม่มีทางทำให้การตรวจผ่านไปเฉย ๆ
เทสต์ลองเรียกบั๊กด้วยแก๊สทุกค่าตั้งแต่ 30k ถึง 400k ทีละ 10k และไม่มีค่าไหนเอาเงินออกไปได้เลย

**การเรียกซ้อน (re-entrant) ถูกตรวจครั้งเดียว** `Firewalled` นับความลึกของการเรียกที่มี firewalled ไว้ใน
transient storage (EIP-1153) และตรวจเฉพาะตอนที่การเรียกชั้นนอกสุดจบ เพราะ invariant เป็นคุณสมบัติของสถานะ
*ระหว่าง*การเรียก ไม่ใช่กลางการเรียก กรณีทดสอบมีสองแบบ
- สมาร์ตวอลเล็ตที่ฝากเงินซ้ำจาก `receive()` ระหว่างที่กำลังรับเงิน: ผ่าน
- การดูดเงินแบบ re-entrancy: ไม่ผ่าน เพราะสถานะตอนจบไม่พอจ่ายหนี้

**ขอบเขต** (เป็นค่าคงที่ governance ขยายไม่ได้)

| กติกา | ค่า |
|---|---|
| จำนวน invariant ต่อโปรโตคอล | ไม่เกิน 8 |
| เพดานแก๊สต่อการตรวจ | 5,000 .. 500,000 |
| การเพิ่ม invariant | มีผลทันที (เข้มขึ้น) ทำได้เฉพาะ governance ของโปรโตคอล และต้องเป็นจริงตอนเพิ่ม |
| การถอด invariant หรือการถอนตัว | หลัง `POLICY_DELAY` = 2 วัน ประกาศให้ทุกคนเห็น และยกเลิกได้ |
| ใครเพิ่มหรือถอด invariant ของโปรโตคอลได้ | governance ของโปรโตคอลนั้นเท่านั้น timelock ทำไม่ได้ |

การรอนี้สำคัญ ถ้าคีย์ของโปรโตคอลถูกขโมย คนร้ายจะแอบถอด invariant ก่อนโจมตีไม่ได้ การถอดต้องประกาศไว้
สองวัน และตลอดสองวันนั้น invariant ยังบังคับใช้อยู่

**วิธีต่อเข้ากับสัญญา** (ดู `FwVault` ใน `test/helpers/FirewallKit.sol`)

```solidity
import {Firewalled, IInvariantFirewall} from "./Firewalled.sol";

contract Vault is Firewalled {
    constructor(IInvariantFirewall fw, address dao) Firewalled(fw) { _firewallRegister(dao); }

    function withdraw(uint256 amount) external firewalled {
        balances[msg.sender] -= amount;
        totalDeposits -= amount;
        _firewallOutflow(address(0), amount);   // SS2: กติกาใบรับรอง
        payable(msg.sender).transfer(amount);
    }
}
```

**ค่าใช้จ่าย** หลังการเรียกชั้นนอกสุด มี `STATICCALL` หนึ่งครั้งต่อ invariant เทสต์จำกัดส่วนที่เพิ่มขึ้นจาก
invariant หนึ่งข้อไว้ไม่เกิน 40,000 แก๊ส งานของตัวตรวจแต่ละตัวคิดแยก และอยู่ในเพดานของมัน

**ข้อจำกัดของชั้นสัญญา** ระบบตรวจเฉพาะการเรียกที่เข้ามาทางฟังก์ชันที่มี `firewalled` ถ้าผู้ที่ได้รับอนุญาต
(approve) ดึงโทเคนออกด้วย `transferFrom` บนสัญญาโทเคนโดยตรง โค้ดของโปรโตคอลจะไม่ได้ทำงานเลย กรณีนี้
ชั้นเชน (ด้านล่าง) เป็นตัวปิดช่อง

## SS1: ชั้นเชน (อยู่ในโหนดแล้ว ปิดไว้เป็นค่าเริ่มต้น)

โค้ดโหนด วิธีเปิด เทสต์ และขั้นตอนอัปเกรด อยู่ใน [docs/CHAIN-FIREWALL.th.md](../CHAIN-FIREWALL.th.md)
ถ้าต่างจากบันทึกการออกแบบด้านล่าง ให้ยึดเอกสารนั้น

ชั้นสัญญาพึ่งให้โปรโตคอลเรียก `enforce` เอง ส่วนชั้นเชนให้โหนดเป็นคนตรวจ หลังทุกธุรกรรม EVM ที่สำเร็จ
(และทุก `MsgEVMCall`) โหนดจะอ่าน `InvariantFirewall.chainCheck()` บนสถานะที่ธุรกรรมทิ้งไว้ ถ้าโปรโตคอลใน
รายชื่อชั้นเชนมี invariant ที่เสียตอนนี้ แต่ก่อนธุรกรรมยังดีอยู่ ธุรกรรมนั้นจะล้มเหลว ไม่ว่าผู้โจมตีจะ
ผ่านสัญญาไหนมาก็ตาม

ใน `evmd` ที่แพตช์แล้ว จะทำงานแบบนี้
- **จุดเกาะ (hook)** cosmos/evm ย้อนทั้งธุรกรรมอยู่แล้วเมื่อ hook `PostTxProcessing` คืน error
  (`x/vm/keeper/state_transition.go`) และ `pqHooks` ของ ZETAPHY ก็คือ hook นี้ (quantum lock, threat gate,
  ระบบภูมิคุ้มกัน) ไฟร์วอลล์เพิ่มการเรียกเข้าไปหนึ่งบรรทัด คือ `firewallPostTx` และ `MsgEVMCall` ก็ได้
  การเรียกเดียวกัน ข้อความที่ล้มเหลวจะทิ้งสถานะของมันไป
- **การเรียก** เป็นแบบอ่านอย่างเดียว จากแอดเดรสโมดูล `zetaphy-firewall` ด้วยแก๊ส `CHAIN_CALL_GAS` =
  3,000,000 วิธีเดียวกับที่ `ModelVersionAt` อ่าน `ModelEpochs` คำตอบต้องเป็น
  `(address[] protocols, uint256 brokenMask)` พอดี มีโปรโตคอลไม่เกิน 8 ตัว และถอดรหัสแบบเข้มงวด
  (`firewallDecode`)
- **จุดตรวจ** โหนดจดไว้ว่าโปรโตคอลไหนเสียอยู่แล้วตอนเริ่มบล็อก (`BeginBlocker`) และจดใหม่หลังทุก
  ธุรกรรมที่ผ่าน ธุรกรรมจะถูกย้อนเฉพาะกรณีที่โปรโตคอลเสียตอนนี้ และ**ไม่ได้**เสียที่จุดตรวจล่าสุด ซึ่ง
  แปลว่าธุรกรรมนี้เป็นคนทำให้เสีย ถ้าโปรโตคอลเสียด้วยสาเหตุอื่น เช่น เวลาผ่านไป ข้อความที่ไม่ใช่ EVM หรือ
  ตัวตรวจที่เปลี่ยนคำตอบ ก็จะไม่ขวางทุกธุรกรรมบนเชน
- **ตั้งใจให้เปิดเมื่อพลาด (fail open)** ถ้าอ่านสัญญาไฟร์วอลล์ไม่ได้ (ไม่มีโค้ด revert แก๊สหมด หรือคำตอบ
  ผิดรูป) โหนดจะส่งอีเวนต์ `zetaphy_firewall_error` แล้วปล่อยธุรกรรมผ่าน ทะเบียนที่เสียจึงทำให้เชนหยุด
  ไม่ได้ `InvariantFirewall` คุมให้ทะเบียนที่ถูกต้องอยู่ในแก๊สเสมอด้วย
  - โปรโตคอลไม่เกิน 8 ตัว (`MAX_CHAIN`)
  - แก๊สตรวจรวมไม่เกิน 2,000,000 (`CHAIN_GAS_BUDGET`)
  - เพดานแก๊สของแต่ละการตรวจ และ `InsufficientGas`

  เทสต์รัน `chainCheck` ที่งบเต็มแล้วยังต่ำกว่า `CHAIN_CALL_GAS` ส่วนชั้นสัญญายังปิดเมื่อพลาดเหมือนเดิม
- **ใครอยู่ในรายชื่อ** governance ของโปรโตคอลขอเข้า (`requestChain`) แล้ว timelock อนุมัติ
  (`approveChain`) ภายในขอบเขต `MAX_CHAIN` และงบแก๊ส timelock เอาโปรโตคอลออกได้ทันที (`dropChain`) เช่น
  เมื่อโหนดรับภาระไม่ไหว invariant ในชั้นสัญญาของโปรโตคอลนั้นยังใช้อยู่ นอกจากนี้ โปรโตคอลจะออกได้ทาง
  เดียวคือถอนตัว ซึ่งต้องรอ
- **สวิตช์** ปิดอยู่จนกว่าข้อเสนอ governance จะตั้ง `security-proposal invariant-firewall <address>`
  (เป็นชนิดหนึ่งของ `MsgSetFuture` คีย์ในสโตร์ `0x31` จุดตรวจ `0x32`) ส่ง `{"address":""}` เพื่อปิด และ
  ใช้ได้เฉพาะบนเชนที่เปิด v5 แล้ว
- **ค่าใช้จ่าย** hook `PostTxProcessing` ใน cosmos/evm ไม่เก็บแก๊ส ทุกธุรกรรม EVM จึงทำให้โหนดต้องรันงาน EVM
  เพิ่มได้สูงสุด `CHAIN_CALL_GAS` นี่คือเหตุผลที่ทุกโปรโตคอลต้องให้ timelock อนุมัติ และงบเป็นค่าคงที่

**สถานะ:** ต้นแบบที่อธิบายไว้ที่นี่เป็นโค้ดโหนดจริงแล้ว (คอมไพล์และผ่าน fork test) ปิดไว้จนกว่าจะอัปเกรด
`zetaphy-firewall` และโหวตผ่าน ดู [docs/CHAIN-FIREWALL.th.md](../CHAIN-FIREWALL.th.md)

## SS2: ใบรับรองเป็นกติกาของเชน

timelock กำหนดเกณฑ์มูลค่าให้สินทรัพย์ได้ด้วย `setThreshold(asset, threshold)` (ไม่เกิน 8 สินทรัพย์
`address(0)` คือเหรียญหลักของเชน) สำหรับทุกสินทรัพย์ที่ตั้งเกณฑ์ไว้ ไฟร์วอลล์ใช้กติกานี้กับทุกโปรโตคอล
ที่ลงทะเบียน ถ้าโปรโตคอลถือสินทรัพย์นั้นตั้งแต่เกณฑ์ขึ้นไป และไม่มีใบรับรองที่ยังใช้ได้ จะจ่ายออกได้ไม่เกิน
`uncertifiedBps` ของยอดคงเหลือต่อวัน

ใบรับรองใช้ไม่ได้เมื่อไม่มี หมดอายุ ถูกเพิกถอน แฮชโค้ดถูกเพิกถอน หรือโค้ดของสัญญาเปลี่ยนไป
(ตรงกับ `AuditCertificate.isCertified` ทุกประการ) ค่า `uncertifiedBps` ตั้งต้นที่ 10% และ timelock ปรับได้
ระหว่าง 1% ถึง 50%

- ก่อนจ่ายเงินแต่ละครั้ง `Firewalled._firewallOutflow(asset, amount)` จะเรียก `recordOutflow` ถ้าเกินเพดานจะ
  revert ด้วย `OutflowLimited(protocol, asset, used, cap)` และ UI ดูยอดที่เหลือของวันนี้ได้จาก
  `outflowLeft(protocol, asset)`
- เพดานคือ `uncertifiedBps` × ยอดคงเหลือสูงสุดที่เห็นตอนมีเงินไหลออกในวันนั้น เงินฝากก้อนใหญ่ดันยอดสูงสุดขึ้นได้
  แต่การถอนเงินก้อนนั้นออกก็นับเป็นเงินไหลออกเต็มจำนวน การปั่นยอดคงเหลือ (เช่นด้วย flash loan) จึงไม่ช่วยให้
  ดึงเงิน*ส่วนอื่น*ออกได้มากขึ้น มีเทสต์ยืนยัน: ฝาก 5,000 แล้วถอน 5,000 ทันที ถูกปฏิเสธ
- เงินไหลออกทุกรายการที่บันทึกไว้ในวันนั้นนับรวมหมด รวมถึงตอนที่ยังมีใบรับรอง ใบรับรองที่หมดอายุกลางวันจึงไม่
  เปิดโควตาใหม่ให้
- พอมีใบรับรองที่ใช้ได้ เพดานหายทันที พอถูกเพิกถอนหรือหมดอายุ เพดานกลับมาทันที มีเทสต์กับ
  `AuditCertificate` ตัวจริง: โค้ดรันไทม์ของห้องนิรภัยผ่านกระบวนการตรวจและได้ใบรับรอง แล้วเพดานกลับมาเมื่อ
  พ้น `validity`
- โปรโตคอลที่ถือต่ำกว่าเกณฑ์ไม่ถูกจำกัด

**ผลต่อผู้ใช้สุจริต** ระหว่างที่ยังไม่มีใบรับรอง โปรโตคอลที่ถือมูลค่ามากจะจ่ายเงินออกได้ช้า ผู้ใช้สัญญาที่ยังไม่
ผ่านการตรวจแต่ถือเงินมากต้องรอหลายวันถ้าจะถอนก้อนใหญ่ นี่คือจุดประสงค์ของกติกา และเป็นเหตุผลที่ให้เป็นแบบ
สมัครใจบนเทสต์เน็ต

**การบังคับ SS2 ในชั้นเชนยังไม่ได้สร้าง** โปรโตคอลที่ลงทะเบียนแต่ไม่เคยเรียก `_firewallOutflow` จะไม่ถูกจำกัด
ถ้าจะให้โหนดบังคับ โหนดต้องเทียบยอดเหรียญหลักของโปรโตคอลที่ลงทะเบียนไว้ก่อนและหลังทุกธุรกรรม โดยใช้ hook และ
จุดตรวจเดียวกับด้านบน ส่วนนี้ยังเป็นแค่แบบร่าง

## ชุด invariant ที่ใบรับรองรับรอง

ใครก็เรียก `attest(protocol, requestId)` ได้ ฟังก์ชันนี้บันทึกแฮชของชุด invariant ปัจจุบันของโปรโตคอล ได้แก่
แอดเดรสตัวตรวจ แฮชโค้ดของตัวตรวจ เพดานแก๊ส และชื่อ ตามลำดับ จะสำเร็จก็ต่อเมื่อโปรโตคอลมีใบรับรองที่ยังใช้ได้ซึ่ง
ออกจากคำขอตรวจ `requestId` **และตัวตรวจทุกตัว**มีใบรับรองที่ยังใช้ได้ เพราะ invariant ก็เป็นโค้ด และต้องผ่านการตรวจแบบเดียวกัน `isAttested(protocol)` เป็นจริงต่อเมื่อ
ครบทุกข้อนี้
- ชุดยังเหมือนเดิม (ถ้าเพิ่ม ถอด หรือเปลี่ยน invariant ก็สิ้นสุด)
- ใบรับรองของโปรโตคอลยังใช้ได้ และมาจากคำขอตรวจ**เดิม**
- ใบรับรองของตัวตรวจทุกตัวยังใช้ได้

ผู้ที่นำไปใช้และ hub จะบังคับให้ต้อง `isAttested` ก็ได้ แบบเดียวกับที่ `AuditVerified` บังคับ `isCertified`

## ทำงานคู่กับ CircuitBreaker

[CircuitBreaker](self-healing.th.md) กับไฟร์วอลล์ทำหน้าที่ต่างกัน
- ไฟร์วอลล์**ปฏิเสธ**ธุรกรรมที่ทำให้ invariant เสีย
- CircuitBreaker **หยุด** selector ที่ระบุไว้ชั่วคราว และ**กัก**เงินไหลออกที่เกินเพดานของมัน

โปรโตคอลใช้ทั้งสองอย่างพร้อมกันได้ (`FwVault` สืบทอดทั้ง `Firewalled` และ `CircuitBreakable`) เทสต์แสดงว่า
เงินที่ CircuitBreaker กักไว้ทำให้บัญชียังพอจ่ายหนี้ ไฟร์วอลล์จึงปล่อยผ่าน หลังจากนั้นการตัดวงจรหยุดการฝากเงิน
และไฟร์วอลล์ยังปฏิเสธบั๊กเหมือนเดิม การละเมิดที่ถูก revert จะมี `InvariantViolated(protocol, checker, name)`
อยู่ในข้อมูล revert รันเนอร์ของ Neuro ที่เห็นความพยายามซ้ำ ๆ ใช้เป็นหลักฐานตัดวงจร CircuitBreaker ได้ (ผ่าน
เส้นทางรันเนอร์ k-of-n ที่มีอยู่) ไม่มีอะไรบนเชนตัดวงจรเองจาก revert เพราะ revert ไม่ทิ้งสถานะไว้

## โมเดลภัยคุกคามและข้อจำกัด

- **ไฟร์วอลล์บังคับ invariant ไม่ได้รับประกันว่าไม่มีบั๊ก** บั๊กที่ไม่ทำให้ invariant ข้อไหนเสียยังใช้ได้ ในเทสต์
  การดูดเงินส่วนเกินที่มีคนบริจาคมาพอดีก็ผ่าน เพราะยังพอจ่ายหนี้อยู่ ควรเขียน invariant จากสิ่งที่ต้องไม่เกิด
  เช่น ต้องพอจ่ายหนี้ ปริมาณโทเคนต้องคงที่ หนี้ต้องไม่เกินหลักประกัน
- **ตัวตรวจที่ผิดหรืออ่อน** ตัวตรวจที่ตอบจริงตลอดไม่ได้ปกป้องอะไรเลย `attest` จึงต้องการใบรับรองของตัวตรวจด้วย
- **โปรโตคอลถูกกลั่นแกล้งด้วยตัวตรวจของตัวเอง** ถ้าตัวตรวจเริ่มตอบไม่ผ่าน ฟังก์ชัน firewalled ของโปรโตคอลจะใช้ไม่ได้
  จนกว่า governance ของโปรโตคอลจะถอดออก และการถอดต้องรอ 2 วัน ตัวตรวจที่ไม่จริงเพิ่มเข้ามาไม่ได้ แต่คำตอบของมัน
  อาจเปลี่ยนในภายหลัง ควรให้ตัวตรวจเป็น view ที่อ่านเฉพาะสัญญาที่ปกป้อง
- **การเลี่ยงชั้นสัญญา** ทำได้ผ่านเส้นทางที่ไม่ได้เข้าฟังก์ชัน `firewalled` (allowance ของโทเคน การส่งด้วย
  `selfdestruct`) ชั้นเชนจะปิดช่องนี้เมื่ออยู่ในโหนดแล้ว
- **governance** timelock เพิ่มหรือถอด invariant ของใครไม่ได้ ย้ายเงินไม่ได้ (ไฟร์วอลล์ไม่ได้ถือเงิน) ทำได้แค่ตั้ง
  พารามิเตอร์ของกติกาใบรับรองที่มีขอบเขต และจัดรายชื่อชั้นเชน
- **Transient storage** solc เตือนว่า EIP-1153 อาจทำให้ประกอบสัญญาเข้าด้วยกันได้ไม่ดี `firewalled` คืนค่าความลึก
  ทุกครั้งที่ออก ช่องนั้นจึงกลับเป็น 0 เมื่อการเรียกชั้นนอกสุดจบหรือ revert

## การวิเคราะห์แบบสถิต

ผลกับ `InvariantFirewall.sol` และ `Firewalled.sol` (solc 0.8.26 เปิด optimizer, cancun)
- **Slither 0.11.6**: ไม่พบระดับ High หรือ Medium ที่เหลือเป็นระดับให้ข้อมูล ได้แก่ การเรียกในลูป (อ่านใบรับรอง)
  การใช้ timestamp, assembly (`STATICCALL` ที่มีเพดาน) รูปแบบของลูปกับอีเวนต์ และฟังก์ชันช่วยที่ยังไม่ถูกใช้ใน
  `Firewalled` ซึ่งเป็น abstract
- **Aderyn**: ไม่พบระดับ High มี Low 7 ข้อ (เรื่องรูปแบบ: ตัวเลขตรง ๆ ลูป การเก็บความยาวอาร์เรย์)

การเรียกออกไปภายนอกของไฟร์วอลล์ทุกครั้งเป็นการเรียกแบบ static (view) และการเปลี่ยนสถานะทุกอย่างเกิดก่อนการเรียก
(`addInvariant`, `recordOutflow`, `attest`) ประตูตรวจของ repository (`audit/`, `.github/workflows/audit.yml`) รันทั้งสองเครื่องมือ

## สิ่งที่ยังขาด

- **ยังไม่ได้ deploy** ยังไม่มีในสคริปต์ deploy คอนสตรักเตอร์คือ
  `InvariantFirewall(AuditCertificate, ZetaphyTimelock, uncertifiedBps)`
- **ชั้นเชนปิดไว้เป็นค่าเริ่มต้น** ต้องอัปเกรด `zetaphy-firewall` และโหวตผ่านก่อน ([CHAIN-FIREWALL.th.md](../CHAIN-FIREWALL.th.md))
- **ยังไม่มี UI** hub และ explorer ยังไม่แสดงโปรโตคอลที่ได้รับการปกป้องหรือการรับรอง ถ้ามีข้อความ UI ต้องมีครบ 8
  ภาษาของ hub
- **ยังไม่ผ่านการตรวจสอบ** สัญญาเหล่านี้ยังไม่ผ่านกระบวนการตรวจแบบเปิดหรือการตรวจแบบอื่นใด
