ไม่ได้แก้ patch ของ node (`zetaphy-chain/setup-node.sh`) ใช้สิ่งที่เชนมีอยู่แล้ว:
- **precompile ML-DSA `0x…0900`** (FIPS 204)
- **precompile P-256 `0x…0100`** ของ cosmos/evm (อินเทอร์เฟซ RIP-7212) ซึ่งเปิดอยู่แล้วใน
  `active_static_precompiles` ดังนั้น passkey ถูกตรวจ **บนเชน** ได้เลย
- precompile มาตรฐานของ EVM: `ecrecover`, `sha256`, `modexp` (ใช้ตรวจลายเซ็น FROST)

การทดสอบใช้ EVM ในหน่วยความจำ ซึ่งตอนนี้รับ precompile ที่เขียนด้วย JS ได้: ตัวตรวจ ML-DSA-44 **จริง**
(`@noble/post-quantum` รูปแบบ input เดียวกับเชน) ที่ `0x…0900` และตัวตรวจ P-256 ที่ `0x…0100` พร้อม
"authenticator" ทดสอบที่สร้าง assertion ของ WebAuthn แบบเดียวกับเบราว์เซอร์ จึงเซ็นด้วยกุญแจจริงทั้งคู่

## 23. ตัวตนและความรับผิดของ agent — `AgentRegistry`

`register(account, pqKeyHash, constitution, checker)` พร้อมเงินประกันอย่างน้อย `minBond` ผู้เรียกเป็น
**ผู้ดูแล (operator)** ที่รับผิดชอบ agent: บัญชี EVM ที่ agent ใช้, hash ของกุญแจ **ML-DSA-44**,
hash ของเอกสารนโยบาย (constitution) และสัญญาตรวจนโยบาย (ถ้ามี)

- `recordAction` บันทึกการกระทำพร้อม `modelHash`, `promptHash` เซ็นด้วยกุญแจ ML-DSA-44 ของ agent
  (ตรวจด้วย precompile, มีลำดับกันเล่นซ้ำ) และจำ constitution ณ เวลานั้นไว้
- **คำร้องแบบกำหนดได้แน่นอน**: `claimByChecker` แสดงเอกสาร constitution ตัวตรวจบอกว่าผิดหรือไม่ ใครเสียหาย
  และเท่าไร แล้วจ่ายจากเงินประกันทันที (`ConstitutionChecker` เป็นตัวอย่างที่ใช้งานได้)
- **คำร้องแบบคณะกรรมการ**: `fileClaim` พร้อมเงินมัดจำ คณะกรรมการที่ governance ตั้งลงคะแนน
  ถึงเกณฑ์ "ใช่" จ่ายผู้ร้อง ถึงเกณฑ์ "ไม่" หรือไม่ตัดสินใน 7 วัน ปฏิเสธและมัดจำไปที่ผู้ดูแล
- ร้องได้ภายใน 30 วันหลังการกระทำ ถอนประกันได้หลังขอ 7 วันและไม่มีคำร้องค้าง

**ข้อจำกัด**: ตัวตรวจเลือกโดยผู้ดูแล การบันทึกเป็นแบบสมัครใจ (ควรใช้คู่กับ `AgentPolicyWallet`)
`modelHash`/`promptHash` เป็นคำยืนยัน ไม่ใช่หลักฐานว่าโมเดลนั้นสร้างผลจริง (zkML/TEE ยังเป็นงานวิจัย)

## 24. Proof of Intent

ผู้ใช้เซ็น **สิ่งที่ต้องการ** (EIP-712 `Intent`: ส่ง/แลก/stake/อนุญาตแบบมีเพดาน/บริดจ์, จ่ายไม่เกิน `maxIn`,
ผู้รับได้อย่างน้อย `minOut`, ผู้รับ, รายการสัญญาที่อนุญาต, nonce, deadline) แบบ ECDSA หรือ **ML-DSA-44**
(`setPqKey`) solver ใดก็ได้ส่ง `execute` สัญญาจะรันคำสั่ง แล้ว **วัดยอดคงเหลือ**: ผู้ใช้เสียไม่เกิน `maxIn`
ผู้รับได้อย่างน้อย `minOut` executor ไม่เก็บอะไรไว้ เรียกได้เฉพาะสัญญาในรายการ ห้ามเรียกตัว token
ห้าม `transferFrom`/`approve`/`permit` ไม่เช่นนั้นยกเลิกทั้งหมด ทดสอบกับ DEX จริงของ ZETAPHY

- ตัวแปลงเป็นธุรกรรม (`src/intent.js`, `zetaphy intent show|compile|execute`) เป็นโค้ดที่แน่นอน ไม่ใช่โมเดล
- **ภาษาธรรมชาติ → intent** ในหน้า Agent: **โมเดลของผู้ใช้เอง** ผ่านชั้น AI ของ Neuro (คีย์ของตัวเอง
  ส่งจากเบราว์เซอร์ไปผู้ให้บริการเท่านั้น) ร่าง JSON ตาม schema ตายตัว ข้อความผู้ใช้ถูกล้อมเป็น "ข้อมูล"
  ระบบเก็บเฉพาะสิ่งที่ตรวจได้ แล้วเติมลงแบบฟอร์ม **เป็นเพียงคำแนะนำโดยตั้งใจ**: ทุกอย่างด้านล่างใช้กับร่างของโมเดล
  เหมือนกับแบบฟอร์มที่พิมพ์เอง

**แบบ (template) และตัวสร้างแบบมีโครงสร้าง** — ใช้ได้โดยไม่ต้องมีโมเดล: เลือกแบบแล้วกรอกช่องของแบบนั้น

| แบบ | kind | ช่อง | สิ่งที่ executor บังคับ |
|---|---|---|---|
| แลก | 2 | โทเคนจ่าย, จำนวน (สูงสุด), โทเคนรับ, ได้อย่างน้อย, ผู้รับ (ว่าง = ตัวเอง), นาที, router ของ DEX | จ่าย ≤ สูงสุด, ได้ ≥ ขั้นต่ำ, เรียกได้แค่ router |
| ส่ง | 1 | โทเคน, จำนวน (พอดี), ผู้รับ, นาที | ส่งจำนวนนั้นพอดีให้ผู้รับ |
| stake | 3 | โทเคนจ่าย, จำนวน, โทเคนใบรับ, ใบรับขั้นต่ำ, ผู้รับ, นาที, vault | เหมือนแลก |
| อนุญาตแบบมีเพดาน | 4 | โทเคน, เพดาน (รวม), ผู้ใช้สิทธิ์, จำนวนวัน (≤ 30) | `spendAllowance(intent, auth, to, amount)` เฉพาะผู้ใช้สิทธิ์, รวม ≤ เพดาน, ก่อนหมดอายุ, `cancel(nonce)` ยกเลิกได้ |
| บริดจ์ | 5 | โทเคน, จำนวน (พอดี), ผู้รับบนอีกเชน, นาที, บริดจ์ (outbox) | ส่งจำนวนนั้นพอดีเข้าบริดจ์เดียวที่ระบุ (`send(to, amount)` แบบ HyperlaneOutbox) executor ไม่เก็บอะไร |

- **schema เข้มงวด**: `validateBuilder()` รับเฉพาะช่องของแบบนั้น (ช่องเกินหรือขาดถือว่าผิด) เป็นข้อความรูปแบบตายตัว
  (ที่อยู่, ทศนิยมไม่เกินที่โทเคนมี, นาที 1…1440, วัน 1…30) โทเคนต้องอยู่ในรายการของ hub แล้ว `buildIntent()`
  และ `checkIntent()` ตรวจอีกครั้งก่อนเซ็น
- **สรุปเป็นประโยคเดียว** (`summary()`, 8 ภาษา) เช่น *"ส่ง 5 TKA พอดีให้ 0x… ใช้ได้ถึง 14:05"* พร้อมตารางทุกช่อง
- **จำลองก่อนเซ็น**: `IntentExecutor.simulate(intent, plan)` ทำทุกอย่างเหมือน `execute` ยกเว้นตรวจลายเซ็น
  และ **revert เสมอ** ด้วย `Simulated(spent, received)` (หรือข้อผิดพลาดที่จะเกิด) หน้าเว็บเรียกผ่าน `eth_call`
  จากที่อยู่ของผู้ใช้ แล้วแสดงว่า "จะสำเร็จ: คุณจ่าย X ผู้รับได้ Y" หรือเหตุผลเป็นคำพูด ปุ่มเซ็นต้องรอให้จำลองก่อน
  ถ้าจำลองล้มเหลว กดครั้งแรกแค่เตือน ธุรกรรม "อนุญาต executor" ผ่าน `send()` ของ hub จึงได้ผู้ช่วยก่อนเซ็น
  (`presign.js`: สรุป, จำลอง, คำอธิบายจาก AI ถ้าตั้งไว้)
- **วันหมดอายุและเพดานบนเชน**: ทุก intent มี deadline (≤ 24 ชม.; การอนุญาต ≤ 30 วัน) `maxIn` จำกัดแต่ละ intent
  และ **`setSpendCap(token, perDay)`** ให้ผู้ใช้ตั้งเพดานของตัวเองว่า intent ทั้งหมดรวมกัน (execute, บริดจ์,
  การดึงตามสิทธิ์) ใช้โทเคนหนึ่งได้เท่าไรต่อวัน (`capLeft`, revert `OverDailyCap`) หน้าตรวจแสดงยอดที่เหลือและตั้งเพดานได้
- CLI: `zetaphy intent show|compile|execute` รู้จักแบบใหม่ (`--bridge 0x…`) และ `zetaphy intent spend <ไฟล์> --to 0x…
  --amount n` สำหรับผู้ใช้สิทธิ์

**ข้อจำกัด**: ไม่มีตลาด solver หรือ relay (ไม่มีเซิร์ฟเวอร์ตลอดเวลา) ERC-20 เท่านั้น หนึ่ง token เข้าหนึ่งออก
การจำลองเป็นสถานะบล็อกล่าสุด ราคาอาจเปลี่ยน ขอบเขตที่เซ็นคือสิ่งที่ปกป้อง บริดจ์ไม่ส่ง value จึงใช้ได้เฉพาะเส้นทาง
ที่ค่า Mailbox เป็น 0 (testnet) และการส่งถึงอีกเชนไม่ได้ถูกตรวจที่นี่ เพดานรายวันตั้งโดยบัญชีเอง จึงจำกัดลายเซ็น
intent ที่หลุด/solver ที่ไม่ดีได้ แต่ไม่กันคนที่ขโมยกุญแจ การอนุญาตใช้ nonce ร่วมกับ intent อื่น
hub เซ็นแบบ ECDSA เท่านั้น แบบ PQ ใช้ผ่าน CLI/SDK

## 25. ป้ายคนหรือ agent — `LabelRegistry`

`labelOf` → 0 ไม่มี, 1 **คน**, 2 **agent** (อ่านสดจาก `AgentRegistry` และชนะป้ายคน)
- **คน บนเชน**: `proveHumanP256` passkey เซ็น challenge ของบัญชี ตรวจ type, challenge, rpIdHash,
  ธง user-present และ **user-verified** และลายเซ็น P-256 ผ่าน **precompile `0x…0100`**
- **คน ผ่านผู้รับรอง**: runner ที่ governance อนุมัติตรวจ WebAuthn นอกเชน แล้วเซ็น EIP-712 `HumanAttestation`
- **Hook**: `LabelFaucet` (จำนวนต่อป้าย, cooldown ต่อบัญชีและต่อ passkey) และ `LabelSwapGate` (วงเงินต่อชั่วโมงต่อป้าย)
- หน้า Agent: ดูป้าย และปุ่ม "ยืนยันว่าเป็นคน (passkey)"

**ข้อจำกัด**: ป้ายคนบอกแค่ว่ามีคนใช้อุปกรณ์ **ไม่ได้พิสูจน์ว่าคนหนึ่งมีบัญชีเดียว** (สร้าง passkey ได้หลายอัน)
faucet ของ node ยังไม่อ่านป้าย (ต้องแก้ patch ของเชน ซึ่งอยู่นอกขอบเขต) DEX ไม่ได้ถูกแก้

### ระดับ "ไม่ซ้ำ" แบบเลือกได้ — `VouchRegistry` (เครือข่ายการรับรอง)

`levelOf(account)` บอกชัดว่าที่อยู่อยู่ระดับไหน และ hub แสดงเป็นคำพูด:

| ระดับ | ชื่อ | ความหมาย |
|---|---|---|
| 0 | ไม่มี | ไม่มีป้ายคน (ไม่มีป้าย หรือเป็น AI agent) |
| 1 | **คน (passkey)** | ป้ายคนของ `LabelRegistry`: มีคนใช้ passkey **ยังไม่พิสูจน์ว่าไม่ซ้ำ** |
| 2 | **คนที่ได้รับการรับรองว่าไม่ซ้ำ** | คน passkey ที่ได้รับการรับรองจากคนระดับ 2 อย่างน้อย `vouchesNeeded` (ค่าเริ่ม 3) คน และไม่ถูกระงับหรือแบน |

ฟรีและไม่มีเซิร์ฟเวอร์: ไม่มีเงินวาง ไม่มีค่าธรรมเนียม ไม่มี oracle ไม่มี API

- **เริ่มต้น**: governance ตั้งชุดแรก (`setGenesis`) เช่นคนที่พบกันในงานมีตอัป คนอื่นเข้ามาด้วยการรับรอง
- **`vouch(who)`**: เฉพาะคนระดับ 2 รับรองคน passkey ได้ ว่า "คนจริงหนึ่งคน บัญชีเดียว" การรับรองผูกกับ **hash ของ passkey**
  ถ้าย้ายป้ายไป passkey อื่น การรับรองไม่นับ **จำกัดอัตรา**: รับรองได้ 1 ครั้งต่อ 7 วัน เปิดค้างได้ไม่เกิน 5
  และบัญชีที่เพิ่งได้ระดับ 2 ต้องรอ 30 วันก่อนรับรองคนอื่น `unvouch` ถอนได้ทุกเมื่อ `refresh(a)` (ใครก็เรียกได้)
  บันทึกสถานะ ส่วนระดับคำนวณ **สด** การรับรองจากบัญชีที่ถูกแบน ถูกระงับ หรือหมดสถานะ จะไม่นับทันที
- **ความรับผิด**: คนระดับ 2 `flag(a)` ได้ ครบ 5 คนบัญชีนั้นถูกระงับ (ระดับ 1, รับรองใครไม่ได้) จนกว่าจะถอนหรือ governance
  `clearFlags` (กันการรุมแจ้ง) governance `ban(a, evidenceHash)` บัญชีที่พิสูจน์ว่าซ้ำ (hash ของหลักฐานอยู่บนเชน)
  ผู้รับรองทุกคนของบัญชีนั้นได้ strike ครบ 2 strike ถูกแบนด้วย ค่าพารามิเตอร์มีขอบเขตและตั้งได้เฉพาะ governance
- **hub**: หน้า Agent → *คนหรือ agent?* แสดงระดับ, "การรับรองที่นับได้ n จาก N", การแจ้ง และปุ่ม **รับรองคนนี้**,
  **ถอนการรับรองของฉัน**, **อัปเดตสถานะ**

**วิเคราะห์ Sybil อย่างตรงไปตรงมา**: คนคนเดียวสร้างตัวตนระดับ 2 เองไม่ได้ (ต้องมี N คนรับรอง) การเพิ่มตัวตนปลอมถูกจำกัด
และช้า — กลุ่มคนจริง k คนที่สมรู้กันเพิ่มตัวปลอมได้ราว k·5/3 ในช่วงแรก ตัวปลอมรับรองต่อได้หลัง 30 วันและสัปดาห์ละครั้ง
จึงโตได้อย่างมากราว ×2.7 ต่อเดือน (โตแบบทวีคูณแต่ช้า และเห็นได้บนเชนเพราะทุกการรับรองเป็น event) ตัวปลอมที่ถูกจับ
ทำให้ผู้รับรองเสีย strike และสถานะ สิ่งที่ **ไม่ได้**: การสมรู้ร่วมคิดและ **การซื้อการรับรอง** ไม่ได้ถูกห้าม
แค่ถูกจำกัดและตามรอยได้ ชุดเริ่มต้นและการแบนขึ้นกับ governance **ปัญหา Sybil (คนหนึ่ง = บัญชีเดียว) ยังแก้ไม่หมด**
hook ควรมองระดับ 2 ว่า "ปลอมยากขึ้น" ไม่ใช่หลักฐานความเป็นบุคคล

**ระบบพิสูจน์ความเป็นคนที่มีอยู่แล้ว**: BrightID (ต้องใช้ API ของโหนด BrightID), Proof of Humanity (อยู่บน
Ethereum/Gnosis ต้องวางเงินและพิสูจน์ข้ามเชน), World ID (ต้องใช้ Orb ซึ่งเป็นอุปกรณ์ชีวมิติของบริษัทเดียว),
Idena (เชนของตัวเอง ต้องมีบริดจ์) ตอนนี้ไม่มีอันไหนตรวจบน ZETAPHY ได้โดยไม่ต้องพึ่งบริการเสียเงินหรือศูนย์กลาง
จึงยังไม่ได้เชื่อม ช่องทาง `attestHuman` ของ `LabelRegistry` คือจุดที่จะต่อได้ภายหลัง

## 9. รั้วกั้นกระเป๋าที่ AI ใช้ — `AgentPolicyWallet`

เจ้าของถือเงินและนโยบาย agent ทำได้แค่ในกรอบ: วงเงินต่อรอบต่อ token, รายการผู้รับและสัญญาที่อนุญาต,
ห้าม `transferFrom`/`increaseAllowance`/`setApprovalForAll`/`permit`, เกินเกณฑ์ต้อง **รอ timelock**
(เจ้าของยกเลิกได้) หรือมี **ลายเซ็นร่วมของ runner** และ **แช่แข็งฉุกเฉิน** ได้ด้วยบัญชีเจ้าของ,
**passkey** ของเจ้าของ หรือกุญแจ **ML-DSA-44** ของเจ้าของ (สองอย่างหลังใครส่งแทนก็ได้) ปลดได้เฉพาะเจ้าของ
ทุกการกระทำบันทึก `modelHash`, `promptHash` หน้า Agent แสดงสถานะ ตั้ง passkey ฉุกเฉิน และแช่แข็งด้วย passkey

**ข้อจำกัด**: วงเงินนับเป็นจำนวน token ไม่ใช่ราคา ถอดรหัสเฉพาะ `transfer`/`approve` สัญญาอื่นในรายการต้องเชื่อถือได้

## 14. AI ผู้ร่วมเซ็น — `CosignCommittee` + `src/cosign.js`

คณะกรรมการ runner ที่ **governance ตั้ง** runner ใช้ `zetaphy cosign review` อ่านสิ่งที่การกระทำแตะ
ด้วยกฎตายตัวของ Neuro (โค้ดเดียวกับ NeuroJobs ไม่ได้แก้ `zetaphy-neuro/src/`) ปฏิเสธถ้าระดับ **high**
(หรือ **medium** เมื่อ `--strict`) ไม่เช่นนั้นเซ็น digest ที่ผูกเชน กระเป๋า nonce ปลายทาง จำนวน calldata
`reportHash` และ deadline แล้ว `zetaphy cosign combine` เรียงลายเซ็นให้ `executeCosigned` (k-of-n ECDSA ทางสำรอง)

### ลายเซ็น threshold: FROST (RFC 9591) — `src/frost.js`, `FrostSecp256k1`, `executeCosignedFrost`

- **แบบแผน**: FROST(secp256k1, SHA-256) ตาม [RFC 9591](https://www.rfc-editor.org/rfc/rfc9591) เซ็นสองรอบ
  สมาชิก t จาก n คนสร้าง **ลายเซ็น Schnorr เดียว 65 ไบต์** โดยไม่มีใครถือกุญแจลับของกลุ่ม ใช้ `@noble/curves` 1.9.7
  (ตรึงเวอร์ชัน) สำหรับเลขคณิตของจุด และ `node:crypto` สำหรับ SHA-256/ECDH/AES
- **สร้างกุญแจโดยไม่มีผู้แจก** (RFC ไม่ได้กำหนด DKG และเราไม่ใช้ผู้แจกใน Appendix C): Pedersen DKG พร้อมการพิสูจน์ว่ารู้
  ค่าคงที่ของพหุนาม ตามเอกสาร FROST (Figure 1, KeyGen) ผูกกับ session ส่วนแบ่งที่ส่งให้แต่ละคน **เข้ารหัส**
  (ECDH → HKDF-SHA256 → AES-256-GCM) จึงส่งเป็นไฟล์หรือแปะในแชตสาธารณะได้ ทุกคนตรวจส่วนแบ่งกับ commitment ของผู้ส่ง
  (ส่วนแบ่งผิดระบุตัวผู้ส่งได้) ทุกขั้นพิมพ์ **transcript hash** ให้เทียบกันนอกระบบ (ไม่มีช่อง broadcast)
- **บนเชน**: `CosignCommittee.setFrostKey(groupKey)` (governance), `isValidFrost(digest, sig)` และ
  `AgentPolicyWallet.executeCosignedFrost(…)` (digest และ nonce เดียวกับทาง k-of-n) ตัวตรวจ `FrostSecp256k1`
  คำนวณ challenge ตาม RFC ใน Solidity (SHA-256 precompile) ยก R จากรูปบีบอัด (modexp) แล้วตรวจ `z·G − c·PK = R` ด้วย
  **ECRECOVER**: `ecrecover(−z·PK.x, v(PK), PK.x, −c·PK.x)` ให้ที่อยู่ของ `z·G − c·PK` เทียบกับที่อยู่ของ R
  (วิธีของ V. Buterin, ethresear.ch 2018 ที่ Chainlink `SchnorrSECP256K1.sol`, `noot/schnorr-verify` และ Scribe ของ
  Chronicle ใช้) ค่า gas ราว **15k** ไม่ว่า t, n เท่าไร (แพงกว่า ECDSA 2 อัน ถูกกว่าตั้งแต่ 3 อันขึ้นไป) และไม่เปิดเผยว่าใครเซ็น
- **CLI ใช้ไฟล์อย่างเดียว ไม่มีเซิร์ฟเวอร์**: `zetaphy cosign dkg1 | dkg2 | dkg3` (สร้างกุญแจ) แล้ว `commit` (รอบ 1),
  `frost-package`, `frost-sign` (รอบ 2: **รัน Neuro ใหม่และคำนวณ digest เอง** ปฏิเสธถ้า digest ในแพ็กเกจต่างกัน),
  `frost-aggregate` (ได้อาร์กิวเมนต์ของ `executeCosignedFrost`) nonce ใช้ครั้งเดียว (ลบไฟล์ก่อนเซ็น) ไฟล์ลับมีสิทธิ์ 0600
  และเข้ารหัสด้วย `ZETAPHY_PASSPHRASE` ถ้าตั้งไว้
- **การทดสอบ**: `test/frost.test.js` ตรวจกับ **test vector ของ RFC 9591 (Appendix E.5)** และ vector ของ DKG จาก
  `frost-secp256k1` 2.1.0 ของ Zcash Foundation, รัน DKG + การเซ็นครบ, กรณีแก้แพ็กเกจ/เล่นซ้ำ/สลับแพ็กเกจ/ส่วนแบ่งผิด/digest ผิด/
  nonce ซ้ำ และตรวจลายเซ็นของ RFC และของเรา **บนเชน** พร้อมกรณีปลอม

**ข้อจำกัด**: ทั้ง k-of-n ECDSA และ FROST บน secp256k1 ไม่ใช่ PQ (คณะกรรมการแบบ ML-DSA ทำได้ภายหลัง)
FROST ที่นี่เป็นโปรโตคอลสองรอบของ RFC: สมาชิกที่ส่งส่วนแบ่งผิดถูกระบุได้แต่ต้องเริ่มรอบเซ็นใหม่ เปลี่ยนสมาชิก/threshold
ต้องทำ DKG ใหม่ (ยังไม่มี refresh/repair) คณะกรรมการยังไม่มีเงินประกัน/รางวัล กฎของ Neuro ตัดสินสัญญา ไม่ใช่เจตนา
จึงยังต้องมีวงเงินและรายการอนุญาต
