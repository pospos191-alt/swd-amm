# ผลตัดสินที่มีหลักฐาน: "AI ที่พิสูจน์ทุกคำตอบ" (testnet)

ผลตัดสินความเสี่ยงของ Neuro ทุกรายการที่ขึ้นเชนผ่าน `ProvenVerdicts` จะมี **หลักฐานแบบ zero-knowledge** (Groth16)
แนบมาด้วยว่า **โมเดลบนเชนที่ตรึงไว้** เป็นผู้คำนวณคะแนนนั้นจริง และ **ฟีเจอร์ที่คะแนนนั้นอ้างถึง ใครก็คำนวณซ้ำได้จากโค้ดของโทเคนเอง**
ผู้รัน (runner) จึงประกาศคะแนนที่โมเดลไม่ได้ให้ไม่ได้ จะพิสูจน์คะแนนจากฟีเจอร์ที่แต่งขึ้นเองก็ต้องเสียเงินค้ำประกัน
และการตรวจไม่ต้องเชื่อใจผู้รัน ผู้ดูแลระบบ หรือเว็บไซต์ เพราะการตรวจทำในเบราว์เซอร์ของผู้อ่านเอง

งานนี้ต่อยอดจากของที่มีอยู่แล้ว (ไม่ได้แก้ส่วนใดของมัน): โมเดลบนเชนและวงจรของมัน (`docs/future/onchain-ml.md`)
ตัวตรวจสอบ `NeuroScoreVerifier.sol` ที่ commit ไว้ `NeuroScore` และ `NeuroJobs` ใช้บน testnet เท่านั้น

| รายการ | สถานะ |
|---|---|
| งานของผู้รัน: ฟีเจอร์จากโค้ด (`zfeat/1`), หลักฐานจากวงจรเดิม, ตรวจในเครื่อง, ส่งทีละหลายรายการ (`zetaphy-network/src/zkverdict/`) | **เสร็จ** พิสูจน์ได้ 1.3-2.0 วินาทีต่อรายการบนเครื่องนี้ |
| `ProvenVerdicts.sol`: ตรวจหลักฐานด้วยตัวตรวจสอบที่ผูกกับโมเดล, คำนวณคะแนนจาก margin ที่พิสูจน์แล้ว, โหมดหลักฐาน (Optional / Required), เงินค้ำและการริบ, ส่งเป็นชุด | **เสร็จ** ทดสอบบน EVM ในหน่วยความจำ กับ `NeuroScore`, ตัวตรวจสอบ และ `NeuroJobs` ตัวจริง |
| การผูกฟีเจอร์: คัดค้านคะแนนบนเชน (รันโมเดลซ้ำ) + คัดค้านฟีเจอร์ที่ตัดสินด้วยงาน NeuroJobs แบบ k-of-n | **เสร็จ** |
| ตรวจในเบราว์เซอร์ทั้งใน hub (การ์ด Immunity) และ explorer (หน้าสัญญา) 8 ภาษา, JS ล้วน (ไม่ใช้ WebAssembly, CSP ไม่ต้องเปลี่ยน) | **เสร็จ** ราว 70-130 ms ต่อหลักฐาน |
| ใช้งานจริง | **ยังไม่ได้**: ตัวตรวจสอบมาจากการซ้อมพิธี (ceremony) บนเครื่องเดียว (หัวข้อ 6) และไม่ได้เผยแพร่คีย์ของการซ้อม ตอนนี้จึงมีแค่หลักฐานตัวอย่างที่ commit ไว้เท่านั้นที่ผ่านการตรวจบนเชน |

## 1. อะไรพิสูจน์แล้ว อะไรยังไม่ได้พิสูจน์

**มีสองโมเดล** โมเดลที่ถูกพิสูจน์คือ **โมเดลบนเชน `nml-b4c35477f7b1`** (`zetaphy-neuro/ml/onchain/model.json`
133 ฟีเจอร์ แฮช H `0x7c420111…a4132`) ซึ่งวงจร zk ฝังไว้ตายตัวและพิธีของวงจรทำขึ้นเพื่อมัน ส่วน **AI ในเบราว์เซอร์**
(`zetaphy-neuro/ai/browser` โมเดล `nml-3ab3cd303911` 158 ฟีเจอร์) เป็น **อีกโมเดลหนึ่งที่ไม่ได้พิสูจน์** ทุกหน้าที่แสดงผลตัดสินที่มีหลักฐานจะบอกเรื่องนี้ไว้
โทเคนเดียวกันอาจได้ระดับความเสี่ยงไม่เท่ากันจากสองโมเดลนี้

**ข้อความที่หลักฐานพิสูจน์** (วงจรเดิม ไม่ได้แก้): "เวกเตอร์ฟีเจอร์ที่ผูกไว้เป็น `commitment` (Poseidon พร้อม salt สุ่ม)
ให้ค่า margin Z ภายใต้โมเดลที่มีแฮช H" ตัวตรวจสอบใส่ H ให้เอง (`verifyModelProof`) หลักฐานของโมเดลอื่น วงจรอื่น หรือคีย์อื่น จึงตรวจไม่ผ่าน

**สิ่งที่ผลตัดสินที่มีหลักฐานเพิ่มขึ้นมา และกลไกที่บังคับแต่ละข้อ:**

| ข้อกล่าวอ้าง | บังคับด้วย |
|---|---|
| คะแนนเป็นผลของโมเดลกับเวกเตอร์ *บางตัว* | หลักฐาน Groth16 (ตรวจบนเชนตอนส่ง และตรวจซ้ำในเบราว์เซอร์) |
| คะแนนที่เก็บคือคะแนนที่พิสูจน์ | สัญญาคำนวณเองจาก margin ที่พิสูจน์: `score = trunc(calibA * Z / scale) + calibB` ตามการปรับเทียบของโมเดลที่ตรึงไว้ (อ่านจากไบต์ของโมเดลตอน deploy) ผู้รันไม่ได้เป็นคนบอกคะแนนเลย |
| เวกเตอร์ที่พิสูจน์คือฟีเจอร์ที่ **ประกาศไว้** | `challengeScore(id, features)`: ใครก็รันโมเดลที่ตรึงไว้กับฟีเจอร์ที่ประกาศบนเชนได้ (`NeuroScore.evaluateAt`) ถ้าได้คะแนนอื่น ผลตัดสินถูกล้มและผู้รันถูกริบเงินค้ำ เบราว์เซอร์ก็ตรวจข้อนี้เหมือนกัน (อ่านไบต์ของโมเดลจาก `NeuroScore` ตรวจว่า keccak เท่ากับ H แล้วรันกับฟีเจอร์ที่ประกาศและเทียบ margin) |
| ฟีเจอร์ที่ประกาศคือฟีเจอร์ **ของโทเคนนั้นจริง** | ต้องเป็น `zfeat/1` ของ runtime code ของโทเคน (หัวข้อ 2) ซึ่ง keccak ของโค้ด (EXTCODEHASH) ถูกบันทึกไว้ตอนผลตัดสินลงเชน ใครก็คำนวณซ้ำได้ ถ้าเห็นไม่ตรงกันจะตัดสินด้วยงาน NeuroJobs แบบ k-of-n (หัวข้อ 2) และริบเงินค้ำของผู้รัน |

ทำไมเทียบ margin แทนการเทียบ commitment: commitment เป็นแฮช Poseidon ของ 20 ค่า (Poseidon บน BN254 ความกว้าง 17 แล้วต่อด้วย 6)
ซึ่ง EVM คำนวณซ้ำด้วยต้นทุนที่สมเหตุสมผลไม่ได้ และเราไม่แก้วงจรเพื่อเปิดเผยมัน การเทียบ margin ให้ผลแม่นยำสำหรับสิ่งที่สำคัญ:
ถ้าฟีเจอร์ที่ประกาศให้ margin เท่ากับที่พิสูจน์ คะแนนที่ประกาศก็คือคะแนนของโมเดลกับฟีเจอร์ที่ประกาศ ไม่ว่าหลักฐานจะผูกกับเวกเตอร์ใด
ถ้าให้ margin อื่น แปลว่าหลักฐานทำมาจากฟีเจอร์อื่น และผู้คัดค้านชนะแน่นอน (เป็นการคำนวณบนเชนที่ให้ผลตายตัว ไม่ต้องเชื่อใจอะไรนอกจากไบต์ของโมเดล)

**สิ่งที่ไม่ได้พิสูจน์** ไม่ได้พิสูจน์ว่าโทเคนไม่มีพิษภัยหรือมีพิษภัย คะแนนเป็นค่าประมาณทางสถิติจากข้อมูลฝึกที่สังเคราะห์ขึ้น
ไม่ได้พิสูจน์ว่า `zfeat/1` ครอบคลุมทุกอย่างที่ Neuro ดู (ใช้แค่โค้ด หัวข้อ 2) และก่อนพิธีสาธารณะจะเสร็จ ไม่ได้พิสูจน์ว่าคีย์ของตัวตรวจสอบสุจริต (หัวข้อ 6)

**พูดตรง ๆ เรื่องคุณค่า** สำหรับโมเดลเล็กที่เปิดเผยแบบนี้ การตรวจที่แข็งแรงที่สุดคือรันโมเดลซ้ำ (126k gas บนเชน ไม่ถึงมิลลิวินาทีใน JS)
และทั้งสัญญาและหน้าเว็บก็ทำแบบนั้นด้วย หลักฐานทำให้คำตอบของผู้รันกลายเป็นคำยืนยันที่ริบเงินได้ ผูกกับโมเดลที่ตรึงไว้ ตรวจได้โดยไม่ต้องรันอะไรซ้ำบนเชน
และจะเป็นการตรวจเดียวที่เหลืออยู่เมื่อฟีเจอร์ถูกเก็บเป็นความลับ หรือโมเดลใหญ่เกินกว่าจะรันใน EVM ระบบจึงสร้างให้การย้ายไปใช้โมเดลแบบนั้น
เป็นแค่วงจรใหม่ + พิธีใหม่ + ตัวตรวจสอบใหม่ + deploy `ProvenVerdicts` ใหม่ โดยใช้งานของผู้รันและหน้าเว็บชุดเดิม

## 2. ฟีเจอร์ที่ใครก็คำนวณซ้ำได้: โปรไฟล์ `zfeat/1`

`zetaphy-network/src/zkverdict/features.js` คือ 133 ฟีเจอร์ของโมเดลบนเชน ที่คำนวณ **จาก runtime bytecode อย่างเดียว**:

- selector และ opcode: `zetaphy-neuro/src/bytecode.js scanBytecode` (ตัวสแกนเดียวกับที่ reader ใช้) โคลน EIP-1167 ดูออกจากไบต์ของมันเอง
- กฎ: `zetaphy-neuro/src/analyze.js analyze()` ที่ป้อนแค่ผลสแกนนั้น ไม่มีการอ่านผ่าน RPC (ไม่มีชื่อ สัญลักษณ์ เจ้าของ หรือ storage slot ของ proxy)
  ไม่ใช้รายชื่อโทเคนที่รู้จัก ไม่ใช้ชุดข้อมูลความคล้าย ไม่ถาม ThreatRegistry
- ตัวสกัดฟีเจอร์ ML `zetaphy-neuro/ml/features.js extractFeatures({ report, code })`: ไม่มีการจำลองซื้อขาย (`m_*` = 0)
  และไม่มีข้อมูลตลาด (`k_*_known` เป็น 0 ทั้งหมด) แปลงเป็นจำนวนเต็มแบบเดียวกับที่ `NeuroScore` รับ (สเกล 1e7, u32 big-endian)

เวกเตอร์จึงเป็นฟังก์ชันของโค้ดล้วน ๆ ใครที่ได้โค้ดมา (จาก RPC ใดก็ได้ผ่าน `eth_getCode` แล้วเทียบกับแฮชโค้ดที่บันทึกไว้) จะได้ 532 ไบต์เดียวกันเป๊ะ
คะแนนที่พิสูจน์จึงหมายถึง "โมเดลที่ตรึงไว้กับฟีเจอร์ที่ได้จากโค้ดอย่างเดียว" และอาจต่างจากคะแนนที่เว็บ Neuro แสดงสำหรับโทเคนเดียวกัน
(เว็บใช้ผลจำลองซื้อขาย ข้อมูลผู้ถือ และข้อมูลจาก RPC เพิ่ม) กรณี proxy ใช้โค้ดของ proxy เอง ไม่ตามไปที่ implementation
(implementation เปลี่ยนได้ แต่แฮชโค้ดที่บันทึกไว้เปลี่ยนไม่ได้)

**การคัดค้านฟีเจอร์** (`contest` / `resolveContest` / `expireContest`):

1. ภายในช่วงคัดค้าน ใครก็วาง `contestBond` คัดค้านผลตัดสิน `id` ได้ ("นี่ไม่ใช่ฟีเจอร์ของโทเคนนี้") ระหว่างนั้นเงินค้ำของผู้รันถูกล็อกไว้
2. ใครก็ขอให้ NeuroJobs ทำงานบนเชน `"zetaphy"` ด้วยเป้าหมาย `featureTarget(id)` = `zfeat/1:<token>:<code hash>`
   ผู้รันของ NeuroJobs (`src/worker.js`) จะรู้จักเป้าหมายแบบนี้ อ่านโค้ด ปฏิเสธถ้าแฮชไม่ตรงกับเป้าหมาย แล้ว commit / reveal
   **keccak256 ของฟีเจอร์ zfeat/1** เหมือนผลตัดสินทั่วไป: commit-reveal, 2 ใน 3 ที่นั่ง และมีรอบคัดค้านของตัวเอง
3. เมื่องานนั้นยุติแล้ว (`NeuroJobs.assurance`) ใครก็เรียก `resolveContest(id, jobId)` ได้ ถ้าผลต่างจากแฮชของฟีเจอร์ที่ประกาศ
   ผลตัดสินถูกล้มและผู้รันถูกริบ (ผู้คัดค้านได้เงินค้ำคืนพร้อมครึ่งหนึ่งของเงินที่ริบ) ถ้าแฮชตรงกัน ผลตัดสินยืนตามเดิม (เงินค้ำของผู้คัดค้านตกเป็นของผู้รัน)
4. ถ้าเลย `contestTimeout` แล้วยังไม่มีงานที่ยุติ เรียก `expireContest`: ผลตัดสินยืน ผู้คัดค้านได้เงินค้ำคืน 80%

## 3. ขั้นตอนการทำงาน

1. **ผู้รัน** (`zetaphy-network/src/zkverdict/job.js`): ทีละโทเคน `eth_getCode` → `zfeat1(code)` → พิสูจน์ด้วยวงจรเดิม
   (`prover.js` คือ `snarkjs.groth16.fullProve` บน `zetaphy-neuro/ml/onchain/zk/out/neuro_score_js/` กับ zkey สุดท้ายของพิธี)
   → ตรวจหลักฐานในเครื่องกับคีย์ของตัวตรวจสอบที่ commit ไว้ (JS ล้วน) และตรวจว่า margin ตรงกับที่โมเดลให้กับฟีเจอร์เหล่านี้
   → ส่งผ่าน `submit` หรือ `submitBatch` หลักฐานที่จะไม่ผ่านบนเชน หรือทำมาจากฟีเจอร์อื่น จะไม่ถูกส่งเลย
2. **`ProvenVerdicts.submit(Proof)`**: ผู้รันต้องวางเงินค้ำแล้ว, `modelId` ต้องเป็นของโมเดลที่ตรึงไว้ (`WrongModel`), ฟีเจอร์ 133 x 4 ไบต์,
   `verifier.verifyModelProof(a, b, c, commitment, margin)` ต้องผ่าน (`InvalidProof`), หลักฐานเดิมใช้ซ้ำกับโทเคนเดิมไม่ได้ (`ProofUsed`),
   และโทเคนต้องมีโค้ด สิ่งที่เก็บ: โทเคน ผู้รัน เวลา คะแนน ระดับ proven = true แฮชฟีเจอร์ แฮชโค้ด แฮชหลักฐาน
   อีเวนต์: `Proven` (ผลตัดสิน) และ `ProofData` (หลักฐาน commitment margin และฟีเจอร์ 532 ไบต์: สิ่งที่เบราว์เซอร์ใช้ตรวจซ้ำ)
3. **การคัดค้าน** (หัวข้อ 1 และ 2)
4. **ผู้อ่าน**: `verdictOf(token)` → known, score, level, proven, weight, settled, id ทั้ง hub (Immunity → ใบรับรอง Neuro-checked)
   และ explorer (หน้าสัญญาและหน้าโทเคน) ตรวจหลักฐานซ้ำในเบราว์เซอร์ แล้วแสดง "พิสูจน์แล้วด้วยโมเดล nml-b4c35477f7b1 …"
   พร้อมเวลาที่ใช้ตรวจ คำเตือนเรื่อง testnet และหมายเหตุว่า AI ในเบราว์เซอร์เป็นอีกโมเดลหนึ่ง

**โหมดหลักฐาน** (`setProofMode` ผู้ตั้งคือ governance = timelock):

| โหมด | `claim(token, features, score)` ที่ไม่มีหลักฐาน | การอ่านผล |
|---|---|---|
| Optional (ค่าเริ่มต้น) | รับ น้ำหนัก 1 (`CLAIM_WEIGHT`) ถ้าคะแนนไม่ตรงกับโมเดล `challengeScore` จะริบเงินค้ำ | ผลที่มีหลักฐานน้ำหนัก 3 (`PROVEN_WEIGHT`) คำอ้างไม่มีหลักฐานจะไม่บังผลที่มีหลักฐานของโค้ดเดียวกัน |
| Required | ปฏิเสธ (`ProofRequired`) | คำอ้างเก่าที่ไม่มีหลักฐานอ่านเป็น "ไม่ทราบ" (น้ำหนัก 0) |

ตัวตรวจสอบของโมเดลอื่นจะถูกปฏิเสธตั้งแต่ตอน deploy (`ModelMismatch`): `ProvenVerdicts` อ่านโมเดลของ `NeuroScore` เวอร์ชันที่ระบุ
และบังคับให้ `verifier.MODEL_HASH()` เท่ากับแฮชของมัน และไบต์ที่เก็บไว้ต้องแฮชได้ค่านั้น โมเดลใหม่จึงหมายถึงวงจรใหม่ พิธีใหม่
ตัวตรวจสอบใหม่ และ `ProvenVerdicts` ตัวใหม่ ซึ่งตั้งใจออกแบบไว้แบบนี้: ตัวตรวจสอบเปลี่ยนไม่ได้

**เงินค้ำและการริบ** `register()` ด้วย `runnerBond` ผลตัดสินที่ถูกล้มทำให้ผู้รันเสียเงินค้ำครึ่งหนึ่ง (ครึ่งให้ผู้คัดค้าน อีกครึ่งเผาทิ้ง)
และถ้าเหลือต่ำกว่าเกณฑ์จะหมดสิทธิ์ส่ง เงินค้ำถอนไม่ได้จนกว่าผลตัดสินทุกรายการของผู้รันจะพ้นช่วงคัดค้านและไม่มีการคัดค้านค้างอยู่
(`withdrawBond` หลัง `unbondDelay`)

## 4. ต้นทุนและการส่งเป็นชุด

วัดบน EVM ในหน่วยความจำ (กฎ Cancun) โดย `test/provenverdicts.test.js`:

450k ไปไหน: ตรวจ pairing ราว 211k, บันทึกข้อมูล (5 storage word) ราว 110k บวกตัวชี้ของโทเคนและตัวกันใช้ซ้ำ, calldata ราว 32k
(หลักฐาน 256 ไบต์ + ฟีเจอร์ 532 ไบต์) และ log `ProofData` ขนาด 600 ไบต์ราว 10k **การส่งเป็นชุดประหยัดได้แค่ค่าโสหุ้ยต่อธุรกรรม (ราว 11%)**
เพราะทุกหลักฐานยังต้องตรวจ pairing ของตัวเอง ซึ่งเป็นต้นทุนหลัก จะประหยัดจริงต้อง **รวมหลักฐาน (aggregation)** เช่น SnarkPack
สำหรับ Groth16 หรือหลักฐานแบบ recursive ที่พิสูจน์การตรวจ N ครั้ง: ตรวจ pairing ครั้งเดียวสำหรับ N รายการ ยังไม่ได้ทำ
(ต้องใช้วงจรหรือไลบรารีใหม่ และแบบ recursive ต้องมีพิธีใหม่อีกรอบ) อีกทางที่ถูกลงทันทีคือส่ง 532 ไบต์ครั้งเดียวต่อแฮชโค้ด
(โค้ดเหมือนกัน ฟีเจอร์ก็เหมือนกัน) แล้วให้ `submitBatch` ใช้ซ้ำ ยังไม่ได้ทำเช่นกัน

## 6. ความน่าเชื่อถือ: เรื่องพิธี (ceremony)

Groth16 ต้องมีการตั้งค่าที่ต้องเชื่อใจ (trusted setup) **เฟส 1** ใช้ Perpetual Powers of Tau สาธารณะ (ผู้ร่วม 80 กว่าราย)
**เฟส 2** (ของวงจรนี้) เป็นพิธีหลายฝ่ายที่เตรียมไว้พร้อมแล้ว แต่ **ยังไม่ได้จัดแบบสาธารณะ**: ตัวตรวจสอบที่ commit ไว้มาจาก **การซ้อมบนเครื่องเดียว**
(`onchain-ml.md` หัวข้อ 6) ผลที่ตามมา ซึ่งทุกหน้าที่แสดงผลตัดสินที่มีหลักฐานจะบอกไว้:

- คนที่รันการซ้อมนั้นปลอมหลักฐานได้: **ใช้บน testnet เท่านั้น**
- ไม่ได้เผยแพร่คีย์สุดท้ายของการซ้อม ตอนนี้ผู้รันจึงสร้างหลักฐานที่ตัวตรวจสอบบนเชนยอมรับไม่ได้ งานของผู้รันจะไม่ส่งหลักฐานแบบนั้น
  (`onChain: false`) และการทดสอบบนเชนใช้หลักฐานตัวอย่างที่ commit ไว้ (ทำด้วยคีย์นั้น) ร่วมกับตัวตรวจสอบจำลองสำหรับทดสอบท่อการทำงาน
- จะใช้งานจริงได้ต้องจัดพิธีสาธารณะ (ขั้นตอนของเจ้าของอยู่ใน `onchain-ml.md` หัวข้อ 6) ถ้ามีผู้ร่วมอย่างน้อยหนึ่งคนทำลายค่าสุ่มของตัวเองจริง
  จะไม่มีใครปลอมหลักฐานได้ จากนั้น: export ตัวตรวจสอบจากคีย์สุดท้าย, สร้าง `zetaphy-hub/zkverdict-vkey.json` ใหม่
  (`node tools/zkverdict-vkey.mjs` มีเทสต์คอยปฏิเสธไฟล์ที่ล้าสมัย), deploy `ProvenVerdicts` กับตัวตรวจสอบนั้น และเผยแพร่คีย์สุดท้ายพร้อมพิธี
  (ผู้รันต้องใช้คีย์นี้ในการพิสูจน์)

งานนี้ไม่ได้แก้ transcript ของพิธี วงจร ตัวสร้างวงจร `ml/onchain/model.json` / `model.fixed.json` หรือ `NeuroScoreVerifier.sol` เลย

## 7. ความปลอดภัยต่อควอนตัม: Groth16 ไม่ปลอดภัย ทางของ STARK ปลอดภัยกว่า

Groth16 บน BN254 อาศัย pairing และ discrete logarithm คอมพิวเตอร์ควอนตัมขนาดใหญ่ที่รันอัลกอริทึมของ Shor ทำลายได้ (ปลอมหลักฐานได้)
และ BN254 ให้ความปลอดภัยแบบดั้งเดิมราว 100 บิต ไม่ถึง 128 ทางเลือกแบบ STARK:

- **STARK** (FRI อาศัยแค่แฮชที่ทนการชนกัน) มีแนวโน้มปลอดภัยต่อควอนตัม และ **ไม่ต้องมี trusted setup** จึงไม่ต้องมีพิธีเลย
  มีตัวพิสูจน์โอเพนซอร์สฟรีให้ใช้ เช่น Stwo / Circle STARKs, Plonky3 และ zkVM อย่าง RISC Zero, SP1
- โมเดลนี้เล็ก (ต้นไม้ 160 ต้น ลึกไม่เกิน 4 รวม 3,072 โหนด) AIR หรือโปรแกรม zkVM ที่เดินบนไบต์ที่แพ็กไว้ใช้ไม่กี่แสนขั้น
  พิสูจน์ได้ในไม่กี่วินาทีบนแล็ปท็อปน่าจะเป็นไปได้
- **ปัญหาอยู่ที่การตรวจบนเชน**: หลักฐาน STARK ใหญ่ราว 100-500 KB และตัวตรวจบน EVM โดยตรงกินหลายล้าน gas
  วิธีที่นิยมคือห่อ STARK ด้วยหลักฐาน Groth16 อีกชั้น ซึ่งดึงทั้ง trusted setup และจุดอ่อนต่อควอนตัมกลับมา
  ทางที่ปลอดภัยต่อควอนตัมจริงคือใช้ STARK ตลอดทาง: ตรวจ **นอกเชนในทุกที่** (เบราว์เซอร์ วอลเล็ต ผู้รัน การตรวจแบบแฮชเร็วพอใน JS / WASM)
  ส่วนบนเชนใช้แบบ optimistic (ประกาศแฮชของหลักฐาน แล้วให้ใครก็คัดค้านด้วยการตรวจเต็มเมื่อมีข้อพิพาท) หรือทำ precompile ตัวตรวจ STARK ในเชน
- commitment ของฟีเจอร์จะเปลี่ยนเป็นแบบแฮช (เช่น Poseidon2 / BLAKE3 ภายใน STARK) ส่วนการผูกฟีเจอร์ยังใช้การเทียบ margin แบบหัวข้อ 1
- ยังไม่ได้สร้างในงานนี้ บัญชีของ ZETAPHY มีทางใช้ลายเซ็นที่ปลอดภัยต่อควอนตัม (ML-DSA) อยู่แล้ว หลักฐานจะเป็นขั้นต่อไป

## 8. ข้อจำกัด

- พิธีที่ยังเป็นการซ้อม (หัวข้อ 6): คนที่รันปลอมได้ และยังส่งหลักฐานจริงไม่ได้จนกว่าพิธีสาธารณะจะเสร็จ
- `zfeat/1` ใช้แค่โค้ด จึงอ่อนกว่ารายงานเต็มของ Neuro และไม่ตาม implementation ของ proxy การสกัดฟีเจอร์ใช้ทศนิยมของ JavaScript
  (`Math.log1p` แล้วปัดที่ 1e-7) เอนจินที่ให้ `log1p` ต่างกันที่บิตสุดท้ายอาจเห็นไม่ตรงกันในฟีเจอร์ที่อยู่พอดีขอบการปัด
  เสียง 2 ใน 3 ของ NeuroJobs รับมือกับเครื่องที่ผิดเพี้ยนเครื่องเดียวได้
- งานฟีเจอร์ของ NeuroJobs ใช้เวลาทั้งช่วง commit, การ reveal และช่วงคัดค้านของมันเอง `contestTimeout` จึงต้องยาวกว่านั้น
  (เป็นพารามิเตอร์ตอน deploy) และเงินค้ำของผู้คัดค้านต้องสูงพอให้การสแปมแพงกว่าค่างาน
- เบราว์เซอร์อ่าน log `ProofData` ด้วย `eth_getLogs` ตั้งแต่บล็อก 0 RPC ที่จำกัดช่วงบล็อกต้องใช้คำค้นที่แคบลง (ไม่ได้เก็บหมายเลขบล็อกของผลตัดสินไว้)
- หนึ่งโมเดลต่อหนึ่งการ deploy ตามที่ออกแบบ ไม่มี aggregation (หัวข้อ 4) ไม่มีหลักฐานสำหรับโมเดลในเบราว์เซอร์
- ยังไม่ได้ต่อเข้ากับ router ของ DEX หรือ `ThreatRegistry` ทั้งสองอ่าน `verdictOf` (weight, proven) ได้เมื่อ governance ต้องการนโยบายที่รับเฉพาะผลที่มีหลักฐาน
