# Mempool แบบเข้ารหัสด้วย threshold ที่ทนควอนตัม (ต้นแบบงานวิจัย)

ใช้บน testnet เพื่อการวิจัยเท่านั้น ยังไม่มีอะไรเข้าไปอยู่ในเชน
สิ่งที่มีตอนนี้คือโค้ดอ้างอิงภาษา JavaScript, การจำลองที่ให้ผลเหมือนเดิมทุกครั้ง และแผนการต่อเข้ากับ `zetaphy-chain`
ไม่มีการแก้โค้ด consensus เลย รายละเอียดทางเทคนิคทั้งหมด (รูปแบบข้อมูล, pseudo-code) อยู่ในฉบับภาษาอังกฤษ
ฉบับนี้อธิบายเนื้อหาเดียวกันให้อ่านง่ายขึ้น

## เป้าหมายแบบสั้น ๆ

ถ้า searcher อ่านคำสั่ง swap ของเราได้ก่อนที่มันจะถูกจัดลำดับ เขาจะซื้อตัดหน้าแล้วขายตามหลังเรา (sandwich)
swap ของเรายังสำเร็จ แต่ได้ราคาแย่ที่สุดเท่าที่ค่า slippage ยอมให้ ส่วนต่างตกเป็นกำไรของ searcher

วิธีแก้คือ ผู้ใช้ส่งธุรกรรมแบบ **เข้ารหัส** บล็อก **ล็อกลำดับของ ciphertext ก่อน**
จากนั้นเมื่อลำดับนั้น commit แล้วเท่านั้น validator อย่างน้อย `t` จาก `n` คนจึงปล่อยสิ่งที่ใช้ถอดรหัสออกมา
แล้วธุรกรรมที่ถอดรหัสได้จะรัน **ตามลำดับที่ล็อกไว้เป๊ะ ๆ** ตอนต้นบล็อกถัดไป
กว่าใครจะอ่าน swap ของเราได้ ทุกธุรกรรมที่จะรันก่อนเราก็ถูกล็อกไปหมดแล้ว

## การออกแบบ

### กุญแจ

validator ทุกคนมี **กุญแจโหวต ML-DSA-44** อยู่แล้ว (ใบรับรองบล็อกแบบ PQ ใน `zetaphy-chain/README.th.md`)
ต้นแบบนี้เพิ่มกุญแจอีกหนึ่งดอกต่อ validator คือ **กุญแจรับส่ง X-Wing** (ML-KEM-768 + X25519)
ใช้รับส่วนแบ่งกุญแจจาก dealer เท่านั้น บนเชนจะลงทะเบียนด้วยข้อความที่เซ็นด้วยกุญแจโหวต (คล้าย `MsgPQVoteKey`)

### รอบ (epoch) และการแจกกุญแจ

แบ่งเวลาเป็นรอบละ `L` บล็อก ก่อนเริ่มรอบ `e` จะสุ่มเลือก **dealer** `d` คนจากค่าสุ่มสาธารณะ
(บนเชนคือค่า PREVRANDAO ที่มาจากใบรับรอง ML-DSA) dealer แต่ละคนจะ

1. สุ่ม seed ของ X-Wing ขนาด 32 ไบต์ใหม่ **ทุกความสูงบล็อก** ในรอบ แล้วประกาศกุญแจสาธารณะของแต่ละความสูง
   (กุญแจลับของ X-Wing ก็คือ seed 32 ไบต์นี้เอง ทำให้ขั้น threshold ง่ายมาก)
2. แบ่ง seed แต่ละตัวด้วย Shamir แบบ `t`-of-`n` และประกาศ hash ของทุกส่วนแบ่งไว้เป็นคำมั่น (commitment)
3. เข้ารหัสส่วนแบ่งของ validator แต่ละคนส่งไปยังกุญแจรับส่งของคนนั้น
4. เซ็นทั้งก้อนด้วยกุญแจโหวต ML-DSA-44 แล้ว **ลบ seed ทิ้ง**

validator แต่ละคนเปิดดูส่วนแบ่งของตัวเอง เทียบกับ commitment แล้วเซ็น **ack**
dealing ที่ได้ ack อย่างน้อย `t` ใบถือว่าใช้ได้ ผู้ใช้จะเข้ารหัสไปยัง dealer ที่ใช้ได้ **ทุกคน** เสมอ

ทำไมต้องมีกุญแจต่อความสูง ไม่ใช่ต่อรอบ: ถ้ามีกุญแจเดียวทั้งรอบ ปล่อยครั้งเดียวก็อ่านธุรกรรมที่เหลือทั้งรอบได้หมด
กุญแจต่อความสูงถูกปล่อยทีละบล็อก ซึ่งเป็นสิ่งที่ Shutter และ Ferveo ได้จาก threshold IBE ("identity = ความสูง")
แต่ IBE แบบ threshold ที่ทนควอนตัมและใช้งานได้จริงยังไม่มี dealer จึงต้องสร้างกุญแจต่อความสูงไว้ล่วงหน้าแทน

### ซองธุรกรรม (envelope)

- ข้างในคือธุรกรรม ZETAPHY ปกติที่เซ็นแล้ว (EVM หรือ PQ native) ซองไม่ได้แทนลายเซ็นเดิม
- ข้างนอกเซ็นด้วย ML-DSA-44 ของผู้จ่ายค่าธรรมเนียม ผู้จ่ายจ่าย **ค่าบรรจุเข้าบล็อก** ทันทีที่ซองถูกใส่ในบล็อก
  ไม่ว่าจะถอดรหัสได้หรือไม่ ขนาดซองจำกัดไว้ที่ 64 KiB
- ซองใช้ได้ **เฉพาะในบล็อก `h` ที่ระบุเท่านั้น** เพราะกุญแจของ `h` จะเปิดเผยทันทีหลัง `h`
  ถ้าพลาดบล็อกนั้น ผู้ใช้ต้องเข้ารหัสใหม่สำหรับความสูงถัดไป
- ข้อมูลส่วนหัว (ความสูง, รอบ, ค่าธรรมเนียม, ผู้จ่าย, ชุด dealer) ถูกผูกกับ ciphertext ผ่าน AAD
  ใครแกะลายเซ็นข้างนอกแล้วเซ็นใหม่ในชื่อตัวเอง จะได้ซองที่ดูถูกต้องแต่ถอดรหัสไม่ได้ตลอดไป
- เนื้อธุรกรรมถูกเติมให้ยาวเป็นทวีคูณของ 256 ไบต์ เพื่อซ่อนขนาดที่แท้จริง (แต่ไม่ซ่อนว่าอยู่ช่วงขนาดไหน)

### ลำดับ, การปล่อยกุญแจ, การถอดรหัส, การหมดอายุ

- **บล็อก `h`:** proposer ใส่ซองสำหรับ `h` ทุกโหนดตรวจซองทีละใบ แล้วคำนวณ `batchHash(h)` จาก hash ของซองตามลำดับในบล็อก
- **หลัง `h` commit:** ลำดับเป็นที่สิ้นสุด ไม่มีใคร (รวมถึง proposer) อ่านเนื้อหาได้
- **หลังจากนั้น:** validator แต่ละคนปล่อยส่วนแบ่งของตัวเองสำหรับความสูง `h` เซ็นด้วย ML-DSA-44 ทับ `batchHash(h)`
  โหนดจะรับเฉพาะเมื่อบล็อก `h` commit แล้ว, batch hash ตรงกับที่ commit, ส่วนแบ่งตรงกับ commitment และลายเซ็นถูกต้อง
- **บล็อกถัดมาที่มีส่วนแบ่งครบ `t`:** ตอนต้นบล็อก ก่อนธุรกรรมปกติใด ๆ ทุกโหนดประกอบกุญแจ ตรวจว่าตรงกับกุญแจสาธารณะ
  ถอดรหัส แล้วรันตามลำดับใน batch ซองขยะที่ถอดไม่ออกจะถูกข้ามไป
- **หมดอายุ:** ถ้าเลย `h + ttl` แล้วยังถอดไม่ได้ batch นั้นหมดอายุ ไม่มีธุรกรรมไหนในนั้นได้รัน
  ผู้ใช้เสียแค่ค่าบรรจุ และ nonce ยังอยู่เหมือนเดิม
- batch รันตามลำดับความสูงเสมอ batch เก่าที่ยังรออยู่จะกั้น batch ใหม่ไว้ ลำดับการบรรจุจึงไม่มีวันกลับหัว

การปล่อยส่วนแบ่งโดยเซ็นทับ batch hash ที่ไม่ใช่ตัวที่ commit คือหลักฐานว่าปล่อยก่อนเวลาหรือปล่อยให้ fork ลงโทษ (slash) ได้
และถ้าส่วนแบ่งที่ตรง commitment ทุกชิ้นประกอบออกมาแล้วไม่ตรงกับกุญแจสาธารณะ แปลว่า dealer แจกมั่ว ระบุตัวได้ (มีเทสต์)

### ทำไม sandwich จึงทำไม่ได้

sandwich ต้องมี **ขาหน้าที่รันก่อนเหยื่อ** และต้องเลือกโดยรู้ว่าเหยื่อจะทำอะไร
ภายใต้กฎนี้ ทุกอย่างที่รันก่อนเหยื่อ อยู่ในบล็อกก่อนหน้า, ในบล็อก `h` เอง (ธุรกรรมปกติของ `h` รันระหว่าง `h`
ส่วน batch รันต้นบล็อก `h+1`) หรืออยู่ใน batch `h` ก่อนหน้าเหยื่อ ทั้งหมดนี้ถูกล็อกตอนที่เหยื่อยังเป็น ciphertext อยู่
ขาหน้าจึงทำได้แค่ **เดา** ส่วนการ back-run หลังเปิดเผยยังทำได้ แต่นั่นคือ arbitrage ธรรมดาที่ไม่ทำให้ราคาของเหยื่อแย่ลง

## ผลการจำลอง (`node scripts/encmempool-sim.js`)

pool แบบผลคูณคงที่ 4,000,000 A / 2,000 B (ค่าธรรมเนียม 0.30%) เหยื่อ swap 60,000 A → B ยอม slippage 1%
searcher จ่ายค่า gas 2 A ต่อขา ฝั่งเข้ารหัสใช้คริปโตจริงทั้งหมด batch มี [เหยื่อ, ซองขยะที่จ่ายเงินแล้ว], ttl = 3
ผู้สมรู้ร่วมคิดเลือกจากคนที่ไม่ใช่ dealer ก่อน ส่วน dealer ที่สมรู้ร่วมคิดจะเก็บ seed ไว้

| สถานการณ์ (n = 21, t = 15, d = 3) | searcher อ่านเหยื่อได้ก่อน | เหยื่อรันที่ | เหยื่อเสีย (≈A) | กำไร searcher (A) |
|---|---|---|---|---|
| mempool ปกติ (ไม่เข้ารหัส) | ได้ | บล็อก 1 | 589.39 | 480.08 |
| เข้ารหัส ไม่มีใครสมรู้ร่วมคิด | ไม่ได้ | บล็อก 2 | 0 | 0 |
| เข้ารหัส สมรู้ร่วมคิด 14 คน (t-1) | ไม่ได้ | บล็อก 2 | 0 | 0 |
| เข้ารหัส สมรู้ร่วมคิด 15 คน (t) | **ได้** | บล็อก 2 | 589.39 | 480.08 |
| เข้ารหัส dealer ทั้ง 3 คนเก็บ seed ไว้ | **ได้** | บล็อก 2 | 589.39 | 480.08 |
| เข้ารหัส กักส่วนแบ่ง 6 คน (n-t) | ไม่ได้ | บล็อก 2 | 0 | 0 |
| เข้ารหัส กักส่วนแบ่ง 7 คน (n-t+1) | ไม่ได้ | หมดอายุที่บล็อก 5 | 0 (เสียแค่ค่าบรรจุ) | 0 |

n = 4 (t = 3) และ n = 100 (t = 67) ให้ผลรูปแบบเดียวกัน ซองของเหยื่อมีขนาด 7,445 ไบต์
ค่าบรรจุ 0.0000075 ZETAPHY (ที่ 1 gwei ต่อไบต์)

sandwich แบบเดา (อ่านเหยื่อไม่ได้) กับเหยื่อสุ่ม 2,000 ราย: ขาหน้า 5,000 A ขาดทุนเฉลี่ย 29.95 A,
20,000 A ขาดทุนเฉลี่ย 173.98 A, 60,000 A ขาดทุนเฉลี่ย 1,054.91 A
ขณะที่ถ้าอ่านได้ กำไรเฉลี่ย 331.09 A ต่อเหยื่อ

อ่านผลอย่างตรงไปตรงมา:

- **ต่ำกว่า threshold** searcher ไม่ได้ข้อมูลอะไรเลย (Shamir ปลอดภัยเชิงทฤษฎีสารสนเทศ) และเหยื่อได้ราคายุติธรรม
- **ถ้าสมรู้ร่วมคิดครบ `t` คน ระบบพังสำหรับบล็อกนั้น** เหมือนระบบ threshold ทุกระบบ
  พวกเขาประกอบกุญแจจากส่วนแบ่งของตัวเองได้ทันที ถอดรหัสจาก mempool แล้ว sandwich ได้กำไรเท่ากับ mempool ปกติ
- **ถ้า dealer ทั้ง `d` คนเก็บ seed ไว้ ก็พังเหมือนกัน** และ `d` (3) น้อยกว่า `t` มาก นี่คือจุดอ่อนหลักของต้นแบบนี้
- **ความต่อเนื่อง (liveness):** กักส่วนแบ่ง `n-t` คนยังถอดรหัสได้ กัก `n-t+1` คนถอดไม่ได้
  batch หมดอายุหลัง `ttl` บล็อก และเหยื่อเสียแค่ค่าบรรจุ คนกักส่วนแบ่งอ่านอะไรไม่ได้ เว้นแต่จะมีครบ `t`

ขนาดเป็นค่าจริง เวลาวัดด้วย JavaScript ล้วน (`@noble/post-quantum`) เธรดเดียว ถ้าเขียนด้วย Go จะเร็วกว่าหลายเท่า

- **ต่อธุรกรรม:** ธุรกรรม 250 ไบต์ กลายเป็นซอง 5,201 / 7,445 / 9,689 ไบต์ เมื่อมี dealer 1 / 3 / 5 คน
  ส่วนคงที่คือกุญแจสาธารณะ ML-DSA-44 ของผู้จ่าย (1,312) และลายเซ็น (2,420) ซึ่งธุรกรรม PQ ของ ZETAPHY ต้องจ่ายอยู่แล้ว
  ตัวการเข้ารหัสเองเพิ่ม 1,120 ไบต์ต่อ dealer
- **เวลา (d = 3):** เข้ารหัส + เซ็นฝั่งผู้ใช้ ~23 ms, โหนดตรวจซอง ~2 ms, ถอดรหัสหนึ่งธุรกรรม ~17 ms

| 4 | 3 | 2,614 B | 10.2 KiB | 158.7 KiB | 15.2 KiB | ~9 ms | ~12 ms |
| 21 | 15 | 2,614 B | 53.6 KiB | 317.5 KiB | 63.5 KiB | ~26 ms | ~6 ms |

ขนาดส่วนใหญ่มาจากลายเซ็น ML-DSA-44 (2,420 ไบต์) ของการปล่อยส่วนแบ่งแต่ละครั้ง
ทางเลือกที่ไม่ต้องมี dealer (ผู้ใช้แบ่งกุญแจของตัวเองส่งให้ validator ทุกคน) ต้องใช้ `n x 1,152` ไบต์ต่อธุรกรรม
คือ 4.6 KB ที่ n = 4, 24 KB ที่ n = 21, 115 KB ที่ n = 100 จึงเหมาะกับคณะเล็ก ๆ เท่านั้น

## ข้อจำกัดที่ต้องพูดตรง ๆ

**ส่วนที่ทนควอนตัม**

- ความลับของซองและของส่วนแบ่งที่แจก: ML-KEM-768 (ใน X-Wing) + AES-256-GCM
  X25519 เก็บไว้แค่กันกรณี ML-KEM มีจุดบกพร่อง
- ความลับของกุญแจเมื่อมีส่วนแบ่งไม่ถึง `t`: Shamir ไม่พึ่งสมมติฐานใด ๆ เลย
- ความถูกต้องของซอง, dealing, ack และการปล่อยส่วนแบ่ง: ML-DSA-44 (FIPS 204)

**ส่วนที่ยังไม่ใช่ หรือยังทำไม่ได้**

- **นี่ไม่ใช่ threshold KEM** ปัจจุบันยังไม่มี threshold KEM หรือ threshold IBE ที่ทนควอนตัมและใช้งานจริงได้
  การถอดรหัสแบบ threshold บน lattice ยังอยู่ในงานวิจัย และการ decapsulate ของ ML-KEM ไม่เป็นเชิงเส้น จึงแบ่งแบบ ElGamal ไม่ได้
- **ต้องไว้ใจ dealer** ต้องมี dealer อย่างน้อยหนึ่งใน `d` คนที่ลบ seed จริง พิสูจน์ไม่ได้ว่าลบแล้ว
  กลุ่มที่คุมสัดส่วน `p` ของ validator จะได้ dealer ครบทั้ง `d` คนด้วยโอกาสประมาณ `p^d` ต่อรอบ
  เช่น `p = 1/3`, `d = 3` ได้ 3.7% ของรอบ ถ้า `p` เกือบ 2/3 จะได้ราว 29% เพิ่ม `d` ได้ แต่ต้องจ่าย 1,120 ไบต์ต่อธุรกรรมต่อ dealer
  ระบบจริงต้องมี DKG ที่ทนควอนตัม (ยังเป็นงานวิจัย) หรือใช้ `d` ที่ใหญ่กว่านี้มาก
- **ไม่มี verifiable secret sharing** ส่วนแบ่งผูกไว้ด้วย hash เท่านั้น (Feldman/Pedersen อาศัย discrete log จึงไม่ทนควอนตัม)
  dealing ที่แจกไม่สอดคล้องกันจะรู้ตอนประกอบกุญแจ ทำให้ความสูงของ dealer นั้นหมดอายุ (กระทบ liveness ระบุตัวคนผิดได้ แต่ไม่ทำให้ความลับรั่ว)
- **การสมรู้ร่วมคิดครบ `t` ตรวจจับไม่ได้** ถอดรหัสล่วงหน้าเงียบ ๆ ได้ทุกความสูงในรอบ
  ระบบนี้ย้ายความไว้ใจจาก "ใครก็ตามที่เห็น mempool" ไปเป็น "validator อย่างน้อย `n-t+1` คนสุจริต"
- **ไม่ถ่วงน้ำหนักตาม stake** หนึ่งคนหนึ่งส่วนแบ่ง ทั้งที่กฎอื่นของเชนถ่วงตาม power (ทำแบบ Ferveo ได้ แต่ยังไม่ได้ทำ)
- **ชุด validator เปลี่ยนกลางรอบ** คนที่ออกไปแล้วยังถือส่วนแบ่งจนจบรอบ และลงโทษไม่ได้แล้ว
- **metadata รั่ว** ผู้จ่าย, ช่วงขนาด, gas limit, ค่าธรรมเนียม, เวลา เป็นสาธารณะ ยัง front-run เชิงสถิติได้
- **ช้าลง** ธุรกรรมรันช้ากว่า mempool ปกติหนึ่งบล็อก (สองบล็อกถ้าใช้เส้นทางสำรองผ่าน vote extension)
- **รู้ว่าธุรกรรมข้างในใช้ได้หรือไม่ก็ต่อเมื่อถอดรหัสแล้ว** ถ้าล้มเหลว (nonce, ยอดเงิน) ค่าบรรจุก็จ่ายไปแล้ว
- **back-run และการเซ็นเซอร์ยังทำได้** proposer ยังเลือกไม่ใส่ซองได้
- **consensus ยังเป็น ed25519** (โหวตของ CometBFT) แต่กฎใบรับรอง ML-DSA ของเชนช่วยกันเรื่อง finality อยู่แล้ว
- **ความลับที่นี่มีอายุสั้นโดยตั้งใจ** ทุกอย่างเปิดเผยหลังรันอยู่แล้ว ปัญหา "เก็บไว้ก่อน ถอดทีหลัง" จึงไม่เกี่ยว
  KEM แบบ PQ มีผลเฉพาะกับผู้โจมตีที่ทำลาย X25519 ได้ *ภายในไม่กี่วินาทีก่อนล็อกลำดับ*
  คุณค่าระยะยาวคือไม่มีส่วนไหนของการออกแบบ (ลายเซ็น, การปล่อยส่วนแบ่ง, dealing) พึ่ง discrete log หรือ pairing เลย
- โค้ดต้นแบบ ยังไม่ผ่าน audit ใช้ JS เท่านั้น

## แผนการต่อเข้าเชน (ออกแบบไว้เท่านั้น)

จะอยู่ในไฟล์ใหม่ `evmd/zetaphy_encmempool.go` ต่อเข้ากับจุดเดียวกับที่ใบรับรอง PQ และระบบภูมิคุ้มกันใช้อยู่
(`pqProposalHandlers`, `setPQVoteHandlers`, `pqPreBlock` ใน `evmd/zetaphy_pqcert.go`) และเปิดใช้ด้วยความสูงบล็อกแบบเดียวกับ `v2`/`v5`

- **PrepareProposal(h):** ใส่ `MsgDecryptionKeys` ต่อจากใบรับรองและ `MsgZXVotes` ถ้ามีส่วนแบ่งครบ `t` สำหรับ batch ที่รออยู่
  (ทางด่วน: ส่วนแบ่งที่กระจายกันหลัง commit ระหว่าง timeout_commit ทางสำรอง: vote extension ใน LocalLastCommit)
  แล้วตามด้วยซองสำหรับ `h` แล้วจึงเป็นธุรกรรมปกติ
- **ProcessProposal(h):** ตรวจซองทุกใบ (ความสูง, รอบ, ชุด dealer, ขนาด, ค่าธรรมเนียม, ลายเซ็น) และตรวจส่วนแบ่ง
  ถ้า vote extension มีส่วนแบ่งครบ `t` แล้ว proposer **ต้อง** ใส่กุญแจ (แนวเดียวกับกฎ v2 ที่ proposer ต้องเซ็นเอง)
- **ExtendVote(h):** ต่อท้ายส่วน `"EM1"` หลังลายเซ็น ML-DSA และ payload ของระบบภูมิคุ้มกัน
  ใส่ส่วนแบ่งเฉพาะ batch ที่ **commit แล้ว** (h-1 และเก่ากว่า) เพราะ ExtendVote(h) ถูกเรียกก่อน `h` จะเป็นที่สิ้นสุด
  ถ้าปล่อยของ `h` ตรงนี้แล้วรอบนั้นล้ม บล็อกอื่นที่ commit แทนจะอ่านเนื้อหาของ `h` ได้
- **VerifyVoteExtension(h):** ตรวจส่วน `"EM1"` ทุกชิ้น
- **PreBlocker(h):** ประกอบกุญแจ ถอดรหัส แล้วรันธุรกรรมของ batch ที่รออยู่ตามลำดับความสูง ก่อนธุรกรรมใด ๆ ของ `h`
  ถ้ายังไม่ครบและยังไม่เลย `ttl` ก็รอ ถ้าเลยก็ให้หมดอายุ
- เรื่องที่ต้องระวังใน Go: ธุรกรรมที่ถอดรหัสแล้วไม่ได้อยู่ใน `req.Txs` จึงต้องออก event/receipt ผ่านธุรกรรมกุญแจ
  และให้ JSON-RPC รู้จัก (ปัญหาเดียวกับ log ของ `MsgEVMCall`), ต้องกัน gas ของ batch ไว้ในบล็อกถัดไป,
  เลือก dealer ล่วงหน้าหนึ่งรอบ, และหลักฐานสำหรับ slash (ปล่อยส่วนแบ่งทับ batch hash ผิด, dealing ที่ไม่สอดคล้อง)

pseudo-code ฉบับเต็มอยู่ในฉบับภาษาอังกฤษ

## เทียบกับระบบอื่น

- **Shutter** (Gnosis Chain): คณะ keyper ทำ DKG แล้วใช้ threshold IBE บน BLS12-381 ปล่อยกุญแจของแต่ละ slot หลัง slot นั้น
  ciphertext เล็ก (ราวร้อยกว่าไบต์) แต่ pairing ไม่ทนควอนตัม
- **Ferveo** (Anoma/Namada และที่เสนอไว้สำหรับ Osmosis): DKG แบบ PVSS ถ่วงน้ำหนักตาม stake,
  threshold encryption บน BLS12-381, ส่งส่วนแบ่งผ่าน vote extension ของ Tendermint (ABCI++)
  รูปแบบการต่อเข้าเชนของเราเหมือนกัน แต่ Ferveo ไม่ทนควอนตัม
- **งานวิจัยของ Ethereum:** roadmap จัด encrypted mempool ไว้เป็นเรื่องที่ยังเปิดอยู่ (หมวด "The Scourge")
  มีทั้งแนว threshold encryption, delay encryption และฮาร์ดแวร์ที่เชื่อถือได้ (TEE)

เท่าที่เรารู้ ยังไม่มี encrypted mempool ตัวไหนที่ใช้งานจริงแล้วทนควอนตัม ต้นแบบนี้แสดงว่าวันนี้ต้องจ่ายอะไรบ้าง
(หลายกิโลไบต์ต่อธุรกรรม และต้องไว้ใจ dealer) และชิ้นที่ยังขาด (threshold KEM หรือ DKG ที่ทนควอนตัม) จะเสียบตรงไหน:
เปลี่ยนแค่ `dealing.js` ส่วนอื่นใช้ต่อได้ทั้งหมด
