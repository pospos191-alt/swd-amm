## 1. สิ่งที่พิสูจน์ได้

**ชุดผู้ตรวจสอบ** ของแต่ละยุค (epoch) ถูกผูกมัดครั้งเดียวเป็น **set root** คือ Merkle root (SHA-256) ของการขยายแบบ
low-degree ของสี่คอลัมน์ หนึ่งแถวต่อผู้ตรวจสอบหนึ่งราย เรียงตามที่อยู่ consensus แล้วเติมแถวศูนย์จนได้ N แถว
(กำลังของสองที่ ≥ n + 1 และอย่างน้อย 8)

- `A` ที่อยู่, `K` ไดเจสต์ของกุญแจโหวต ML-DSA-44 (SHA-256 ตัดเหลือ 31 ไบต์ แยกโดเมน; 0 = ไม่มีกุญแจ),
  `Z` = 1 ถ้าผู้ตรวจสอบไม่มีกุญแจโหวต, `P` พลังโหวต (< 2^64)

ใครก็ตามที่มีรายชื่อผู้ตรวจสอบ คำนวณรากนี้ซ้ำได้ตรงทุกบิต (`buildSet`) และเพราะชุดผู้ตรวจสอบถูกผูกมัดในรูปเดียวกับ trace
("คอลัมน์ที่เตรียมไว้ล่วงหน้า") จึงไม่ต้องคำนวณแฮชใดๆ ภายใน STARK เลย

**หลักฐานของบล็อก** ผูกมัด trace ของพยาน (หนึ่งแถวต่อผู้ตรวจสอบ):

- `B` บิตแมปผู้ลงนาม, `G` ไดเจสต์ของลายเซ็น ML-DSA ของผู้ลงนาม (0 ถ้าไม่ได้ลงนาม) ซึ่งก็คือ **การผูกมัดใบรับรอง**
  และผลรวมสะสม `CS` (พลังที่ลงนาม), `CT` (พลังทั้งหมด), `CU` (พลังที่ไม่มีกุญแจ), `CC` (จำนวนผู้ลงนาม)

เงื่อนไขทุกแถว: `B(B−1)=0`, `(1−B)·G=0`, `B·Z=0` (ผู้ไม่มีกุญแจลงนามไม่ได้), `Z(Z−1)=0`, `Z·K=0`
การเปลี่ยนแถว: `CS'=CS+B·P`, `CT'=CT+P`, `CU'=CU+Z·P`, `CC'=CC+B` เงื่อนไขขอบ: ผลรวมทุกตัวเป็น 0 ที่แถวแรก
และที่แถวสุดท้าย (แถวเติม) `CS=S, CT=T, CU=U, CC=C` และ `P=0` เนื่องจาก `P < 2^64` และ `n < 2^20` ผลรวมจึงไม่มีทางวนรอบฟิลด์
252 บิต ดังนั้นตัวเลขสาธารณะ **S, T, U, C เท่ากับ** พลังที่ลงนาม พลังทั้งหมด พลังที่ไม่มีกุญแจ และจำนวนผู้ลงนาม
**ของชุดที่ปักหมุดไว้** ตามบิตแมปที่ผูกมัดไว้ **ทุกประการ** จากนั้นตัวตรวจใช้กฎเดียวกับเชน (`zetaphy_pqcert.go`):
**3·S > 2·T − 3·U** (`ok`) และรายงาน `pqMajority` (3·S > 2·T คือเกิน 2/3 ของพลังทั้งหมด)

ข้อความที่พิสูจน์ (chain id, ความสูง, แฮชบล็อก ซึ่งเป็นไบต์เดียวกับที่ผู้ตรวจสอบลงนาม `voteMessage`) และ set root
ถูกใส่เข้า transcript ของ Fiat–Shamir เป็นอย่างแรก หลักฐานจึงย้ายไปใช้กับบล็อก เชน หรือชุดผู้ตรวจสอบอื่นไม่ได้

**ความถูกต้องของลายเซ็น** คือการที่ `G` แต่ละค่าเป็นไดเจสต์ของลายเซ็น ML-DSA-44 ที่ *ถูกต้อง* ด้วยกุญแจของแถวนั้น
ในขั้น A ยังไม่ได้พิสูจน์ภายใน STARK หลักฐานแต่ละชิ้นจึงระบุโหมดหนึ่งในสามแบบ และตัวตรวจกำหนดระดับขั้นต่ำได้

| โหมด | ไคลเอนต์ตรวจอะไร | ความแน่นหนาของลายเซ็น |
|---|---|---|
| `all` | เปิดเผยลายเซ็นและกุญแจของผู้ลงนามทุกราย แต่ละอันผูกกับ trace ด้วยการเปิดแบบ DEEP ที่แถว w^i (B=1, G=digest(sig), K=digest(pk), P); จำนวนต้องเท่ากับ C; ตรวจลายเซ็นทุกอันด้วย ML-DSA-44 | ครบถ้วน |
| `sample` | หลังผูกมัด trace แล้ว Fiat–Shamir สุ่มจุด r ∈ [0, S) จำนวน k จุดแบบถ่วงตามพลัง แต่ละจุดต้องตกในแถวที่เปิดเผย (CS_i ≤ r < CS_{i+1} เปิดจาก trace) แล้วตรวจลายเซ็นของแถวนั้น | k · log2(3S / (2T − 3U)) บิต |
| `none` | ไม่ตรวจลายเซ็น: **เชื่อ** ผู้สร้างหลักฐานเรื่องความถูกต้องของ ML-DSA (พิสูจน์เฉพาะการนับพลัง) | 0 บิต (ถูกปฏิเสธ เว้นแต่ตั้ง `minSigBits: 0`) |

ความแน่นหนาของการสุ่ม: ถ้าผู้ลงนามจริงมีพลังรวม W ≤ (2T−3U)/3 (กฎไม่ผ่านจริง) แต่หลักฐานอ้างว่าเป็น S
แต่ละจุดสุ่มจะตกแถวปลอมด้วยความน่าจะเป็น ≥ 1 − (2T−3U)/(3S) ทั้ง k จุดจะรอดด้วยความน่าจะเป็น ≤ ((2T−3U)/(3S))^k
ถ้าแทบทุกคนลงนาม จะได้ log2(1.5) = 0.585 บิตต่อจุด: **ต้องสุ่ม 219 จุดเพื่อให้ได้ 128 บิต** ไม่ขึ้นกับ n

### ยุค: ส่งต่อชุดผู้ตรวจสอบเป็นทอดๆ

ไคลเอนต์เริ่มจาก **ชุดเริ่มต้น (genesis) ที่ปักหมุดไว้** `{ root, logN, logBlowup }` จะขยับจากยุค e ไป e+1 ได้ต้องมี
**หลักฐานการส่งต่อ (handoff)** ซึ่งเป็น STARK แบบเดียวกันบนชุดของยุค e สำหรับข้อความ
`"zetaphy/pq-setroot\0" ‖ chain id ‖ "\0" ‖ uint64(e+1) ‖ root(e+1) ‖ logN ‖ logBlowup` โดยต้องมีผู้ลงนามที่มี
**พลังเกิน 2/3 ของพลังทั้งหมด** ของยุค e (ไคลเอนต์บังคับ `pqMajority` ไม่ใช่กฎที่หักพลังผู้ไม่มีกุญแจ) ต้องส่งต่อตามลำดับ
และหลักฐานบล็อกของชุดที่ไคลเอนต์ยังไปไม่ถึงจะไม่ผ่าน (รากไม่ตรง) ทดสอบไว้ใน `epoch chain`
(genesis → handoff → บล็อก; handoff ที่ชุดใหม่ลงนามเอง, พลังไม่ถึง 2/3, ผิดประเภท หรือข้ามยุค ถูกปฏิเสธทั้งหมด)

## 2. สิ่งที่ต้องเชื่อ (ขั้น A)

1. **หมุด genesis** (32 ไบต์ กับจำนวนเต็มเล็กๆ สองตัว) ที่ได้มาจากช่องทางอื่น เช่น ฝังมากับแอป หรือเทียบจากหลายแหล่ง
   ทุกอย่างที่เหลือตามมาจากหมุดนี้
2. **ความถูกต้องของ ML-DSA ในโหมด `none`** และในโหมด `sample` เชื่อได้เท่าจำนวนบิตที่ระบุ (ค่าเริ่มต้นขั้นต่ำ 128)
3. **SHA-256**: ทนการชน (สำหรับ Merkle; `K`/`G` ตัดเหลือ 248 บิต จึงทนการชนได้ 124 บิต) และทำตัวเหมือน random oracle (Fiat–Shamir)
4. **บนเชนยังไม่มีลายเซ็น handoff** ปัจจุบันผู้ตรวจสอบลงนามเฉพาะแฮชบล็อก ต้องแก้เชนให้ vote extension ที่รอยต่อยุค
   มีลายเซ็น ML-DSA บน set root ของยุคถัดไปด้วย (`handoffMessage`) ตอนนี้ชุดทดสอบและเดโมสร้างลายเซ็นนี้ด้วยกุญแจทดสอบ
   ระหว่างนี้ ถ้าจะใช้งานจริงต้องปักหมุดชุดปัจจุบัน แล้วปักหมุดใหม่เองเมื่อผู้ตรวจสอบหรือกุญแจเปลี่ยน (แบบ `pqcert.js --pin`)
5. เหมือนไลต์ไคลเอนต์ทั่วไป: ผู้ตรวจสอบที่มีพลังถึงเกณฑ์ซื่อตรงเรื่อง *สิ่งที่ลงนาม* (ไม่ได้พิสูจน์ว่าสถานะถูกต้อง)
   และผู้สร้างหลักฐานถูกเชื่อ **เฉพาะเรื่องความพร้อมให้บริการ** (ผู้สร้างที่ไม่ซื่อทำได้แค่ไม่ส่งหลักฐาน ปลอมไม่ได้)

ไม่ต้องเชื่อ: โหนด RPC, ผู้สร้างหลักฐาน, ช่องทางส่งหลักฐาน โหนดที่โกหกจะได้หลักฐานที่ไม่ผ่าน (รากไม่ตรง การเปิดไม่ตรง
หรือลายเซ็นผิด) ชุดทดสอบใช้ `collectFromNode` กับใบรับรองจริงจาก devnet ที่เชน Go สร้าง (`test/fixtures/pqcert-devnet.json`)
มาสร้างและตรวจหลักฐานจริง

## 3. ระดับความปลอดภัย

พารามิเตอร์เริ่มต้น: blowup 16 (`logBlowup` 4), **28 queries, grinding 16 บิต**, พหุนามสุดท้ายดีกรี < 8,
ฟิลด์ขนาดราว 2^251 (ไม่ต้องใช้ฟิลด์ขยาย ความผิดพลาดของ challenge ราว 2^−230)

| | บิต | สูตร |
|---|---|---|
| STARK แบบคาดการณ์ (แบบ ethSTARK) | **128** | queries · log2(blowup) + grinding = 28·4 + 16 |
| STARK แบบพิสูจน์ได้ (Johnson bound) | **72** | queries · log2(blowup)/2 + grinding |
| ลายเซ็น โหมด `all` | ครบถ้วน | ตรวจทุกลายเซ็น |
| ลายเซ็น โหมด `sample` | ≥ 128 (ปรับได้) | k · log2(3S/(2T−3U)) |
| ชุดพารามิเตอร์เสริมทนควอนตัม `{ queries: 60 }` | 256 คาดการณ์ / 136 พิสูจน์ได้ | +38 KB ที่ n = 100 (82 KB) ตรวจ 63 ms |

ตัวตรวจปฏิเสธหลักฐานที่ต่ำกว่า `minStarkBits` (ค่าเริ่มต้น 100 แบบคาดการณ์) และ `minSigBits` (ค่าเริ่มต้น 128)
สำหรับผู้โจมตีที่มีคอมพิวเตอร์ควอนตัม SHA-256 ยังทนการหา preimage ได้ราว 128 บิต แต่การค้นหาแบบควอนตัมทั่วไปบน transcript
ของ Fiat–Shamir อาจลดส่วน queries ลงได้ถึงราวรากที่สอง ถ้ามองแบบระมัดระวัง ค่าเริ่มต้นจึงเหลือราว 64 บิตสำหรับส่วน STARK
ถ้าจะใช้เกินระดับต้นแบบ ให้ใช้ชุด 60 queries (ราว 128 บิตตามมุมมองนั้น)

| 1000 | none | 73.2 KB | 73.2 KB | 3.7 s | 59 ms | – | เชื่อผู้สร้าง |

ทำซ้ำได้ด้วย `node zetaphy-network/scripts/starklc-bench.js 4 21 100` และ
`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers node zetaphy-explorer/scripts/starklc-browser-bench.js`
(ขนาดต่างกันไม่กี่ร้อยไบต์ในแต่ละรอบ เพราะการลงนาม ML-DSA มีการสุ่ม) แถว n = 1000 วัดครั้งเดียวด้วยโค้ดชุดเดียวกัน

อ่านผลอย่างตรงไปตรงมา:

- **ส่วน STARK เล็กและแทบไม่โตตาม n**: 22 → 44 → 73 KB และ 10–60 ms จาก n = 4 ถึง 1000 และตัดการเชื่อโหนด RPC
  และไฟล์หมุดกุญแจออกไป (ปักหมุดแค่ 32 ไบต์ และชุดผู้ตรวจสอบเปลี่ยนได้ผ่าน handoff)
- **ขั้น A ยังไม่ได้ลดขนาดข้อมูลลายเซ็นเมื่อต้องตรวจครบ** โหมด `all` ต้องแนบทั้งลายเซ็น *และกุญแจ* (เพราะไคลเอนต์ไม่ได้เก็บกุญแจแล้ว)
  จึงใหญ่กว่า "direct" ที่ปักหมุดกุญแจไว้ ส่วน `sample` คุ้มก็ต่อเมื่อ n มากกว่า 219 มาก (n = 1000: 843 KB เทียบกับ 2.4 MB)
  ถ้าจะได้หลักฐานเล็ก *และ* ตรวจลายเซ็นครบ ต้องรอขั้น B
- เวลาสร้างหลักฐาน (JS BigInt เธรดเดียว) พอสำหรับต้นแบบ ตัวสร้างจริงที่เขียนด้วย Rust จะเร็วขึ้น 100–1000 เท่า

## 5. ขั้น B (ออกแบบ): ตรวจ ML-DSA-44 ภายในหลักฐาน แล้วทำ recursion

เป้าหมาย: ได้ความแน่นหนาระดับโหมด `all` ด้วยขนาดระดับโหมด `none` (หลักสิบ KB และไม่โตตาม n) ไคลเอนต์ตรวจแค่ STARK อย่างเดียว

**ต้นทุนของการตรวจ ML-DSA-44 หนึ่งครั้งในรูป AIR** (FIPS 204, k = l = 4, n = 256, q = 8,380,417):

- ต่อ **ผู้ตรวจสอบ** (ครั้งเดียวต่อยุค เตรียมไว้ล่วงหน้าเหมือนคอลัมน์ของชุด): เมทริกซ์ Â ที่ขยายจาก `ρ` ในรูป NTT
  (16 × 256 สัมประสิทธิ์), t1·2^d ในรูป NTT (4 × 256), tr = H(pk) ส่วนนี้จึงไม่อยู่ในวงจรของแต่ละบล็อก
- ต่อ **ลายเซ็น**: ถอดรหัส z (1,024 สัมประสิทธิ์ ตรวจช่วง ‖z‖∞ < γ1 − β), hint h (มีเลข 1 ไม่เกิน 80 ตัว),
  c = SampleInBall(c̃) (ราว 1–2 รอบ Keccak-f), μ = H(tr ‖ M') (ราว 1–2 รอบ), NTT ของ z (4 พหุนาม) และ c (1),
  คูณทีละตำแหน่ง 16 × 256 + 4 × 256 ครั้ง, inverse NTT 4 ครั้ง, UseHint, w1Encode (768 ไบต์) และ
  c̃' = H(μ ‖ w1) (ราว 6 รอบ) แล้วเทียบกับ c̃
  รวมราว **Keccak-f[1600] 9–10 รอบ**, **butterfly ของ NTT ราว 9 × 1,024 ครั้ง + การคูณ mod q ราว 5,000 ครั้ง** และตรวจช่วงราว 2,000 ครั้ง
- ในฟิลด์ 31 บิต (BabyBear/M31) การคูณ mod q ต้องมีผลหารและ lookup ตรวจช่วง ในฟิลด์ Goldilocks (64 บิต) ผลคูณใส่ได้ตรงๆ
  Keccak-f ใช้ราว 24 แถว × 2,600 คอลัมน์ (Plonky3 `keccak-air`) ≈ 60 k เซลล์ ส่วนเลขคณิตราว 100–150 k เซลล์
  **รวมราว 0.7–1 ล้านเซลล์ต่อลายเซ็น** n = 100 → ราว 10^8 เซลล์
- ประมาณการด้วยตัวสร้างหลักฐานระดับใช้งานจริง (Plonky3 หรือ Stwo บนโน้ตบุ๊กหลายคอร์ใช้ SIMD): **สร้างหลักฐาน 100 ลายเซ็นราว 2–10 วินาที**
  หลักฐานราว 100–200 KB ก่อน recursion ตรวจราว 10–50 ms ส่วนตัวสร้าง JS BigInt ในรีโปนี้รับ 10^8 เซลล์ไม่ไหว
  (เป็นชั่วโมงและใช้หน่วยความจำหลาย GB) ขั้น B จึงเป็นงานออกแบบในที่นี้
- คอลัมน์พยาน `G` จะกลายเป็นตัวลายเซ็นเอง (ผูกมัดไว้) และเงื่อนไข "B = 1 ⇒ Verify(pk_i, M, sig_i)" มาแทนการเปิดเผยลายเซ็น
  ส่วนข้อความที่พิสูจน์และการผูกมัดชุดผู้ตรวจสอบคงเดิม

**Recursion** (ตัวตรวจ STARK อยู่ภายใน STARK แบบ Plonky3/Stwo/RISC Zero):

1. รวมการตรวจลายเซ็น n อันเป็นหลักฐานเดียวต่อบล็อก (หรือแบ่งพิสูจน์ขนานแล้วรวม) ขนาดหลักฐานจะไม่ขึ้นกับ n
   (ราว 50–100 KB ที่ 128 บิต ขึ้นกับแฮชและฟิลด์)
2. **ต่อ handoff เป็นสาย (IVC):** หลักฐานเดียวว่า "genesis root → … → root(e)" อัปเดตทุกยุค ไคลเอนต์ใหม่โหลดหลักฐานเดียว
   แทนที่จะโหลดทีละยุคตั้งแต่ genesis
3. ภายใน recursion อาจใช้แฮชเชิงเลขคณิต (Poseidon2) เพื่อความเร็ว ยังเป็นแบบแฮชและทนควอนตัม แต่ผ่านการศึกษามาน้อยกว่า
   SHA-256/Keccak ชั้นนอกสุดจึงควรใช้ SHA-256 หรือ Keccak ต่อไป

## 6. แผนสู่สะพานข้ามเชนที่ไม่ต้องเชื่อใคร

1. **เชน:** ลงนาม `handoffMessage` ใน vote extension ที่รอยต่อยุค (และคงกฎหมุนกุญแจ: ใช้กุญแจที่ใช้ได้ที่ความสูง H)
   เผยแพร่รายชื่อชุดผู้ตรวจสอบของแต่ละยุค เพื่อให้ทุกคนคำนวณรากซ้ำได้
2. **บริการสร้างหลักฐาน:** `collectFromNode` → `proveBlock` / `proveHandoff` แล้วให้บริการไฟล์ `.bin`
   (หน้า explorer ตรวจไฟล์เหล่านี้ได้แล้ว และ PWA เก็บหมุดปัจจุบันไว้ได้)
3. **ตัวสร้างหลักฐานขั้น B** (Rust, Plonky3/Stwo) ที่ตรวจ ML-DSA-44 ภายในวงจร แล้วทำ recursion โดยเบราว์เซอร์ยังเป็นผู้ตรวจเหมือนเดิม
4. **สัญญาตัวตรวจบน Ethereum** สำหรับสะพาน ZETAPHY → Ethereum: เก็บ set root ที่ปักหมุด รับ handoff และหลักฐานบล็อก
   แล้วตรวจหลักฐาน Merkle/IAVL เทียบกับ header ที่ได้รับการรับรอง (`app_hash` ผ่าน Merkle tree ของ header ซึ่งใช้ SHA-256)

**ประมาณค่าแก๊สของตัวตรวจบน EVM** (n = 100 พารามิเตอร์เริ่มต้น หลักฐานที่วัดได้ 43.5 KB มีไบต์ที่ไม่เป็นศูนย์ 39.4 k;
แฮชใบราว 167 ครั้ง + โหนดภายในราว 750 ครั้ง; คูณในฟิลด์ราว 5 k ครั้ง และหาอินเวอร์สแบบรวมครั้งเดียว):

| รายการ | แก๊ส |
|---|---|
| calldata ที่ 16/4 แก๊สต่อไบต์ | ≈ 0.65 M |
| SHA-256 precompile (ราว 920 ครั้ง × 300–400) | ≈ 0.3 M |
| เลขคณิตในฟิลด์ (`mulmod` ใช้ได้ตรงๆ เพราะ p < 2^256), ถอดรหัส, หน่วยความจำ | ≈ 0.3–0.5 M |
| **รวม** | **≈ 1.3–1.5 M** (ขั้นต่ำ calldata ตาม EIP-7623: ≈ 1.6 M) |

ดังนั้น **ราว 1.5–2 M แก๊สต่อหลักฐานบล็อกหรือ handoff หนึ่งชิ้น** (ราว 2.5–3 M สำหรับ n = 1000 ขนาด 73 KB)
ถ้าเปลี่ยนเป็น Keccak (ใช้ opcode แทนการเรียก precompile) จะประหยัดได้ราว 0.2 M หลักฐานขั้น B ที่ขนาดใกล้กัน
(50–100 KB หลัง recursion) จะอยู่ในช่วง **≈ 2–4 M** เช่นกัน การตรวจลายเซ็น ML-DSA-44 ตรงๆ ใน Solidity กินแก๊สหลายล้าน
*ต่อลายเซ็น* (จากโค้ดที่เผยแพร่สาธารณะ; มีข้อเสนอ precompile สำหรับ ML-DSA แล้ว) การตรวจผู้ลงนาม 67+ รายตรงๆ จึงทำไม่ได้
STARK คือทางไปสู่สะพานที่ทนควอนตัม การห่อ STARK ด้วย SNARK แบบ pairing (ราว 250–300 k แก๊ส) ถูกกว่า แต่ **ไม่** ทนควอนตัม
จึงไม่ใช่เป้าหมาย

สะพานขั้น A ที่ใช้โหมด `none` **ยังต้องเชื่อใจ** ผู้สร้างหลักฐานเรื่องลายเซ็น ทางเลือกระหว่างนี้คือสะพานแบบ optimistic:
รับหลักฐาน `none` หลังช่วงคัดค้าน ซึ่งใครก็ได้ส่งลายเซ็นในใบรับรองของแถวที่ผูกมัดไว้ซึ่งตรวจ ML-DSA ไม่ผ่านมาคัดค้านได้
(แพง แต่จ่ายเฉพาะตอนมีข้อพิพาท)

## 7. ข้อจำกัดของต้นแบบ

- เลขคณิตฟิลด์ด้วย JS BigInt และฟิลด์ 252 บิต: ตรวจสอบโค้ดง่าย แต่สร้างหลักฐานช้า ไม่มี zero-knowledge (ไม่จำเป็น เพราะข้อมูลเป็นสาธารณะทั้งหมด)
- ลายเซ็น handoff สร้างโดยชุดทดสอบและเดโมเท่านั้น (รอแก้เชน) หน้าเดโมใช้กุญแจทดสอบ
- รูปแบบหลักฐาน v1 ยังไม่ตายตัว พารามิเตอร์ติดมากับหลักฐาน และถูกตรวจเทียบกับหมุดและค่าขั้นต่ำ
- ยังไม่ผ่านการตรวจสอบความปลอดภัย; ไม่มีประเด็นเวลาคงที่ (ตัวตรวจไม่มีความลับ)
