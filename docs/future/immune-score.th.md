## SS5: วัคซีนจากช่องโหว่ที่ยืนยันแล้ว

### อะไรนับว่า "ยืนยันแล้ว"

`ImmuneVaccines` ไม่เชื่อสิ่งที่ผู้เรียกบอก ผู้เรียกทำได้แค่ชี้ไปที่ข้อเท็จจริงบนเชนหนึ่งในสามอย่างนี้:

| ฟังก์ชัน | ข้อเท็จจริงที่อ่าน |
|---|---|
| `vaccinateFromFinding(findingId)` | ข้อค้นพบใน `AuditNetwork` ที่คณะกรรมการตัดสินว่า**จริง** ระดับ**สูงหรือวิกฤต** และไม่มีการอุทธรณ์ค้างอยู่ ใช้ได้ทั้งข้อค้นพบระหว่างการแข่งขันและหลังออกใบรับรอง |
| `vaccinateFromRevocation(chainId, target)` | ใบรับรองของ `AuditCertificate` ที่ถูกเพิกถอน หรือ code hash ของมันถูกเพิกถอน |
| `vaccinateFromClaim(claimId, target)` | เคลมของ `HackInsurance` ที่**อนุมัติ**หรือ**จ่ายแล้ว** ซึ่ง target key ของกรมธรรม์คือ `addressKey(chainid, target)` HackInsurance คุ้มครองเฉพาะเชนนี้ และ code hash คือโค้ดของ target ณ ตอนนั้น |

ทั้งสามแบบชี้ไปที่โค้ดที่มีช่องโหว่ชุดเดียวกัน id ของวัคซีนคือ `keccak256("zetaphy.vaccine.v1", chainId, target, codeHash)`
การยืนยันซ้ำของโค้ดเดียวกันจึงเพิ่มแหล่งยืนยันให้วัคซีนเดิม (`sources` เป็นบิตมาสก์)

### วัคซีน

ถ้าโค้ดอยู่บน ZETAPHY และยังไม่เปลี่ยน สัญญาจะสกัดรูปแบบบนเชนเองจากตัวโค้ด
ถ้าไม่ใช่ ใครก็เรียก `derivePattern(id, code)` พร้อม runtime code ได้ โดยโค้ดต้องแฮชได้ตรงกับ code hash ของวัคซีน รูปแบบประกอบด้วย:

- **code hash**: `keccak256` ของ runtime code ใช้จับโค้ดที่ตรงกันทุกไบต์
- **body hash**: `keccak256` ของโค้ดที่ตัด CBOR metadata ออก (แบบ `codeLengthWithoutMetadata` ของ Neuro) ใช้จับซอร์สเดิมที่คอมไพล์ใหม่
- **selector เฉพาะตัว**: ทุก `PUSH4 <sel> EQ` (หรือ `PUSH4 <sel> DUP2 EQ`) ใน dispatcher โดยตัด baseline ของ ERC-20 ที่สุจริตของ Neuro ออก
  ได้ชุดเดียวกับที่ตัวสแกนของ Neuro (`zetaphy-neuro/src/bytecode.js`) และ `src/immune/vaccines.js signatureOf(code).selectors` หาได้
  การทดสอบเทียบกันบนสัญญาที่คอมไพล์จริง และค่าคงที่ baseline ถูกตรวจเทียบกับ `threat-signatures.generated.js`

### บน ZETAPHY: พักไว้รอตรวจสอบและแจ้งเจ้าของ

ใครก็เรียก `checkMatch(id, contract)` ได้ สัญญาจะตรวจการตรงกันซ้ำบนเชนเอง:

| ความแรง | กฎ | ผล |
|---|---|---|
| 3 ตรงทุกไบต์ | EXTCODEHASH เดียวกัน | **พักไว้รอตรวจสอบ** และแจ้งเจ้าของ |
| 2 body | โค้ดเดียวกันเมื่อตัด metadata ออก | **พักไว้รอตรวจสอบ** และแจ้งเจ้าของ |
| 1 selector | มี selector เฉพาะตัวของวัคซีนอย่างน้อย 80% (วัคซีนต้องมีอย่างน้อย 3 ตัว) | **ผู้ต้องสงสัย**: บันทึกไว้และแจ้งเจ้าของ แต่**ไม่พัก** (คะแนนลด 150) |

**การพัก**คือการเรียก `ThreatRegistry.holdForReview(addressKey(chainid, contract), vaccine, reviewWindow)` เป็นการเพิ่มความสามารถโดยไม่แก้ของเดิม และมีขอบเขตดังนี้:

- เรียกได้เฉพาะที่อยู่ `vaccines` ที่ governance (timelock) ตั้งไว้ใน ThreatRegistry
- พักได้นานสุด `MAX_REVIEW_HOLD` (14 วัน) ส่วน `reviewWindow` ใน ImmuneVaccines จำกัดไว้ที่ 1–14 วัน ค่าเริ่มต้น 7 วัน
- **การพักไม่ใช่การตั้งธง**:
  - `is*Held` จะรายงานการพักด้วย `Reason.Other` ทำให้ BridgeAirlock และ BridgeGuard พักการบริดจ์ของฝ่ายนั้นไว้ (ย้อนกลับได้)
  - `is*Flagged` และ `is*Enforced` ไม่เปลี่ยน การตั้งธงยังทำได้เฉพาะ quorum ของรันเนอร์เหมือนเดิม
- **คีย์ที่ได้รับการคุ้มครองจะไม่ถูกพักเลย** และการคุ้มครองคีย์จะยกเลิกการพักของคีย์นั้น
- **พักได้ครั้งเดียวต่อ (สัญญา, วัคซีน)** เมื่อหมดช่วงเวลาหรือถูกปล่อยแล้ว ไม่มีใครต่ออายุได้ หลังจากนั้นมีแต่ธงจาก quorum ของรันเนอร์ที่พักสัญญานั้นได้อีก
- การพักสิ้นสุดเมื่อเกิดอย่างใดอย่างหนึ่ง:
  - หมดช่วงเวลา
  - governance หรือ guardian ของ ThreatRegistry ตรวจแล้วเรียก `releaseReview`
  - คีย์ได้รับการคุ้มครอง
  - วัคซีนถูกปลดระวางแล้วมีคนเรียก `release`

**การแจ้งเจ้าของ**: ทุกการตรงกันจะปล่อย event `OwnerNotified(owner, contract, vaccine, strength)`
โดย owner คือค่าจาก `owner()` ของสัญญา (อ่านแบบจำกัดแก๊ส) หรือศูนย์ถ้าไม่มี
วอลเล็ต ฮับ และระบบ index ติดตาม event นี้ได้ เจ้าของตอบกลับได้ผ่านสิทธิ์โต้แย้งของ ThreatRegistry

**การปลดระวาง**: ใครก็เรียก `retire(id)` ได้ ฟังก์ชันจะตรวจทุกแหล่งยืนยันซ้ำ แล้วตัดแหล่งที่ไม่จริงแล้วออก ได้แก่
- ข้อค้นพบที่ถูกกลับคำตัดสินในการอุทธรณ์
- เคลมที่ถูกกลับคำตัดสิน

การอุทธรณ์ที่แค่**เปิดค้างอยู่**ไม่ตัดอะไรออก การยื่นอุทธรณ์จึงใช้ปลดการพักไม่ได้ ส่วนใบรับรองที่ถูกเพิกถอนแล้วถือเป็นที่สิ้นสุด
เมื่อไม่เหลือแหล่งยืนยัน วัคซีนจะถูกปลดระวาง และไม่นับเป็นประวัติช่องโหว่อีก จากนั้น `release(contract)` จะยกเลิกการพักที่วัคซีนนั้นตั้งไว้

### เชนอื่น: ใช้เส้นทางภูมิคุ้มกันเดิม

ไม่มีช่องทางข้ามเชนใหม่ ช่องโหว่ที่ยืนยันแล้วเข้าเครือข่ายภูมิคุ้มกันแบบเดียวกับข้อค้นพบอื่น:

1. `src/immune/confirmed.js confirmedReport({ record, id, code, vaccines })` สร้างรายงานสำหรับ detector ใหม่ชื่อ **`confirmed`** (`detectors.js confirmedVerdict`)
   เป็น verdict บริสุทธิ์ที่ตรวจบันทึกของ ImmuneVaccines กับโค้ดว่า:
   - บันทึกยังใช้งานอยู่
   - บันทึกระบุเชนและที่อยู่นี้
   - `keccak256(code)` ตรงกับ code hash ในบันทึก

   รายงานแนบวัคซีนนอกเชนฉบับเต็ม (`vaccines.js deriveVaccine`: แบบตรงทุกไบต์, fingerprint, ความคล้าย และ selector)
2. รันเนอร์ของ NeuroJobs รันซ้ำจากบันเดิลอย่างเดียว (`runnerVote`) และเห็นพ้องกัน จากนั้น `ImmuneRegistry.attest` ตั้งธงบัญชีของสัญญาที่โจมตี
   และ **code hash บนทุกเชน** พร้อม id ของวัคซีน
3. `ImmuneBroadcaster.broadcast` ส่งธงและ id วัคซีนไปยัง `ImmuneMirror` ทุกตัว ซึ่งตอบผ่าน `isCodeFlagged` และ `vaccineOf`
   sentinel บนทุกเชนโหลดวัคซีนแล้วสแกนสัญญาใหม่ โคลนที่คอมไพล์ใหม่หรือดัดแปลงจะถูก `clone` จับได้ และผ่านการเห็นพ้องแบบเดียวกัน

การทดสอบ `immune-vaccine.test.js` รันทั้งหมดนี้บนเชนในโปรเซส:
- เคลมประกันบน ZETAPHY กลายเป็นธงที่ NeuroJobs เห็นพ้อง และถูกส่งไปยังมิเรอร์บน B และ C พร้อมวัคซีน
- vault เดิมที่คอมไพล์ใหม่ด้วย metadata hash อื่น (code hash จึงต่างกัน) บน C ถูกวัคซีนนั้นจับได้
- โค้ดสุจริตไม่ถูกจับ

`findMatches(send, record, candidates)` ใน `confirmed.js` ใช้กฎเดียวกับสัญญาเพื่อเลือกสัญญาบน ZETAPHY ที่จะส่งไปให้ `checkMatch`
การทดสอบตรวจว่าฝั่ง JS กับสัญญาให้ความแรงตรงกันทุกกรณี

## S10 + SS7: คะแนนความปลอดภัย

### ใครโพสต์อะไร

**ไม่มีใครโพสต์คะแนน** `SecurityScore.breakdown(chainId, target)` คำนวณใหม่ทุกครั้งที่เรียก
จากสัญญาที่ถือข้อเท็จจริงซึ่งมีผู้รับผิดชอบอยู่แล้ว แหล่งข้อมูลกำหนดตายตัวตอนดีพลอย จะเป็นศูนย์ก็ได้ ไม่มี setter และไม่มีคีย์ผู้ดูแล:

| แหล่ง | อ่านอะไร | ใครเขียนที่นั่น |
|---|---|---|
| AuditCertificate | ใบรับรอง: ระดับ วันออก วันหมดอายุ การเพิกถอน และ code hash ที่ถูกเพิกถอน | `certify` (ผ่านทุกกฎการตรวจสอบ), `revokeFor` (ข้อค้นพบวิกฤต/สูงที่ตัดสินว่าจริง) |
| AuditNetwork | ข้อค้นพบล่าสุด 16 รายการของคำขอที่ได้ใบรับรอง ที่เปิดเผยแล้ว ยังไม่ตัดสิน ยื่นหลังออกใบรับรอง และอ้างระดับสูง/วิกฤต | ผู้ตรวจที่วางประกัน (commit-reveal) และคณะกรรมการตัดสิน |
| CircuitBreaker | ลงทะเบียนเฝ้าระวังหรือไม่ ถูกตัดอยู่ไหม เวลาเริ่มการตัดครั้งล่าสุด และพิสูจน์แล้วว่าตัดผิดหรือไม่ | governance ของโปรโตคอลเอง และรันเนอร์ที่วางประกันหรือ invariant |
| NeuroScore | `scoreOf(target)`: ระดับความเสี่ยงของโมเดลที่ใช้งานอยู่ | feeder ที่ governance แต่งตั้ง และโมเดลที่ timelock เปิดใช้ |
| ImmuneVaccines | `exploitsOf(chainId, target)`, `matchOf(target)` | เฉพาะช่องโหว่ที่ยืนยันแล้ว (ดูด้านบน) |
| ThreatRegistry | ตั้งธง บังคับใช้ พักรอตรวจสอบ | quorum ของรันเนอร์ที่วางประกัน และ ImmuneVaccines (พักได้อย่างเดียว) |
| ImmuneRegistry / ImmuneMirror | `isFlagged`, `isCodeFlagged` | การเห็นพ้องแบบ k-of-n ใน NeuroJobs |

`refresh(chainId, target)` (ใครก็เรียกได้) เก็บคะแนนและปล่อย `ScoreUpdated` ให้ระบบ index
ส่วน `cached` ใช้อ่านค่าที่เก็บไว้ สำหรับโปรโตคอลที่ยอมรับอายุของค่าได้ สัญญา DeFi ควรเรียก `score` แบบสด

### สูตร (ตายตัวในโค้ด)

| ส่วน | คะแนน |
|---|---|
| ใบรับรอง | ถ้ายังมีผล: Bronze 250, Silver 325, Gold 400 คูณ (½ + ½ × สัดส่วนอายุที่เหลือ) |
| Neuro | ทราบระดับ: ระดับ 0 ได้ 200, ระดับ 1 ได้ 150, ระดับ 2 ได้ 60, ระดับ 3 ได้ 0 / ไม่ทราบหรือเป็นเชนอื่น: 100 |

| ประวัติ | 250 − 125 ต่อช่องโหว่ที่ยืนยันใน 365 วันล่าสุด (ตั้งแต่ 2 ครั้งขึ้นไป: 0) |
| − ข้อค้นพบค้าง | 100 ต่อข้อค้นพบหลังออกใบรับรองที่เปิดเผยแล้ว ยังไม่ตัดสิน และอ้างระดับสูง/วิกฤต (สูงสุด 3 รายการ) |
| − เบรกเกอร์ | 300 ระหว่างถูกตัด / ถ้าไม่ได้ถูกตัดอยู่ หัก 100 เมื่อการตัดครั้งล่าสุดเริ่มภายใน 30 วัน (เว้นแต่พิสูจน์ว่าตัดผิด) |
| − ผู้ต้องสงสัย | 150 เมื่อสัญญามี selector ส่วนใหญ่ตรงกับวัคซีนที่ยังใช้งาน |

รวมสูงสุด 400 + 200 + 150 + 250 = 1000 จากนั้นใช้**เพดาน** (ค่าต่ำสุดชนะ):

| เพดาน | เมื่อ |
|---|---|
| 0 | ThreatRegistry บังคับใช้ธง หรือฟีดภูมิคุ้มกันระบุวิกฤต (4) |
| 100 | ThreatRegistry ตั้งธง / ฟีดระบุสูง (3) / ตรงกับวัคซีนที่ใช้งานแบบตรงทุกไบต์หรือแบบ body |
| 150 | มีช่องโหว่ที่ยืนยันภายใน 30 วัน |
| 200 | ใบรับรองหรือโค้ดที่รับรองถูกเพิกถอน |

ทุกการอ่านจำกัดแก๊สและดักข้อผิดพลาดไว้ แหล่งที่เสียจึง**ลดคะแนน**ลงเท่านั้น ไม่เคยทำให้โปรโตคอลค้าง
ในการทดสอบ การอ่านสดของสัญญาที่มีการเฝ้าระวังและมีคะแนน Neuro ใช้แก๊สต่ำกว่า 600k

### ตัวอย่างการใช้งาน: `ScoredCollateral`

ในรีโปนี้ไม่มีสัญญาปล่อยกู้ (DEX มีแค่ pair และ router) ตัวอย่างจึงเป็นตัวช่วยด้านหลักประกันที่ตลาดปล่อยกู้ vault หรือพูลใดก็เรียกใช้ได้:

- `collateralFactorBps(asset)` และ `maxBorrow(asset, value)` ใช้คะแนนสดผ่านขั้น (tier) ของ governance ค่าเริ่มต้นในการทดสอบคือ 400 → 40%, 600 → 60%, 800 → 75%
- `poolLimit(pool, baseLimit)` ปรับวงเงินของพูล vault หรือเส้นทางแบบเส้นตรง เป็น 0 เมื่อคะแนนไม่เกิน 300 และได้เต็มวงเงินที่ 1000

ขั้นเป็นของ governance (timelock) ภายในขอบเขตตายตัว:
- มีได้ไม่เกิน 4 ขั้น
- ตัวคูณแต่ละขั้นไม่เกิน 85%
- คะแนนขั้นต่ำต้องเพิ่มขึ้นเคร่งครัด และตัวคูณต้องไม่ลดลง
- **ขั้นต่ำสุดต้องมากกว่า 300**

ดังนั้นสิ่งที่ถูกตั้งธง ถูกพัก เพิ่งถูกโจมตี หรือถูกเพิกถอน (ทั้งหมดมีเพดานไม่เกิน 300) จะ**ไม่มีมูลค่าเป็นหลักประกันเลย** ไม่ว่า governance จะตั้งค่าอย่างไร
ใบรับรองที่ถูกเพิกถอน ช่องโหว่ที่ยืนยัน การตรงกับวัคซีน หรือธง จะเปลี่ยนตัวคูณได้ในบล็อกเดียวกัน

### ใน explorer

เมื่อตั้ง `securityScore` ใน `config.json` (หรือในหน้า Settings) หน้าที่อยู่และหน้าโทเคนของสัญญาจะแสดงป้าย เช่น "ความปลอดภัย 850/1000"
และต่อท้ายด้วย "· ถูกพักไว้รอตรวจสอบ" หรือ "· ถูกตั้งธง" เมื่อเกี่ยวข้อง คำอธิบายเมื่อชี้แสดงทุกส่วนของคะแนน
มีข้อความครบ 8 ภาษา (en, zh, es, ko, ja, ru, vi, th) ป้ายอ่าน `breakdown(77390, address)` ด้วย `eth_call` ครั้งเดียว และจำค่าไว้ตลอดการเข้าชม
ถ้าโหนดล่ม ป้ายจะไม่แสดงอะไร

## SS8: เครือข่ายตรวจสอบตรวจสอบตัวเอง

### สคริปต์ตรวจสอบตัวเอง

`test/audit-self.test.js` รันกระบวนการทั้งหมดบน ZETAPHY ในหน่วยความจำ (เชน 77390):

1. ดีพลอย AuditNetwork, AuditRunners, AuditJudges และ AuditCertificate
2. ยื่น**คำขอสี่รายการ แต่ละรายการระบุที่อยู่และ EXTCODEHASH ของสัญญานั้นเอง**
3. ผู้ตรวจที่วางประกันสามคนเข้าร่วมการแข่งขัน
4. รันเนอร์สามคน commit และ reveal ผลอัตโนมัติ ได้แก่ pipeline adapter บนไฟล์รายงาน fixture ที่คอมมิตไว้
   บวก**การสแกนเฉพาะโค้ดของ Neuro บนโค้ดที่ดีพลอยของแต่ละสัญญา** Neuro พบแค่ระดับ info/low ในทั้งสี่สัญญา จำนวนวิกฤต/สูงที่ค้างจึงเป็น 0
5. ปิดยอด แล้วออกใบรับรองให้ทุกสัญญา

จากนั้นการทดสอบเขียนบันทึก รันการตรวจของ CI บนบันทึกนั้น (ผ่าน) และแสดงว่าการตรวจจะล้มเหลวในกรณีต่อไปนี้:
- ใบรับรองหมดอายุ
- artifact เปลี่ยนไป
- มีข้อค้นพบวิกฤตที่จริงต่อ AuditJudges หลังออกใบรับรอง ทำให้ใบรับรองถูกเพิกถอน (การตรวจบนเชนล้มเหลว)

บนเทสต์เน็ต:

```
node scripts/audit-self.js plan   --rpc https://… [--source <commit>]   # พิมพ์คำสั่ง `zetaphy audit request` สี่คำสั่ง
# … การตรวจสอบดำเนินไปในเครือข่ายเหมือนโค้ดของใครก็ได้ …
node scripts/audit-self.js record --rpc https://…                       # เขียน deployments/audit-self-77390.json
node scripts/audit-self.js check  [--rpc https://…]                     # สิ่งที่ CI รัน
```

### การตรวจใน CI (ปิดอยู่จนกว่าจะมีบันทึก)

`.github/workflows/security.yml` รัน `node scripts/audit-self.js check` ในงาน zetaphy-network
ตราบใดที่ยังไม่มี `zetaphy-network/deployments/audit-self-77390.json` การตรวจจะพิมพ์ `OFF` และผ่าน
เมื่อมีบันทึกแล้ว การตรวจจะ**ล้มเหลว** เว้นแต่ทั้งสี่สัญญาผ่านทุกข้อนี้:
- มีใบรับรองที่ออกแล้ว ไม่ถูกเพิกถอน และไม่หมดอายุ สำหรับ code hash ที่บันทึกไว้
- artifact ที่คอมมิตคือตัวที่ผ่านการตรวจ ถ้าซอร์สเปลี่ยน artifact จะเปลี่ยน และต้องยื่นคำขอใหม่

ถ้าใส่ `--rpc` จะตรวจบนเชนเพิ่มด้วยว่าโค้ดที่ดีพลอยยังเป็นตัวที่บันทึกไว้ และ `AuditCertificate.isCertified` เป็นจริง

### คุณสมบัติเชิงรูปนัย (invariant)

`zetaphy-network/audit/invariants/AuditNetwork.inv.t.sol` ใช้สไตล์ Foundry เดียวกับรีโป handler สุ่มลำดับการกระทำต่อไปนี้:
- คำขอ
- การ commit และ reveal ของผู้ตรวจ
- รันเนอร์สามที่นั่ง (ผลสะอาดหรือวิกฤต)
- การโหวตของกรรมการ การปฏิเสธรายงาน การอุทธรณ์ และการตัดสินของ governance
- การปิดยอดและการออกใบรับรอง
- ข้อค้นพบหลังออกใบรับรอง
- การเคลมและการถอนเงินทุกแบบ

handler ยังมีขั้นตอนแบบทั้งคำขอและทั้งข้อค้นพบ เพื่อให้การรันแบบสุ่มไปถึงการออกใบรับรองและการเพิกถอน
ตัวตรวจ (probe) ยืนยันแล้วว่าการรันแบบสุ่มไปถึงทั้งสองอย่าง และ `test_handlerReachesCertificatesAndRevocations` ตรึงพฤติกรรมนี้ไว้

| คุณสมบัติ | invariant |
|---|---|
| ไม่มีการจ่ายเกินเงินที่ฝากไว้: คำขอไม่จ่ายเกินพูลของตัวเอง ไม่มีใครถอนเกินที่จ่ายเข้า และยอดคงเหลือ = เงินเข้า − เงินออก | `invariant_noPayoutExceedsDeposits` |
| ยอดค้างจ่ายทุกยอด เงินประกันของผู้ตรวจและกรรมการ และเงินที่ถูกหักไว้ มียอดคงเหลือของสัญญารองรับ | `invariant_creditsBacked` |
| ใบรับรองไม่ออกขณะที่มีข้อค้นพบวิกฤตค้างอยู่: ข้อค้นพบวิกฤต/สูงที่จริงเป็นศูนย์ ไม่มีข้อที่ยังไม่ตัดสิน ไม่มีการอุทธรณ์ค้าง และชั้นอัตโนมัติเห็นพ้องโดยมีวิกฤต/สูงเป็นศูนย์ | `invariant_noCertificateWithOpenCritical` |
| ใบรับรองที่โดนข้อค้นพบวิกฤต/สูงที่จริงหลังออกใบรับรอง จะไม่กลับมามีผลอีก | `invariant_revokedStaysRevoked` |

วิธีรัน: `cd zetaphy-network && forge test --match-path audit/invariants/AuditNetwork.inv.t.sol`
(ใช้ `FOUNDRY_PROFILE=deep` สำหรับ 1000 × 100) ขั้นตอน invariant ของ pipeline (`audit/tools/invariants.sh`) จะรันชุดนี้ไปพร้อมชุดอื่น

## การดีพลอย (เทสต์เน็ต ทุกขั้นผ่าน timelock)

1. ดีพลอย `ImmuneVaccines(AuditNetwork, AuditCertificate, HackInsurance, ThreatRegistry, timelock)`
2. ให้ timelock เรียก `ThreatRegistry.setVaccines(ImmuneVaccines)` ก่อนหน้านั้น `checkMatch` ที่ตรงแบบทุกไบต์หรือแบบ body จะ revert (`NotVaccines`)
   ทำให้เห็นการตั้งค่าที่ผิดได้ชัด
3. ดีพลอย `SecurityScore(AuditCertificate, AuditNetwork, CircuitBreaker, NeuroScore, ImmuneVaccines, ThreatRegistry, ImmuneRegistry)`
   (แหล่งใดเป็นศูนย์ก็ได้) และจะดีพลอย `ScoredCollateral(SecurityScore, timelock, tiers)` ด้วยก็ได้
4. ตั้งค่า `securityScore` ของ explorer

ไม่มีสัญญาใดในส่วนนี้มีคีย์เจ้าของ สิ่งที่ governance ทำได้มีเท่านี้:
- เปลี่ยน `reviewWindow` (1–14 วัน)
- ตั้งที่อยู่ vaccines ใน ThreatRegistry
- เปลี่ยนขั้นของหลักประกัน (ภายในขอบเขตข้างต้น)

## ข้อจำกัด (อะไรยังเป็นต้นแบบ)

- **ยังไม่ได้ดีพลอย** ทั้งหมดรันบน EVM ในโปรเซส การเห็นพ้องของ NeuroJobs การกระจาย และมิเรอร์ ใช้ Hyperlane จำลองของเครือข่ายภูมิคุ้มกัน
- **การตรงกันด้วย selector เป็นการประมาณ** จึงไม่พักอะไร มีผลแค่ลดคะแนนและแจ้งเจ้าของ ส่วนการตรงแบบทุกไบต์และแบบ body ไม่ใช่การประมาณ
- **เวอร์ชันที่แก้แล้วของสัญญาที่ถูกโจมตี** มักยังมี selector เดิม จึงแสดงเป็น*ผู้ต้องสงสัย* (−150) จนกว่าจะได้ใบรับรองของตัวเอง
  นี่เป็นความตั้งใจ และคะแนนก็บอกไว้ตรง ๆ
- **การแจ้งเจ้าของเป็น event** สัญญาที่ไม่มี `owner()` จะถูกแจ้งเป็น `0x0` คู่กรณีของสัญญาเหล่านั้นใช้เส้นทาง responder ของ ThreatRegistry
- **คะแนนอ่านข้อค้นพบหลังออกใบรับรองล่าสุด 16 รายการ**ของคำขอที่ได้ใบรับรอง เพื่อให้ค่าแก๊สมีขอบเขต ข้อค้นพบที่ค้างนานกว่านั้นจะไม่ถูกนับ
- **สัญญาบนเชนอื่น**ได้คะแนนจากสิ่งที่ ZETAPHY รู้เท่านั้น คือใบรับรอง ประวัติ และธง โดยไม่มีคะแนนหรือการหักจาก Neuro เบรกเกอร์ หรือการตรงกับวัคซีน
- **การตรวจสอบตัวเองรันแค่ในการทดสอบ** การตรวจของ CI จะปิดอยู่จนกว่าจะคอมมิตบันทึกจากการตรวจสอบตัวเองจริงบนเทสต์เน็ต
  คุณสมบัติเชิงรูปนัยเป็นการทดสอบ invariant (แบบ fuzz) ไม่ใช่การพิสูจน์ด้วยเครื่อง
