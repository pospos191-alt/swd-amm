# ZETAPHY Offline Cash และ ZETAPHY Mesh

**ใช้บนเทสต์เน็ตเท่านั้น** ไม่ใช่เงินจริง เป็นต้นแบบ สัญญายังไม่ผ่านการตรวจสอบ (audit)

เป็นเงินที่ใช้ได้โดยไม่ต้องมีอินเทอร์เน็ต และเดินทางได้ไกลข้ามทวีปโดยไม่ต้องใช้เน็ต

- **Offline Cash** คือธนบัตรผู้ถือที่มีเงินค้ำ ผู้ออกล็อกเหรียญไว้บนเชนเป็นธนบัตร จากนั้นธนบัตรก็ส่งต่อกันมือต่อมือได้ในขณะที่ทุกคนออฟไลน์
  การส่งต่อแต่ละครั้งคือลายเซ็นแบบทนควอนตัม (ML-DSA-44) คนที่ถือเป็นคนสุดท้ายนำไปขึ้นเงินเมื่อกลับมาออนไลน์
- **ZETAPHY Mesh** คือการส่งแบบเก็บแล้วส่งต่อ (store-and-forward) ระบบจะหั่นของที่เซ็นแล้วทุกชนิด (ธนบัตร เช็ค คำสั่งแลกเปลี่ยน
  หรือธุรกรรมที่เซ็นแล้ว) ออกเป็นเฟรมเล็ก ๆ ที่มีเลขลำดับและเช็กซัม เฟรมขนาดพอดีกับ SMS ข้อความ LoRa / Meshtastic หรือคิวอาร์โค้ด
  ส่งผ่านหลายคนและหลายช่องทางได้ ลำดับไหนก็ได้ แล้วตัวส่งต่อ (relay) จะนำขึ้นเชนเมื่อออนไลน์

ระบบนี้ต่อยอดจาก[การเทรดออฟไลน์](offline-trading.th.md) (เช็คและคำสั่งออฟไลน์) และใบรับรองบล็อกแบบ PQ (`zetaphy-network/src/pqcert.js`)

| | ออนไลน์ครั้งแรก | ระหว่างออฟไลน์ | ออนไลน์อีกครั้ง |
|---|---|---|---|
| **ผู้ออก** | วางเงินค้ำ (≥ 150%) แล้ว `issue` ธนบัตร ล็อกไว้จนถึง `lockUntil` | เซ็นโอนธนบัตรแต่ละใบให้ผู้ถือคนแรก | หลัง `lockUntil` เรียกคืน (`reclaim`) ใบที่ไม่มีใครขึ้นเงิน |
| **ผู้ถือ** | (ไม่บังคับ) วางเงินค้ำของกุญแจตัวเอง | ตรวจธนบัตร เก็บไว้ หรือเซ็นโอนให้กุญแจคนถัดไป | `redeem` เอง หรือเซ็นใบขึ้นเงินให้ relay คนไหนก็ได้ส่งขึ้นเชน |
| **ผู้รับเงิน** | ปักหมุดชุด validator (ครั้งเดียว) | ตรวจสายลายเซ็นและหลักฐานเงินทุน | |
| **Relay** | | รวบรวมเฟรมจาก SMS / LoRa / คิวอาร์ / ไฟล์ | ส่งขึ้นเชน ได้ค่าธรรมเนียมที่ระบุไว้ในข้อมูลที่เซ็น |

## 1. ธนบัตร

- **กุญแจผู้ถือ** ผู้ถือคือกุญแจ ML-DSA-44 เรียกด้วย `keccak256(publicKey)` แฮชนี้คือ "แฮชกุญแจ" ขนาด 32 ไบต์ที่คุณให้คนที่จะจ่ายเงินให้คุณ
  ฮับสร้างกุญแจนี้ในเบราว์เซอร์และเก็บ seed 32 ไบต์แบบเข้ารหัส (AES-GCM ด้วยกุญแจจาก PBKDF2-SHA256 600,000 รอบ เหมือนกุญแจเช็ค)
  ส่วน CLI เก็บไว้ที่ `~/.zetaphy/cash.seed`
- **`issue(issuerKey, lockUntil, values[])`** (ต้องแนบเงิน) ล็อก `msg.value` ไว้เป็นธนบัตร `values` คือราคาหน้าธนบัตร ได้สูงสุด 64 ใบต่อครั้ง
  ผู้ถือคนที่ 0 ของทุกใบคือ `issuerKey` ส่วน `lockUntil` ต้องอยู่ห่างออกไป 1 ถึง 366 วัน ก่อนถึง `lockUntil` มีแต่ผู้ถือเท่านั้นที่ดึงมูลค่าธนบัตรออกได้
  ผู้ออกดึงไม่ได้
- **เงินค้ำของผู้ออก** `bondIssuer(until)` (ต้องแนบเงิน) การ `issue` ต้องมีเงินค้ำ ≥ 150% ของธนบัตรที่ยังไม่ถูกขึ้นเงิน และเงินค้ำต้องล็อกไว้อย่างน้อยจนถึง
  `lockUntil + 30 วัน` (ช่วงยื่นเคลม) ถอนก่อนกำหนดไม่ได้ ทุกครั้งที่ `issue` จะปล่อยเหตุการณ์ `IssuerBonded` ที่บันทึกยอดเงินค้ำ ณ ตอนนั้น
  หลักฐานออฟไลน์จึงแสดงยอดนี้ได้
- **ลิงก์ (การส่งต่อ)**
  `keccak256(abi.encode(LINK_TAG, DOMAIN, noteId, seq, prev, to, cond))`
  - ผู้ถือลำดับที่ `seq` เซ็นด้วย ML-DSA-44 และลายเซ็นนี้ระบุผู้ถือคนถัดไป `to`
  - `prev` คือแฮชของลิงก์ก่อนหน้า สำหรับลำดับ 0 จะเป็นรากของธนบัตร
    `keccak256(abi.encode(NOTE_TAG, DOMAIN, id, value, lockUntil, issuerKey))` ลายเซ็นแรกของผู้ออกจึงยืนยันเงื่อนไขของธนบัตรไปด้วย
  - `DOMAIN` ผูก chain id กับสัญญาไว้
- **ใบขึ้นเงิน (terminal)**
  `keccak256(abi.encode(TERMINAL_TAG, DOMAIN, prev, payout, fee))`
  ผู้ถือปัจจุบันเป็นคนเซ็น ใครส่งขึ้นเชนก็ได้ relay เป็นคนจ่ายค่าแก๊สและได้ `fee` ที่เหลือเข้า `payout` relay เปลี่ยนสองค่านี้ไม่ได้
- **`redeem(id, links, terminal)`**
  - ถ้าธนบัตร**ยังไม่ถูกใช้** จะจ่ายเงินออก **สายที่ถูกต้องและขึ้นเชนได้ก่อนเป็นฝ่ายชนะ**
  - ถ้าธนบัตร**ถูกจ่ายไปแล้ว** สัญญาจะตรวจหาการเคลมเรื่องโกง (ข้อ 2)
  - ทุกข้อความที่รับแล้วจะบันทึกเป็น `spentBy[prev] = ข้อความนั้น` การส่งซ้ำ สายเก่าที่สั้นกว่า หรือการเคลมซ้ำ จึงไม่ได้เงิน
- **`reclaim(ids)`** หลัง `lockUntil` ผู้ออกเอาธนบัตรที่ไม่มีใครขึ้นเงินคืนไปได้ นี่คือการหมดอายุ ไม่ใช่การโกง ผู้ถือใบที่ถูกเรียกคืนจึงไม่มีอะไรให้เคลม
  กระเป๋าจะเตือนเมื่อเหลือเวลาไม่ถึง 3 วัน
- ผู้ถือส่งต่อธนบัตรแบบออฟไลน์ได้เรื่อย ๆ (สูงสุด 64 ลิงก์) แต่ละลิงก์เพิ่มขนาด 3,765 ไบต์ (ดูตารางขนาด)

## 2. การใช้ซ้ำ (double-spend): ใครรับความเสี่ยง

ใครก็เซ็นโอนธนบัตรใบเดียวกันสองครั้งได้ คือมีสองข้อความที่ใช้ `prev` ตัวเดียวกัน เพราะสายที่ขึ้นเชนก่อนชนะ ผู้ถืออีกคนจึงเป็นผู้เสียหาย
ผู้เสียหายเรียก `redeem` ด้วยสายของตัวเอง สัญญาจะหาตำแหน่งแรกที่สายนี้แยกออกจากประวัติที่จ่ายไปแล้ว ผู้ถือ ณ ตำแหน่งนั้นเซ็นทั้งสองข้อความ
จึงเป็นคนโกง จากนั้นสัญญาจ่ายมูลค่าธนบัตรให้ผู้เสียหาย ภายในเวลา `lockUntil + 30 วัน`

| แยกที่ตำแหน่ง | จ่ายจาก | ถ้าเงินค้ำไม่พอ |
|---|---|---|
| ลำดับ 0 (**ผู้ออก**เซ็นโอนสองครั้ง หรือเซ็นโอนแล้วยังเซ็นขึ้นเงินเอง) | **เงินค้ำของผู้ออก** (≥ 150% ของธนบัตรที่ยังไม่ถูกขึ้นเงิน ณ ตอนออก) | ผู้เสียหายรับส่วนที่เหลือเอง |
| ลำดับ k ≥ 1 (**ผู้ถือคนหลัง**ใช้ซ้ำ) | **เงินค้ำของผู้ถือคนนั้น** (`bondHolder(key, until)` ใครวางก็ได้ แต่คนแรกที่วางเท่านั้นที่เติมได้และถอนได้หลัง `until`) | ผู้เสียหายรับส่วนที่เหลือเอง ถ้าไม่มีเงินค้ำเลยก็เสียทั้งหมด |

**การตัดสินใจ: ผู้ออกรับผิดชอบเฉพาะลายเซ็นของตัวเอง** ผู้ออกไม่ได้ประกันให้ผู้ถือคนหลัง ไม่อย่างนั้นใครก็ใช้ธนบัตรซ้ำเพื่อดูดเงินค้ำของผู้ออกได้
แล้วจะไม่มีใครกล้าออกธนบัตร ผู้ถือคนหลังแต่ละคนรับผิดชอบด้วยเงินค้ำของตัวเอง ดังนั้น

- ธนบัตรที่ได้**ตรงจากผู้ออก** ได้รับความคุ้มครองไม่เกินเงินค้ำของผู้ออก เงินค้ำก้อนนี้ใช้ร่วมกันระหว่างผู้เสียหายทุกรายของผู้ออกคนนั้น
  ใครมาก่อนได้ก่อน
- ธนบัตรที่ผ่านมือคนอื่นมาแล้ว ได้รับความคุ้มครองไม่เกิน**เงินค้ำที่น้อยที่สุดในบรรดากุญแจทุกดอกที่เซ็นอยู่ในสาย** เพราะใครในสายก็อาจเป็นคนแยกสาย
  ไม่ใช่แค่คนที่จ่ายให้คุณ ฮับและ `zetaphy cash check` แสดงเป็น "คุ้มครอง X จาก Y" เงินค้ำของผู้ถือจะนับก็ต่อเมื่อล็อกไว้อย่างน้อยจนถึง
  `lockUntil + 30 วัน` ของธนบัตรใบนั้น
- เงินค้ำหนึ่งก้อนใช้ร่วมกันกับทุกใบที่เจ้าของส่งต่อ คนโกงอาจแยกสายหลายใบ และเงินค้ำจะจ่ายให้ผู้เสียหายตามลำดับที่มาเคลม นี่เป็นข้อจำกัดของเงินสดออฟไลน์แบบมีเงินค้ำทุกระบบ
  **ส่วนที่เกินมูลค่าที่ได้รับความคุ้มครอง ผู้รับเงินเป็นคนรับความเสี่ยง** ลดความเสี่ยงได้โดยรับธนบัตรตรงจากผู้ออก ให้ผู้จ่ายวางเงินค้ำของผู้ถือก้อนใหญ่
  และรีบขึ้นเงิน
- การแยกสายที่เกิดต่อลงไปในสายของผู้เสียหายที่ได้รับเงินแล้วก็ไล่ตามได้ด้วย พอผู้เสียหายได้รับเงิน สายของเขาจะถูกบันทึกไว้
  ถ้าผู้เสียหายคนนั้นส่งต่อธนบัตรซ้ำสองครั้งด้วย คนที่สองในสายนั้นก็เคลมจากเงินค้ำของผู้เสียหายคนนั้นได้
- ผู้เคลมที่เซ็นใช้ซ้ำเองจะได้ `OwnDoubleSpend` เพราะการจ่ายผู้เคลมจากเงินค้ำของตัวเขาเองไม่มีความหมาย

## 3. หลักฐานเงินทุนแบบออฟไลน์

ตอนรับเงินแบบออฟไลน์ คุณอยากรู้ว่าธนบัตรถูกล็อกไว้บนเชนจริง และเงินค้ำมีเท่าไร **หลักฐานธนบัตร**บอกเรื่องนี้ได้ หลักฐานตรวจได้**โดยไม่ต้องใช้เน็ต**
เทียบกับ**ชุด validator ที่ปักหมุดไว้** ซึ่งก็คือผลของ `zetaphy pq export-vote-keys` ที่บันทึกไว้ครั้งเดียวจากโหนดที่คุณไว้ใจ

**ทางหลัก: หลักฐานจากผลธุรกรรม (`kind: 'results'`)** สร้างด้วย `buildResultsProof` จาก CometBFT RPC และ `zetaphy cash proof` ก็ใช้วิธีนี้ ประกอบด้วย

1. **ผลธุรกรรม** ผลของธุรกรรมที่ปล่อยเหตุการณ์ (`NoteIssued`, `IssuerBonded` หรือ `HolderBonded`) ในบล็อก H คือ `ExecTxResult` แบบกำหนดแน่นอนของ
   CometBFT (code, data, gas_wanted, gas_used) โดย `data` มี `MsgEthereumTxResponse` ของ Cosmos EVM ซึ่งมี **log ของ EVM** อยู่
2. **เส้นทาง Merkle** เส้นทางแบบ RFC 6962 จากผลนั้นไปถึง `last_results_hash` ใน**ส่วนหัวของบล็อก H+1**
3. **ใบรับรอง** **ใบรับรอง PQ ของบล็อก H+1** คือ attestation ในธุรกรรมแรกของบล็อก H+2 ตรวจแบบเดียวกับ `pqcert.js`
   คือข้อความโหวต แฮชส่วนหัว และกุญแจโหวตที่ใช้ได้ ณ ความสูงนั้น

ตัวตรวจ (`cash-core.js verifyProofItem`) คำนวณแฮชส่วนหัวใหม่และนับ attestation ของ validator ที่ปักหมุดไว้ ต้องมีผู้เซ็นที่มี**พลังเกิน 2/3
ของพลังทั้งหมดที่ปักหมุด** ซึ่งเข้มกว่ากฎของเชนที่นับเฉพาะ validator ที่มีกุญแจโหวต จากนั้นตรวจเส้นทาง Merkle ถอดรหัส log
และตรวจว่า log มาจากสัญญาที่ปักหมุดไว้ CLI ส่ง `headerHash` ของ `pqcert.js` เข้ามาใช้ ส่วนฮับใช้ฟังก์ชันที่พอร์ตมาโดยไม่มี dependency
และมีเทสต์ยืนยันว่าทั้งสองให้ผลตรงกัน

**ทำไมไม่ใช้ `eth_getProof`** Cosmos EVM ตอบ `eth_getProof` ด้วยหลักฐาน IAVL / ICS-23 ของ KV store ไม่ใช่หลักฐาน Merkle-Patricia แบบ Ethereum
ถ้าจะตรวจแบบออฟไลน์ ต้องตรวจ IAVL บวก multistore เทียบกับ `app_hash` ซึ่งเป็นโค้ดมากกว่าที่ต้นแบบนี้มี ทางผลธุรกรรมใช้แค่ SHA-256 protobuf และใบรับรอง

**ทางสำรอง: validator รับรอง (`kind: 'attest'`)** validator เซ็น log นั้นตรง ๆ ด้วยกุญแจโหวต:
`"zetaphy/cash-attest\0" ‖ chainId ‖ "\0" ‖ height ‖ time ‖ keccak(address ‖ topics ‖ data)`
(ML-DSA-44 แบบ k จาก n ต้องเกิน 2/3 ของพลังที่ปักหมุด) สร้างได้ด้วย `attestLog` วิธีนี้ต้องให้ validator รันบริการเซ็น
ซึ่ง**ยังไม่ได้ deploy** ตอนนี้มีแค่รูปแบบและตัวตรวจ ซึ่งผ่านเทสต์แล้ว

**หลักฐานที่ผ่านบอกอะไร และไม่ได้บอกอะไร**

- บอกได้ว่าธนบัตรถูกออกด้วยเงื่อนไขนี้ และเงินค้ำมียอด X ณ บล็อก H โดยต้องเชื่อว่า validator ที่ปักหมุดไว้ซื่อสัตย์ ซึ่งเป็นความไว้ใจระดับเดียวกับ light client ทั่วไป
- **บอกไม่ได้ว่าหลังจากนั้นยังไม่มีใครขึ้นเงินธนบัตรใบนี้** สิ่งที่ปกป้องคุณเรื่องนี้มีแค่สายลายเซ็นกับเงินค้ำ
- เงินค้ำอาจลดลงหลังออกหลักฐาน เมื่อจ่ายให้ผู้เสียหายรายอื่น หลักฐานที่เก่ากว่า 7 วันจะถูกติดป้ายว่า **เก่า**
- หลักฐานมีขนาดใหญ่ มีลายเซ็น ML-DSA หนึ่งอัน (2,420 ไบต์) ต่อ validator บวกส่วนหัวราว 1 KB ควรส่งทางคิวอาร์หรือไฟล์ ส่งครั้งเดียวต่อผู้ออกและต่อเงินค้ำ
  ไม่ใช่ส่งทาง SMS ทุกครั้งที่จ่ายเงิน

## 4. ตั๋วแลกเปลี่ยนแบบ atomic

ผู้ถือ P มีธนบัตร A ผู้ถือ Q มีธนบัตร B ทั้งสองแลกกันแบบออฟไลน์

- **ตั๋ว** กำหนดทั้งสองขาและเส้นตาย:
  `(noteA, seqA, prevA, toA = กุญแจของ Q, payoutA, noteB, seqB, prevB, toB = กุญแจของ P, payoutB, deadline)` ไอดีของตั๋วคือ `ticketId`
- **การเซ็น** ผู้ถือแต่ละคนเซ็นขาของตัวเองเป็นลิงก์ที่มี `cond = ticketId` ลายเซ็นแต่ละอันจึงยืนยันทั้งสองขา ชุดข้อมูลนี้จึง "เซ็นโดยทั้งสองฝ่าย"
- **การชำระ** ลิงก์ที่มีเงื่อนไขนับผลได้เฉพาะผ่าน `settleSwap(ticket, chainA, chainB)` ฟังก์ชันนี้ตรวจทั้งสองสาย แล้วจ่าย A เข้า `payoutA` และ B เข้า `payoutB`
  ใน**ธุรกรรมเดียว** หรือไม่ก็ย้อนกลับทั้งหมด ถ้าธนบัตรใบใดถูกใช้ไปแล้ว (เช่น P เอา A ไปใช้ซ้ำก่อน) จะไม่มีอะไรขยับ และ Q ยังถือ B อยู่
- **ก่อนชำระ** ตั๋วที่ยังไม่ชำระเป็นแค่ข้อเสนอ ขาของตั๋วไม่นับเป็นการใช้จ่าย จึงใช้เป็นหลักฐานการโกงไม่ได้ และขึ้นเงินขาเดียวไม่ได้ (`UnsettledSwap`)
- **หลังชำระ** ลายเซ็นบนตั๋วนับเป็นใบขึ้นเงินของผู้ถือแต่ละคนด้วย ถ้า Q ยังเซ็นโอน A ให้ W อีก W เคลมจากเงินค้ำของ Q ได้
- **ข้อจำกัด (v1)** ธนบัตรที่ได้มาจากตั๋วส่งต่อแบบออฟไลน์ก่อนชำระไม่ได้ กระเป๋าจะปฏิเสธ เพราะขาอีกข้างจะต้องเดินทางไปด้วย

## 5. ZETAPHY Mesh

**แพ็กเก็ต**

```
"Z" 0x01 | ชนิด (1) | flags | เส้นตาย (uint32 วินาที unix, 0 = ไม่มี) | ค่าธรรมเนียม relay โดยประมาณ (varint) | ความยาว (varint) | ข้อมูล
```

- ชนิด: `tx` (ธุรกรรมดิบที่เซ็นแล้ว), `note`, `redeem` (ธนบัตรพร้อมใบขึ้นเงิน), `swap`, `proof`, `cheque` (ข้อความ `ZCHQ1:`), `order` (`ZORD1:`), `raw`
- ธนบัตรและการแลกเปลี่ยนใช้รูปแบบไบนารีแบบกะทัดรัด ไม่ใช้ JSON และไม่ใช้เลขฐานสิบหก
- ไอดีแพ็กเก็ตคือ 8 ไบต์แรกของ SHA-256 และ relay ใช้ไอดีนี้กันข้อมูลซ้ำ
- ค่าธรรมเนียมในแพ็กเก็ตใช้แค่จัดลำดับคิว ค่าธรรมเนียมที่ผูกมัดจริงคือค่าที่อยู่ในข้อมูลที่เซ็นแล้ว (`fee` ของใบขึ้นเงิน หรือ `relayerFee` ของคำสั่ง)

**เฟรม**

```
0xB1 | ไอดีแพ็กเก็ต (4) | ลำดับ (uint16) | จำนวนทั้งหมด (uint16) | ชิ้นข้อมูล | CRC-16/CCITT
```

ส่วนหัวเพิ่ม 11 ไบต์ต่อเฟรม หลังประกอบกลับแล้ว แพ็กเก็ตต้องได้แฮชตรงกับไอดี ทำให้ทิ้งเฟรมที่ปนกันหรือเสียหายได้

**รูปแบบข้อความ**

- `ZM` + base45 (RFC 9285) โดยเขียนช่องว่างเป็น `_` ทุกตัวอักษรจึงอยู่ในชุด GSM 03.38 7 บิตพื้นฐาน และในเฟรมไม่มีช่องว่างเลย วางข้อความแชตทั้งก้อนได้เลย
- `zm` + base32 (RFC 4648 ตัวพิมพ์เล็ก) สำหรับช่องทางที่ตัวพิมพ์ใหญ่เล็กหรือเครื่องหมายวรรคตอนหายไป

**โปรไฟล์**

| โปรไฟล์ | ขนาดเฟรม |
|---|---|
| `sms-binary` | 140 ไบต์ |
| `sms-text` | 160 ตัวอักษร |
| `lora` | 200 ไบต์ (พอร์ตแอปส่วนตัวของ Meshtastic) |
| `lora-text` | 200 ตัวอักษร |
| `qr` | 1,500 ตัวอักษร |
| `file` | เฟรมเดียว |

**การประกอบกลับ** (`Reassembler`) เฟรมมาลำดับไหนก็ได้ ปนกันหลายช่องทางได้ ซ้ำหรือหายบ้างก็ได้ ตัวประกอบจะบอกว่าขาดเฟรมลำดับไหน
เมื่อแพ็กเก็ตครบแล้ว เฟรมของแพ็กเก็ตนั้นที่มาทีหลังจะถูกบอกว่า `done`

**หลายเส้นทาง**

- ส่งแพ็กเก็ตเดียวกันผ่าน relay หลายตัว ชุดที่ขึ้นเชนได้ก่อนชนะ
- ชุดอื่นจะถูกเชนปฏิเสธด้วยระบบกันส่งซ้ำของเชนเอง ได้แก่ `spentBy` และ `AlreadyPaid` ของธนบัตร ยอดสะสมของเช็ค nonce ของคำสั่ง และ nonce ของธุรกรรม
- `MeshRelay` บันทึกการปฏิเสธเหล่านี้เป็น `landed-elsewhere` และไม่ลองส่งซ้ำ
- ทิ้งแพ็กเก็ตที่เลยเส้นตาย เรียงคิวตามค่าธรรมเนียมแล้วตามเส้นตาย และจำสถานะไว้แม้รีสตาร์ต

**วิธีใช้**

- **CLI**
  - `zetaphy mesh send <ชนิด> <ไฟล์> --profile sms-text`
  - `zetaphy mesh relay --in frames.txt [--submit]`
  - `zetaphy mesh sizes`
- **ฮับ** แท็บ Offline การ์ด **Mesh**
  - ส่งออก: ได้เฟรมเป็นข้อความ และคิวอาร์โค้ดทีละเฟรม (ก่อนหน้า / ถัดไป)
  - นำเข้า: วางเฟรมได้ทุกลำดับ จากทุกช่องทาง ฮับแสดงความคืบหน้าและเฟรมที่ขาด เมื่อออนไลน์ก็ส่งใบขึ้นเงิน เช็ค หรือคำสั่งขึ้นเชนได้
    เบราว์เซอร์จึงทำหน้าที่เป็น relay ได้

ความหมายในทางปฏิบัติ

- **เช็ค คำสั่ง และธุรกรรมธรรมดา ส่งได้ด้วย SMS หรือข้อความ LoRa ไม่กี่ข้อความ** เหมาะกับช่องทางที่ช้าและไกล
- **ธนบัตรทนควอนตัมใช้ราว 30–40 SMS ต่อการส่งต่อหนึ่งครั้ง** ควรใช้คิวอาร์ (4 รูปต่อการส่งต่อ) ไฟล์ บลูทูธ หรือส่ง LoRa ต่อเนื่องเป็นชุดแทน
- **หลักฐาน** ควรส่งครั้งเดียวทางคิวอาร์หรือไฟล์ แล้วใช้ซ้ำ

อีกสองเรื่องเกี่ยวกับขนาด

- **การลดขนาด** รุ่นต่อไปอาจส่งกุญแจสาธารณะของผู้ถือแต่ละคนแค่ครั้งเดียวต่อคู่ติดต่อ หรือใช้รูปแบบลายเซ็นทนควอนตัมที่เล็กกว่าสำหรับการส่งต่อ
  ที่ยังใช้ ML-DSA-44 เพราะ precompile ของเชนตรวจได้แล้ววันนี้
- **เวลาออกอากาศของ LoRa** ที่ค่าตั้งต้นทั่วไปของ Meshtastic ข้อความ 200 ไบต์ใช้เวลาออกอากาศราว 0.3–1.5 วินาที และข้อจำกัด duty cycle
  (เช่น 1% ในบางย่านของยุโรป) จำกัดจำนวนเฟรมต่อชั่วโมงที่โหนดหนึ่งส่งได้ ธนบัตรหนึ่งใบจึงใช้เวลาออกอากาศเป็นนาที ไม่ใช่วินาที

| ความเป็นส่วนตัว | สายกุญแจและยอดเงินเห็นได้โดยผู้ถือทุกคนถัดไป และเห็นบนเชนตอนขึ้นเงิน | ธนบัตรไม่เป็นส่วนตัว ควรใช้กุญแจผู้ถือใหม่ |

## 7. ข้อกฎหมาย: วิทยุ

กฎวิทยุสมัครเล่น (แฮม) ในหลายประเทศห้ามการสื่อสารเพื่อธุรกิจหรือการชำระเงิน และห้ามการเข้ารหัสหรือการสื่อความหมายแบบปิดบัง
ตัวอย่างเช่น สหรัฐฯ (47 CFR §97.113 และ §97.113(a)(4)) สหราชอาณาจักร หลายประเทศในยุโรป และเงื่อนไขใบอนุญาตวิทยุสมัครเล่นของไทย
เฟรมการชำระเงินที่เซ็นแล้วเป็นการสื่อสารทางการเงิน **จึงห้ามส่งบนย่านความถี่วิทยุสมัครเล่น**

LoRa / Meshtastic บนย่าน ISM ที่ไม่ต้องมีใบอนุญาต (เช่น 433, 868, 915 หรือ 920–925 MHz แล้วแต่ประเทศ) ใช้ได้ภายใต้ข้อจำกัด duty cycle
และกำลังส่งของท้องถิ่น ตรวจกฎของประเทศคุณเองก่อน ส่วน SMS คิวอาร์โค้ด ไฟล์ บลูทูธ และอินเทอร์เน็ตไม่มีข้อจำกัดแบบนี้

## 8. ข้อจำกัดของต้นแบบนี้

- **หลักฐานจากผลธุรกรรมทดสอบแค่กับ CometBFT จำลอง** โดยใช้ log จริงจากสัญญาและกุญแจ validator ML-DSA-44 จริง ยังไม่ได้รันกับ devnet
  โครงสร้าง protobuf ตาม `MsgEthereumTxResponse` ของ `cosmos/evm` (log เป็นสตริงฐานสิบหก) และใบของต้นไม้ตาม `ExecTxResult` แบบกำหนดแน่นอนของ CometBFT
- **ทางสำรองแบบ attestation มีแค่รูปแบบและตัวตรวจ** ยังไม่มีบริการของ validator ที่เซ็นให้
- **ไม่มีเงินทอนและแบ่งธนบัตรไม่ได้** ธนบัตรต้องใช้ทั้งใบ จ่ายด้วยหลายราคาหน้าธนบัตรรวมกัน
- **ใน v1 ธนบัตรที่ได้จากตั๋วแลกเปลี่ยนทำได้แค่ชำระ** ส่งต่อไม่ได้
- **ค่าแก๊ส** แต่ละลิงก์ใช้ precompile ML-DSA หนึ่งครั้งบวก calldata ราว 3.8 KB สัญญาจำกัดสายไว้ที่ 64 ลิงก์
- **ธนบัตรเป็น ZETAPHY เหรียญหลักเท่านั้น** ยังไม่มีธนบัตร ERC-20
- **กุญแจเงินสดในฮับยังส่งออกไม่ได้** ให้สำรองข้อความของธนบัตรไว้แทน ส่วน `~/.zetaphy/cash.seed` ของ CLI เข้ารหัสได้ด้วย `ZETAPHY_PASSPHRASE`
