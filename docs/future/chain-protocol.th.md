# ZETAPHY v5: การป้องกันที่ฝังอยู่ในเชน (งานวิจัยบน testnet)

English: [chain-protocol.md](chain-protocol.md)

เอกสารนี้อธิบายฟีเจอร์ห้าอย่างใน patch ของโหนด `zetaphy-chain` (`setup-node.sh` ไฟล์
`evmd/zetaphy_future.go`, `zetaphy_aimodel.go`, `zetaphy_immune.go`, `zetaphy_breaker.go`, `zetaphy_guard.go`)
ทั้งหมด **ใช้บน testnet เท่านั้น** และ **ปิดอยู่จนกว่าจะมีคนเปิด**:
ส่วนที่มีผลทั้งเชน governance เป็นผู้เปิด ส่วนการป้องกันของแต่ละบัญชี เจ้าของบัญชีเป็นผู้เปิดเอง
รายละเอียดทางเทคนิคทั้งหมดอยู่ในฉบับภาษาอังกฤษ ฉบับนี้สรุปเนื้อหาเดียวกัน

## การเปิดใช้ (ความสูงบล็อก v5)

- **เชนใหม่:** v5 ทำงานตั้งแต่บล็อก 1 (`zetaphyd init` และ `setup-node.sh` เขียนคีย์ `20` ไว้ใน `app_state.zetaphypq`)
- **เชนที่รันอยู่แล้ว:** เสนอ `gov.sh propose-upgrade zetaphy-v5 <H> "<summary>"` แล้วโหวตให้ผ่าน v5 จะมีผลตั้งแต่บล็อก H+1
  เชนต้องผ่าน `zetaphy-v4` มาก่อน
- ก่อนถึงความสูง v5 ทุกอย่างทำงานเหมือนเดิม:
  - ที่อยู่ทั้งสามเป็นบัญชีว่าง
  - vote extension ที่มีข้อมูลเกินลายเซ็น ML-DSA จะถูกปฏิเสธเหมือนเดิม

ค่าตั้งของ governance ทั้งหมดส่งผ่านข้อความเดียว `MsgSetFuture{kind, data}` โดยใช้ `gov.sh`:

```bash
bash gov.sh ai-model model.hex          # node zetaphy-chain/tools/gbdt-export.mjs > model.hex
bash gov.sh immune '{"enabled":true,"enforce_bps":9000,"hold_bps":8000,"protect_bps":7000}'
bash gov.sh breaker '{"bridge":"0x…","topic":"0x<topic0>","recipient_topic":2,"amount_word":0,"min_volume":"1000000000000000000000","vol_mult_bps":50000,"new_ratio_bps":5000,"enabled":true}'
bash gov.sh breaker-rearm 0x…
```

## (11) AI precompile `0x…0902`

`score(bytes features) → uint16 bps` และ `model()` ประเมินโมเดล GBDT ที่ governance เก็บไว้ใน state
โดยใช้ **จำนวนเต็มล้วน** ทุกโหนดจึงได้ผลตรงกัน
- ฟีเจอร์เป็น int32 แบบ big-endian
- ใช้ sigmoid แบบจำนวนเต็ม 65 จุด
- มีขีดจำกัด 64 KiB, 512 ต้น และ 255 โหนดต่อต้น
- gas = 2,000 + 6 ต่อ word ของ input + 40 ต่อต้น + 8 ต่อโหนดที่เดินผ่าน
  โมเดลจริงของ Neuro (160 ต้น) ใช้ 39,404 gas ต่อการเรียกหนึ่งครั้ง (รวมค่าพื้นฐาน 21,000) และใช้เวลาประเมินราว 35 µs

`tools/gbdt-export.mjs` แปลง `zetaphy-neuro/ml/model.json` เป็นรูปแบบ `ZGB1`
โดยคูณฟีเจอร์และ threshold ด้วย 1e4 แล้วปัดลง และรวม calibration เข้าไปในค่าของใบไม้

ผลทดสอบ:
- เชนให้คะแนนตรงกับตัว export ทุกค่า บน 41 เวกเตอร์
- เมื่อเทียบกับโมเดล float ของ Neuro ต่างกันไม่เกิน 15 bps
  เมื่อค่าฟีเจอร์อยู่ห่างจาก threshold เกิน 2e-4

ข้อจำกัด: ค่าที่อยู่ห่างจาก threshold ไม่ถึง 1e-4 อาจไปคนละกิ่งกับโมเดล float
และผู้เรียกต้องคำนวณฟีเจอร์มาเอง

## (12) ระบบภูมิคุ้มกัน `0x…0903`

ขั้นตอน:
1. **บล็อก N:** สัญญาที่สร้างระดับบนสุดในบล็อกนี้ (ไม่เกิน 16 สัญญา) เข้าคิวรอให้คะแนน
2. **การโหวตบล็อก N+1:** validator แต่ละรายให้คะแนนจาก bytecode ด้วยกฎชุดย่อยของ Neuro
   - SELFDESTRUCT, DELEGATECALL, CALLCODE, tx.origin, CREATE2
   - ถ้าเป็น ERC-20: ฟังก์ชัน blacklist, ตั้งค่าธรรมเนียม, เปิด/ปิดการเทรด, mint, กระเป๋าภาษี

   คะแนนถูกใส่ใน vote extension **ต่อท้ายลายเซ็น ML-DSA** โดยไม่แตะรูปแบบของใบรับรอง PQ
3. **บล็อก N+2:** proposer นำคะแนนทั้งหมดมาใส่ใน `MsgZXVotes`
   - ทุกโหนดตรวจลายเซ็น ed25519 ของ CometBFT ทีละราย
   - เชนบันทึก **ค่ามัธยฐานถ่วงด้วย voting power** ก็ต่อเมื่อมีผู้ส่งคะแนนรวมกัน **เกิน 2/3 ของ power**

คะแนนถูกบันทึกที่ N+2 ไม่ใช่ N+1 เพราะใน ABCI++ การโหวตบล็อก H เกิดขึ้นก่อนที่บล็อก H จะถูกประมวลผล

การอ่านค่า:
- `scoreOf` คืนคะแนนที่บันทึกไว้
- `isContractEnforced` และ `isContractHeld` ใช้อินเทอร์เฟซเดียวกับ ThreatRegistry
  จึงใช้ร่วมกับ threat gate ได้ทันที (`gov.sh threat-gate 0x…0903 on`) และใช้กับ `BridgeGuard.setThreats` ได้

ข้อจำกัด:
- **ยังไม่ให้คะแนนสัญญาที่สร้างจากสัญญาอื่น (factory)** เพราะต้องใช้ tracer ใน consensus
- ให้คะแนนได้ไม่เกิน 16 สัญญาต่อบล็อก
- เป็นกฎชุดเล็ก ไม่ใช่การวิเคราะห์เต็มรูปแบบของ Neuro
- proposer ตัดคะแนนทิ้งได้ (เป็นการเซ็นเซอร์ ทำให้บันทึกช้าลง) แต่ปลอมคะแนนไม่ได้
- ลายเซ็นที่ครอบคลุมข้อมูลคะแนนเป็น ed25519 ยังไม่ใช่ post-quantum

## (13) โหมดบัญชีที่ได้รับการป้องกัน `0x…0904`

`protect(mode, delay)` มีสามโหมด:
- 0: ปิด
- 1: คิวหน่วงเวลา
- 2: ปฏิเสธ

สำหรับบัญชีที่เปิดใช้ ธุรกรรมต่อไปนี้ถูกหยุด ถ้าปลายทางเป็นสัญญาความเสี่ยงสูง:
- การเรียกสัญญาหรือส่งเหรียญเข้าสัญญานั้น
- การ approve หรือ transfer ให้สัญญานั้น
- การส่งผ่าน bank ไปยังสัญญานั้น

สัญญาความเสี่ยงสูงคือ:
- สัญญาที่มีคะแนนภูมิคุ้มกัน ≥ `protect_bps` (ค่าเริ่มต้น 7000) หรือ
- สัญญาที่ ThreatRegistry ติดธงแบบ enforced

ในโหมด 1 บัญชีต้องเรียก `queue(target)` ไว้ล่วงหน้าอย่างน้อย delay วินาที แล้วจะใช้ได้ภายในหนึ่งวัน
การเพิ่มความเข้มมีผลทันที การลดความเข้มหรือปิดต้องรอ `max(delay, 1 วัน)`
คนที่ขโมยกุญแจไปจึงปิดการป้องกันทันทีไม่ได้
บัญชีที่ไม่ได้เปิดใช้จะไม่ถูกตรวจเลย

ข้อจำกัด:
- เห็นเฉพาะสิ่งที่ผู้ลงนามธุรกรรมทำเอง ไม่เห็นสิ่งที่ smart wallet ทำภายใน
- ไม่ถอด calldata ของ multicall

## (31) ตัวตัดวงจรของสะพาน

governance กำหนดสะพานที่จะเฝ้าดูได้ไม่เกิน 4 แห่ง โดยระบุ event ที่แสดงการไหลออก
แล้วทุกโหนดนับจาก log ในแต่ละบล็อก:
- ปริมาณที่ไหลออก
- จำนวนครั้ง
- จำนวนผู้รับรายใหม่
- ค่าฐานแบบ EMA

validator ติดธงเมื่อครบทั้งสามข้อ:
- ปริมาณ ≥ `min_volume`
- ปริมาณ ≥ ค่าฐาน × `vol_mult_bps`
- สัดส่วนผู้รับรายใหม่ ≥ `new_ratio_bps`

ถ้า validator ที่มี power **เกิน 2/3** ติดธง เชนจะเรียก `pause()` ของสะพานจาก `BreakerAddress` ในบล็อก N+2
governance ต้องให้สิทธิ์ผู้หยุด (pauser) แก่ที่อยู่นี้ก่อน เช่น `setGuardian(BreakerAddress, true)`
เชน **ไม่เคยเรียก unpause** การเปิดสะพานอีกครั้งทำได้ทาง governance เท่านั้น
`breaker-rearm` ทำให้ตัวตัดวงจรทำงานได้อีกครั้ง

ผ่านการทดสอบด้วยการจำลองการดูดเงินออกจากสะพาน

ข้อจำกัด:
- การดูดเงินช้า ๆ ที่ต่ำกว่า `min_volume` ในแต่ละบล็อกจะตรวจไม่พบ
- บล็อกที่ถูกดูดเงินเองหยุดไม่ทัน
- ชุดผู้รับที่เคยเห็นจะโตขึ้นเรื่อย ๆ

## (33) การกักธุรกรรมผิดปกติ `0x…0904`

`holdOptIn(guardian, timeout, minAmount, multBps)` เปิดใช้การกัก
เชนเก็บสถิติราคาถูกต่อบัญชี: จำนวนครั้งที่ส่งเหรียญหลักออก และค่าเฉลี่ยเคลื่อนที่

ยอดส่งออกถูก **กัก** เมื่อเกิน `minAmount` และเข้าข้อใดข้อหนึ่ง:
- เป็น 5 ครั้งแรกของบัญชี
- เกินค่าเฉลี่ย × `multBps`

ยอดที่ถูกกักจะผ่านได้เมื่อ:
1. บัญชีเรียก `requestRelease(amount)`
2. แล้วรอจนครบ timeout **หรือ** ให้ guardian (กุญแจที่สอง เช่น บัญชี ML-DSA-44 หรือ passkey wallet) เรียก `confirmRelease`

guardian ยกเลิกคำขอได้ การยกเลิกการใช้งานต้องรอ timeout และ guardian ยกเลิกการยกเลิกนั้นได้

ข้อจำกัด:
- นับเฉพาะเหรียญหลัก ยังไม่นับ ERC-20
- ถ้า guardian ไม่ทำอะไร หัวขโมยยังส่งออกได้หลังครบ timeout การกักช่วยซื้อเวลา ไม่ใช่สิทธิ์ยับยั้ง

## ประสิทธิภาพและความปลอดภัย

- ต้นทุนต่อบล็อกต่ำมาก:
  - อ่าน bytecode ไม่เกิน 16 สัญญา
  - ตรวจ ed25519 หนึ่งครั้งต่อ validator
  - เรียก EVM เฉพาะเมื่อตัวตัดวงจรทำงาน
- ใช้หน่วยความจำเพิ่มไม่เกิน 64 KiB จึงรันบน validator ที่มี RAM 1 GB ได้
- ทุกอย่างที่เปลี่ยน state เป็นแบบกำหนดผลได้แน่นอน (deterministic)
- ข้อมูลโหวตที่ผิดรูปแบบหรือถูกปลอมจะถูกข้ามไป ไม่ทำให้บล็อกล้ม

## สิ่งที่ยังเหลือ

- ให้คะแนนสัญญาที่สร้างจาก factory
- ลายเซ็น post-quantum สำหรับข้อมูลคะแนน
- โปรไฟล์ของ ERC-20
- ถอด calldata ของ multicall
- ตัดแต่งชุดผู้รับที่เคยเห็น
- ทดสอบตัวตัดวงจรสะพาน, AI precompile และตัวป้องกันบัญชีบน devnet จริง
  (ส่วนระบบภูมิคุ้มกันผ่านการทดสอบแล้วใน `test-vote-keys.sh` ขั้นที่ 9:
  เป็น devnet จริงที่มี validator สองรายและ full node หนึ่งตัว
  ทั้งสองโหนดบันทึกคะแนน 5500 bps ตรงกัน และใบรับรอง PQ ยังทำงานต่อ)
