# Proof of useful work สำหรับการฝึก AI: เอาพลังประมวลผลของเครือข่ายมาฝึก Neuro

ใช้บน testnet เท่านั้น ไม่มีอะไรในนี้ถือหรือจ่ายเงินจริง และข้อมูลที่ใช้ฝึกในการจำลองเป็น **ข้อมูลสังเคราะห์**
(ระบุไว้ชัดเจน) หน้านี้อธิบายว่าในรีโปมีอะไรแล้วบ้าง พิสูจน์อะไรได้ และพิสูจน์อะไรไม่ได้

## ทำไมถึงเรียกว่างานที่ "มีประโยชน์"

Proof of work แบบเดิมเผาพลังงานไปกับแฮชที่ไม่มีใครต้องการ ที่นี่พลังประมวลผลที่ว่างอยู่ของเครือข่ายถูกเอาไปทำ
สามงานที่ทำให้ Neuro (โมเดลตรวจจับการหลอกลวง, `zetaphy-neuro/ml`) เก่งขึ้น และผู้ร่วมงานจะได้เงินก็ต่อเมื่องาน
**ผ่านการตรวจ** และผลลัพธ์ **มีประโยชน์จริงแบบวัดได้**

1. **(a) งานติดป้ายข้อมูล** — แปลงสัญญาเป็นแถวข้อมูลสำหรับฝึก: worker อ่าน bytecode ของสัญญา ดึงฟีเจอร์ของ
   Neuro (`zetaphy-neuro/ml/features.js`) กับป้ายกำกับแบบหยาบจากกฎ แล้วเอา keccak ของแถวนั้นเป็นคำตอบของ
   งานสแกนใน `UsefulWork` ตามปกติ: มี 3 ที่นั่ง จ่ายเมื่อ 2 ที่นั่งตอบตรงกัน และใช้ commit-reveal จึงลอกคำตอบกัน
   ไม่ได้ (สัญญาเดิม ไม่ต้องแก้; ฟังก์ชัน `labelRow`)
2. **(b) งานฝึกโมเดล** — worker ฝึกโมเดลหนึ่งขั้น (ต้นไม้ตัดสินใจไม่กี่ต้น) บนข้อมูลส่วน (shard) ที่ได้รับมอบหมาย
   ด้วย seed ที่กำหนดตายตัว เพราะการฝึกได้ผลตรงกันทุกบิต คนอื่นจึงรันซ้ำส่วนไหนก็ได้และต้องได้ไบต์เดียวกัน
3. **(c) งานประเมินผล** — worker วัดผลโมเดลตัวใหม่ (โมเดลปัจจุบัน + ขั้นการฝึกที่ผ่านการตรวจ) บนข้อมูลกันไว้
   (held-out) ที่ **ไม่มีใครรู้ล่วงหน้า** นี่คือนิยามของคำว่า "มีประโยชน์": รอบหนึ่งจะจ่ายผู้ฝึก **ก็ต่อเมื่อ** AUC บน
   ข้อมูลกันไว้สูงขึ้นอย่างน้อย `minGainAuc` (0.005) และ recall ที่ false positive 1% ไม่ลดลง

งานตรวจได้เงินไม่ว่าผลจะออกมาอย่างไร (ผู้ตรวจและผู้ประเมินจึงไม่มีเหตุผลจะเอียงไปทางรับโมเดล) ส่วนงานฝึก
ได้เงินเฉพาะเมื่อโมเดลถูกรับเท่านั้น

## การฝึกที่ได้ผลตรงกันทุกบิตใน JavaScript

`train-core.js` ปลูกต้นไม้แบบ gradient boosting (logistic loss, รูปแบบ `neuro-ml-gbdt/1` ของ Neuro ต้นไม้ที่ได้จึง
รันใน `zetaphy-neuro/ml/model.js` ได้ทันที) worker ที่ซื่อสัตย์สองคนต้องได้ **ไบต์ที่เหมือนกันเป๊ะ** ไม่ว่าจะใช้
JS engine ไหน ตัวเลขใน JavaScript เป็น double ตาม IEEE-754 และ `+ - * /` ปัดเศษถูกต้องเหมือนกันทุกที่ (ภาษานี้ไม่รวม
`a*b+c` เป็นคำสั่งเดียว) แต่ `Math.exp/log/pow` สเปกบอกแค่ว่า "ประมาณค่าตามแต่ละ implementation" เราจึง

- **ไม่ใช้คณิตที่ขึ้นกับ engine**: `dexp` ลดช่วงเอง (`x = k·ln2 + r` โดยแยก ln2 แบบ fdlibm) แล้วใช้พหุนามดีกรี 16
  และคูณด้วย 2 แบบแม่นยำ ห่างจาก `Math.exp` ไม่เกิน 2.2e-16 และได้บิตเดียวกันทุกที่ ถ้ามี `Math.exp/log/pow/random/sqrt/…`,
  `**` หรือ `toPrecision` โผล่ในไฟล์ เทสต์จะล้ม
- **บวกตามลำดับเดียว**: แถวเรียงตาม index, bin เรียงตาม index, ต้นไม้เรียงตาม index; margin อัปเดตทีละต้น
- **สุ่มด้วยจำนวนเต็ม**: xoshiro128** ตั้ง seed ต่อต้นจาก `(seed, shard, tree)`; การสุ่มแถว/คอลัมน์เทียบจำนวนเต็ม 32 บิต
- **ปัดค่าให้ลงตาราง**: ค่าที่ใบปัดเป็นช่วง 2^-24; ถ้าการแบ่งเสมอกันให้ฟีเจอร์ที่เลขน้อยสุด แล้วจึง bin ที่น้อยสุด

หลักฐานอยู่ในเทสต์: `zetaphy-network/test/trainwork.test.js` ล็อกแฮชอ้างอิงไว้ (โมเดลฐาน, แถวของ shard, root ของ
checkpoint, ต้นไม้) และคำนวณ root ใหม่ใน V8 isolate ตัวใหม่ (worker thread); ส่วนเทสต์เบราว์เซอร์ของ hub
(`zetaphy-hub/test/work.e2e.mjs`) รันงานฝึกซ้อมใน Web Worker ของ **Chromium** แล้วเช็กว่า root ของ checkpoint
ตรงกับของ Node ทุกบิต

## Checkpoint และการสุ่มตรวจ (แนว "proof of learning")

งานที่มี `T` ต้นถูกแบ่งเป็น `C = T / every` ช่วง (ค่าเริ่มต้น 24 ต้น 8 ช่วง ช่วงละ 3 ต้น) ในแต่ละช่วง ผู้ฝึกแฮชต้นไม้
ที่ปลูก **พร้อมบันทึกขั้นตอน (transcript) ว่าปลูกอย่างไร**: gain และผลรวม gradient `(G, H)` ของทุกการแบ่ง และ `(G, H)`
ของทุกใบ

```
d_s  = keccak("zetaphy-train/1 segment" ‖ s ‖ trees_s ‖ transcript_s)
root = keccak(d_1 ‖ … ‖ d_C)
```

ผู้ฝึก commit `keccak(root, treesHash, worker, salt, task)` แล้วค่อยเปิด `root` กับ `treesHash` ทีหลัง และเผยแพร่ต้นไม้
(อ้างอิงด้วย `treesHash`) จากนั้น **แฮชของบล็อกในอนาคต** จะสุ่มเลือก `checksPerJob` ช่วงของทุกงาน (และผู้ตรวจ
`verifiersPerCheck` คนต่อช่วง ไม่มีทางเป็นผู้ฝึกเอง) ผู้ตรวจเอาต้นไม้ที่เผยแพร่แล้ว **ก่อน** ช่วง `s` มาฝึกช่วง `s` ใหม่
แล้วปิดผนึก `d_s` ของตัวเอง (commit แล้วค่อย reveal) หลังจากผู้ตรวจปิดผนึกครบแล้วเท่านั้น ผู้ฝึกจึงเปิด `d_1..d_C`
(เช็กกับ `root`) คำตอบเสียงข้างมากเป็นตัวตัดสิน

- เสียงข้างมาก = `d_s` ของผู้ฝึก → ผ่าน
- เสียงข้างมาก ≠ (ช่วงที่ปลอม, transcript ที่แต่งขึ้น, ต้นไม้ที่ไม่ได้เผยแพร่หรือแฮชไม่ตรง `treesHash` → `UNAVAILABLE`)
  → งาน **ไม่ผ่าน** และผู้ฝึกโดนยึด `trainSlash` (ครึ่งหนึ่งให้ผู้ตรวจที่จับได้ ตาม `catchBps`)
- ผู้ตรวจที่เป็นเสียงข้างน้อยหรือไม่เปิดคำตอบ โดนยึด `missSlash`

ทำไมต้องมี transcript: ต้นไม้เป็นข้อมูลสาธารณะทันทีที่เผยแพร่ ผู้ตรวจขี้เกียจจึงอาจแค่แฮชต้นไม้แทนการฝึกซ้ำ
(ปัญหา "verifier's dilemma") แต่ transcript (gain, ผลรวม gradient) ไม่เคยถูกเผยแพร่ก่อนผู้ตรวจ commit การจะได้มันมา
**ก็คือ** การรันช่วงนั้นซ้ำนั่นเอง

## สัญญา

**`TrainingPool`** — worker วางเงินค้ำ (`join` อย่างน้อย `minStake`) ตลาดที่ governance อนุญาตจะล็อกสมาชิกไว้ระหว่างที่
ถือที่นั่งหรือได้รับมอบหมายงาน และยึดเงินค้ำได้ (เงินเข้ากองสำรองของตลาดนั้น) `exit` ออกจากการสุ่มทันที แต่เงินค้ำ
จะคืนหลัง `exitDelay` (นานกว่าหนึ่งรอบเต็ม ตลาดเช็กให้) คนโกงจึงหนีก่อนถูกตัดสินไม่ได้

**`TrainingMarket`** — หนึ่ง task = หนึ่งรอบ

| ขั้น | ใคร | ทำอะไร |
|---|---|---|
| post | ผู้ตั้งงาน (ถ้าเป็นรอบที่มีเงินอุดหนุนต้องเป็น feeder) | งบประมาณ (เก็บไว้ในสัญญา), `specHash` (shard ข้อมูล, โมเดลฐาน, seed, ไฮเปอร์พารามิเตอร์), โมเดลฐาน = เวอร์ชันที่ใช้อยู่ใน `ModelEpochs`, `heldoutCommit = keccak(secret, poster)` |
| ที่นั่ง → commit → reveal | สมาชิกในพูล | ที่นั่ง j ฝึก shard j; ปิดผนึก `keccak(root, treesHash, worker, salt, task)`; แล้วเปิด |
| requestDraw → draw | ใครก็ได้ | แฮชของบล็อกที่ถูกกำหนด **ก่อน** บล็อกนั้นจะเกิด ใช้สุ่มช่วงที่ตรวจ ผู้ตรวจ (ไม่ใช่ผู้ฝึกเอง) และผู้ประเมิน (ไม่ใช่ผู้ฝึกที่เปิดผลแล้ว) ที่นั่งที่ไม่ยอมเปิดผลโดนยึด `missSlash` |
| verify | ผู้ตรวจ, ผู้ฝึก, ผู้ตั้งงาน | digest ที่ปิดผนึก; ผู้ฝึกเปิด `d_1..d_C`; ผู้ตรวจเปิดคำตอบ; ผู้ตั้งงานเปิด secret |
| judge | ใครก็ได้ | ตัดสินเสียงข้างมากทีละจุดตรวจ; งานไม่ผ่านโดนยึด; จ่ายผู้ตรวจ (`checkBps` ของงบ); id ของโมเดลใหม่ = `keccak(baseModel ‖ treesHash ของทุกงานที่ผ่าน)`; seed ของข้อมูลกันไว้ = `keccak(secret, randomness)` |
| eval → finalize | ผู้ประเมิน | ปิดผนึก `keccak(baseAuc, candAuc, baseRecall, candRecall)`; เสียงข้างมาก; จ่ายผู้ประเมิน (`evalBps`); **รับโมเดล** ก็ต่อเมื่อ `candAuc ≥ baseAuc + minGainAuc` และ `candRecall ≥ baseRecall` แล้วผู้ฝึกของงานที่ผ่านแบ่ง `trainBps` + เงินอุดหนุน |

โมเดลที่ถูกรับจะถูกบันทึกไว้ (`acceptedBy`) และ **governance เป็นคนตั้งเวลาให้เวอร์ชันใหม่มีผล**: การโหวตผ่าน timelock
เรียก `ModelEpochs.schedule(candidate, activation, uri)` (การจำลองทำแบบนี้จริง) ตัวตลาดเองไม่เคยเปลี่ยนโมเดลที่ใช้อยู่
และรอบใหม่ต้องเริ่มจากเวอร์ชันที่ใช้อยู่ (ไม่อย่างนั้นได้ `StaleBase`)

**ไม่มีกุญแจแอดมิน** ทั้งสองสัญญาบังคับให้ governance เป็น timelock ที่หน่วงอย่างน้อย 2 วัน (ถ้าเป็น EOA จะได้
`NotTimelock`) และตลาดเริ่มต้นแบบหยุดไว้จนกว่าจะมีการโหวตเปิด ไม่มีทางถอนเงินของคนอื่น: การจ่ายเป็นแบบให้ผู้รับมาดึงเอง
(`withdraw`) เทสต์ตรวจบัญชีหลังทุกสถานการณ์: `ยอดในตลาด = owed + reserve + escrow` และ `ยอดในพูล = totalStake`

**การออกเหรียญ (issuance)** รอบของ feeder ใส่ `subsidy` (ไม่เกิน `maxSubsidy`) ให้ผู้ฝึกของรอบที่ถูกรับได้ โดยดึงจาก
กองสำรองของตลาด (เงินค้ำที่ถูกยึด) ก่อน แล้วค่อยดึงจาก **`UsefulIssuance`** (ถังรางวัลจาก RewardVault ที่มีเพดาน,
ดึงได้อย่างเดียว, อยู่หลัง timelock; ดู [useful-work.th.md](useful-work.th.md) ข้อ 34) ไม่มีการมิ้นต์เหรียญใหม่ การฝึก
ตัวตรวจจับการหลอกลวงคืองานด้านความปลอดภัย ซึ่งก็คือสิ่งที่ส่วนแบ่ง issuance นี้มีไว้จ่าย และจ่ายหลังจากผลบนข้อมูล
กันไว้ถูกรับแล้วเท่านั้น

## การจำลองครบวงจร (เชนในหน่วยความจำ, สัญญาจริง)

`node zetaphy-network/src/trainwork/cli.js simulate` (และเทสต์) รัน worker 6 คนในพูล: w1–w4 ซื่อสัตย์, **w5 คนโกง**
(ฝึกจริงแค่ 2 จาก 8 ช่วง ที่เหลืออีก 6 แต่งขึ้นเพื่อประหยัดพลังประมวลผล), **w6 คนลอกขี้เกียจ** (ลอกคำมั่นที่ปิดผนึกของคนอื่น
แล้วพยายามเอาการเปิดเผยของเขามาใช้ซ้ำ) แต่ละรอบ: 4 shard × 8 ช่วง × 3 ต้น; ตรวจ 2 ช่วงต่องาน ผู้ตรวจ 3 คนต่อช่วง
ผู้ประเมิน 3 คน; งบ 30, เงินอุดหนุน 3, `trainSlash` 5, `missSlash` 1, เงินค้ำ 20 (ZETAPHY ทดสอบ)

  คือช่วง 0 ซึ่งมันฝึกจริงจึงผ่าน — การตรวจเป็นเรื่องของความน่าจะเป็น), **w6 ขาด** (คำมั่นที่ลอกมาเปิดไม่ได้)

### การวางยาข้อมูล (data poisoning) และการประเมินบนข้อมูลกันไว้ช่วยได้แค่ไหน

การสุ่มตรวจพิสูจน์ว่า **การคำนวณ** ซื่อสัตย์ แต่ไม่ได้พิสูจน์ว่า **ข้อมูล** ซื่อสัตย์ เทสต์จึงป้อน shard ที่ป้ายกำกับถูกวางยา
(ตระกูลสแกมใหม่ถูกติดป้ายว่า "ปลอดภัย", `world: 'v1p'`) ส่วนข้อมูลกันไว้มาจากโลกจริง ทุกจุดสุ่มตรวจผ่าน (เพราะการฝึก
ซื่อสัตย์) แต่การประเมินวัดได้ **AUC 0.7164 → 0.5120**, recall 0.1238 → 0.0766: **ไม่รับ** ผู้ฝึกไม่ได้เงินค่าฝึก
ผู้ตรวจและผู้ประเมินได้เงิน ผู้ตั้งงานได้กองเงินค่าฝึกคืน และโมเดลที่ใช้อยู่ไม่เปลี่ยน ที่ได้ผลเพราะข้อมูลกันไว้ (1) ถูกเลือก
ด้วย seed ที่ไม่มีใครรู้จนกว่าการฝึกจะถูก commit แล้ว และ (2) ไม่เคยอยู่ใน shard ที่ใช้ฝึก (shard ถูกกำหนดใน spec และ
การสุ่มตรวจบังคับว่างานหนึ่งฝึกบน shard ของตัวเองเท่านั้น — ถ้าแอบเอาข้อมูลกันไว้ไปฝึก digest จะเปลี่ยน)

## ข้อจำกัด (อ่านก่อนจะเชื่อ)

- **การสุ่มตรวจเป็นเรื่องความน่าจะเป็น** งานที่ปลอมนิดหน่อยโดนจับด้วยโอกาสน้อย (ดูตาราง) สิ่งที่ป้องกันคือความคุ้ม
  (ค่าปรับ ≫ สิ่งที่ประหยัดได้) บวกกับชื่อเสียง ไม่ใช่การพิสูจน์ทางคณิตศาสตร์ ยิ่งตรวจมาก ยิ่งต้องรันซ้ำมาก
- **สมมติว่าเสียงข้างมากซื่อสัตย์** แต่ละจุดตรวจตัดสินโดยสมาชิกที่วางเงินค้ำ 3 คนที่สุ่มมา ใครคุมพูลส่วนใหญ่ได้ก็คุมการตรวจได้
  การสุ่มนับต่อสมาชิก ไม่ใช่ต่อเงินค้ำ บัญชีปลอม (Sybil) จ่ายคนละ `minStake` การสุ่มแบบถ่วงตามเงินค้ำหรือชื่อเสียงคือขั้นต่อไป
- **ความสุ่ม** การสุ่มใช้แฮชของบล็อกที่ถูกกำหนดก่อนบล็อกจะเกิด ผู้เสนอบล็อกยังเอียงผลได้ด้วยการไม่ปล่อยบล็อก seed ของ
  ข้อมูลกันไว้ผสม secret ของผู้ตั้งงานด้วย จึงไม่มีฝ่ายไหนคุมได้คนเดียว ผู้ตั้งงานที่ไม่ยอมเปิด secret เสียเงินคืนทั้งหมด
  ถ้าใช้ beacon (drand, VRF) จะแข็งแรงกว่านี้
- **ความพร้อมของข้อมูล** ต้นไม้ที่เผยแพร่อยู่นอกเชน (ในการจำลองใช้ที่เก็บแทน IPFS / HTTP) การกักไว้ทำให้งานไม่ผ่าน (มีเทสต์)
  แต่ถ้าที่เก็บล่ม งานที่ซื่อสัตย์ก็อาจไม่ผ่านได้เหมือนกัน
- **การวางยาที่ไม่กระทบตัวเลขรวม** ประตูข้อมูลกันไว้หยุดการวางยาที่ทำให้ AUC/recall ตก แต่ backdoor แบบเจาะจง
  (มีตัวกระตุ้นที่พลิกผลของตระกูลเดียว ขณะที่ตัวเลขรวมยังดี) อาจผ่านได้ สิ่งที่ช่วยได้และมีในรีโปแล้ว: ชุดหลบเลี่ยงของ
  red team ของ Neuro (`ml/redteam`), การเช็ก recall รายตระกูลใน `ml/train/train.js` และ `combine.js` ที่ไม่เคยลดระดับ
  ที่กฎตัดสินไว้ งานติดป้าย (a) เป็นการเห็นตรงกัน k จาก n บนป้ายแบบ *หยาบ* ความจริงยังต้องมาจากผลที่เกิดขึ้นจริง
  และป้ายจากคน (DataDAO, label registry)
- **ข้อมูลประเมินค่อยๆ รั่วเมื่อใช้ซ้ำ** ถ้าหลายรอบใช้ชุดเดิม ข้อมูลจะค่อยๆ รั่ว (ปัญหา "reusable holdout") ต้องหมุนเวียน
  ชุดประเมินด้วยข้อมูลติดป้ายใหม่
- **ความตรงกันทุกบิตใช้ได้กับตัวฝึกนี้เท่านั้น** ที่ทำได้เพราะโมเดลเล็กและเป็นโค้ด CPU ใน JS ธรรมดา deep learning บน GPU
  ไม่ได้ผลตรงกันทุกบิตข้ามฮาร์ดแวร์ถ้าไม่ใช้ kernel พิเศษ ซึ่งเป็นส่วนยากที่โครงการด้านล่างกำลังแก้
- **ข้อมูลสังเคราะห์** ทั้งในการจำลองและงานฝึกซ้อมในเบราว์เซอร์ ของจริงจะใช้แถวจาก corpus (`rowsHash` ของไฟล์ที่อ้างอิง
  ด้วยแฮช) และโมเดลฐานคือ `zetaphy-neuro/ml/model.json` (รูปแบบต้นไม้เดียวกัน เทสต์รันต้นไม้ใหม่ผ่าน `ml/model.js` แล้ว)
- **ต้นทุน** ในการจำลอง การตรวจใช้พลังประมวลผลเพิ่ม 58% และค่าแก๊สโตตามจำนวนงาน × จุดตรวจ × ผู้ตรวจ `TrainingMarket`
  มีขนาด 24,491 ไบต์ เกือบชนเพดาน 24,576 ไบต์ (EIP-170) ถ้าจะเพิ่มฟีเจอร์ต้องแยกสัญญาอีก (พูลแยกออกมาแล้วหนึ่งตัว)
- **ยังไม่ได้ deploy** และยังไม่ผ่านการ audit

## เทียบกับโครงการอื่น

| | ตรวจอะไร | อย่างไร | หมายเหตุ |
|---|---|---|---|
| **ของเรา (ZETAPHY)** | ว่าขั้นการฝึกถูกคำนวณจริงบน shard ที่ได้รับ และผลลัพธ์ช่วยได้จริง | ตัวฝึก JS ที่ตรงกันทุกบิต; digest ของแต่ละช่วงรวม transcript ที่ปิดผนึก; สุ่มรันซ้ำโดยผู้ตรวจที่วางเงินค้ำ; ประเมินบนข้อมูลกันไว้ด้วย seed ที่เปิดทีหลัง | ใช้ได้กับโมเดลเล็ก (GBDT); การตรวจพึ่งเสียงข้างมากที่ซื่อสัตย์; ตอนนี้ยังเป็นข้อมูลสังเคราะห์ |
| **Gensyn** | งานคำนวณ ML บนฮาร์ดแวร์ที่ไม่ไว้ใจกัน | แนวทางที่เผยแพร่รวม operator ที่ให้ผลตรงกันข้ามฮาร์ดแวร์ (RepOps) เข้ากับ refereed delegation / เกมโต้แย้งที่บีบความเห็นต่างให้เหลือ operation เดียว (Verde) | มุ่งไปที่ deep learning บน GPU งานวิศวกรรมด้านความตรงกันแข็งกว่าของเรามาก |
| **Bittensor** | ว่าผลงานของ miner ถูก validator ให้คุณค่า | Yuma consensus: validator ให้คะแนน miner ถ่วงด้วยเงินค้ำ แล้วรางวัลไหลตามคะแนน | ไม่มีการรันซ้ำ "มีประโยชน์" คือสิ่งที่ validator ให้คะแนน มีปัญหาที่รู้กันเรื่องการลอกน้ำหนักและการเล่นกับคะแนนที่เป็นอัตวิสัย |
| **Prime Intellect** | การฝึกแบบกระจาย | การฝึกที่สื่อสารน้อย (แนว DiLoCo) ข้าม GPU ที่คนนำมาร่วม; TOPLOC (แฮชแบบ locality-sensitive ของ activation) ใช้ตรวจ inference | ฝึกระดับใช้งานจริง ที่ผ่านมาผู้ร่วมมักผ่านการคัดกรอง ไม่ได้ trustless เต็มที่ |
| **งานวิจัย proof-of-learning** | ว่าโมเดลเกิดจากการฝึกที่อ้างจริง | Jia et al. 2021: checkpoint + รันช่วงสุ่มซ้ำ ใกล้กับแบบของเรามาก งานต่อมา (เช่น Fang et al. 2023) แสดงการโจมตีปลอมหลักฐาน PoL เมื่อการรันซ้ำยอมให้คลาดเคลื่อนทศนิยมได้ | การรันซ้ำแบบตรงกันทุกบิตของเราตัดความคลาดเคลื่อนที่การโจมตีเหล่านั้นใช้ แลกกับการจำกัดชนิดโมเดลและการคำนวณ |

แนวคิดหลัก — commit checkpoint ไว้ สุ่มรันซ้ำบางช่วง ยึดเงินค้ำเมื่อไม่ตรง — คือรูปแบบ proof-of-learning / Truebit
สิ่งที่รีโปนี้เพิ่มคือทำให้ขั้นการฝึก **ตรงกันเป๊ะ** ในเบราว์เซอร์ ปิดผนึก transcript ไว้เพื่อไม่ให้ข้ามการตรวจได้ และผูก
การจ่ายเงินไว้กับผลที่ดีขึ้นบนข้อมูลกันไว้ ซึ่งยังช่วยกันการวางยาข้อมูลที่ทำให้ตัวเลขแย่ลงด้วย

## ลองใช้

```bash
cd zetaphy-network
npm run build                                  # คอมไพล์ TrainingMarket + TrainingPool
node --test test/trainwork.test.js             # ความตรงกันทุกบิต, ความถูกต้องของการสุ่มตรวจ, สัญญา, การจำลอง, การวางยา
node src/trainwork/cli.js simulate             # รอบ 6 worker ออกมาเป็นรายงาน markdown
node src/trainwork/cli.js table                # ตารางโอกาสจับคนโกงได้
node src/trainwork/cli.js train spec.json 0 --out trees.json   # ฝึก shard หนึ่งของ spec (JSON จาก T.makeSpec)
node src/trainwork/cli.js verify spec.json 0 trees.json 3 0x<treesHash>   # สิ่งที่ผู้ตรวจปิดผนึก
```

ใน hub: **Mine → 🧠 Useful work → งานฝึกโมเดล → ลองฝึกโมเดล** (Web Worker; root ของ checkpoint ที่แสดงคือค่าเดียวกับที่
Node คำนวณ)

## สิ่งที่ยังขาด

- การ deploy (สคริปต์ deploy และโหมด on-chain ใน hub แบบที่ `UsefulWork` มี) การ์ดงานฝึกใน hub ตอนนี้เป็นโหมดฝึกซ้อมอย่างเดียว
- ใช้ shard จาก corpus จริงและ `ml/model.json` เป็นโมเดลฐาน (โค้ดและรูปแบบพร้อมแล้ว การจำลองยังใช้แถวสังเคราะห์)
- สุ่มผู้ตรวจแบบถ่วงตามเงินค้ำหรือชื่อเสียง; beacon สำหรับความสุ่ม; เกมโต้แย้งบนเชนสำหรับต้นไม้หนึ่งต้น (การแบ่งครั้งเดียว
  ถูกพอจะตัดสินบนเชนได้) แทนการโหวตเสียงข้างมาก
- เอาการฝึก head ของ federated learning (`ml/fl/head.js`) มาเป็นหน่วยงานด้วย: ใช้รูปแบบเดียวกันได้ (ขั้นอัปเดตเป็นแค่ผลคูณ
  จุดไม่กี่ครั้ง) ภายใต้กฎความตรงกันทุกบิตชุดเดียวกัน
