# ตัวตนแบบส่วนตัวบน ZETAPHY: หลักฐาน zero-knowledge บนป้าย "คน" (testnet)

[English](zk-identity.md)

**ใช้บน testnet / เป็นต้นแบบเท่านั้น ไม่มีเงินจริง การตั้งค่าเริ่มต้น (trusted setup) เป็นแบบ DEV ที่ทำโดยฝ่ายเดียว
และ Groth16 บน BN254 ไม่ทนต่อคอมพิวเตอร์ควอนตัม** อ่านข้อ 7 และข้อ 8 ก่อนจะพึ่งพาส่วนใดก็ตาม

คนที่มีป้ายแล้ว (ป้าย HUMAN ของ `LabelRegistry` ที่ยืนยันด้วย passkey และอาจเป็น "คนที่มีผู้รับรองว่าไม่ซ้ำ" ของ
`VouchRegistry` ดู [agents.th.md ข้อ 25](agents.th.md)) พิสูจน์ได้ว่า

- **"ฉันเป็นคนที่มีป้าย"**: ตัวตนของฉันอยู่ในต้นไม้ของทะเบียน
- **"ฉันทำที่นี่ได้ครั้งเดียว"**: หนึ่ง nullifier ต่อหนึ่งคนต่อหนึ่ง *scope* (รหัสแอร์ดรอป รหัสโพล) การรับหรือโหวตครั้งที่สองจึงถูกปฏิเสธ
  ส่วนสอง scope จะเห็น nullifier ที่ไม่เกี่ยวกัน (**โยงข้ามแอปไม่ได้**)
- **"ระดับของฉันอย่างน้อย X"**: 1 = คนที่ยืนยันด้วย passkey, 2 = คนที่มีผู้รับรองว่าไม่ซ้ำ
- **ผูกกับ signal** (ผู้รับแอร์ดรอปและค่าตอบแทนผู้ส่งแทน หรือตัวเลือกในโพล) คนที่เห็นหลักฐานใน mempool จึงเปลี่ยนปลายทางไม่ได้

โดยไม่บอกว่าบัญชี passkey หรือตัวตนไหนเป็นของตน ส่วนการพิสูจน์อายุหรือข้อมูลรับรองจากผู้ออก (issuer) เป็นส่วนต่อขยาย (ข้อ 10) ยังไม่ได้สร้าง

## 1. การออกแบบ

**ตัวตน** คือเลขสุ่มสองตัวในฟิลด์ที่สร้างในเบราว์เซอร์: `secret` กับ `nullifierKey` (สุ่ม 31 ไบต์ต่อตัว น้อยกว่าขนาดฟิลด์ของ
BN254) เก็บใน `localStorage` ของเบราว์เซอร์นี้ (`zetaphy-hub:zkid`) ส่งออกเป็นไฟล์สำรองแบบเข้ารหัสได้ (PBKDF2-SHA-256
600,000 รอบ → AES-256-GCM เป็นไฟล์ JSON) ไม่ถูกส่งไปไหนเลย

```
commitment C = Poseidon(secret, nullifierKey)        ลงทะเบียนบนเชน ไม่เปิดเผยอะไร
leaf         = Poseidon(C, level)                     ระดับ 1 คนที่ยืนยันด้วย passkey, 2 คนที่มีผู้รับรองว่าไม่ซ้ำ
nullifier    = Poseidon(nullifierKey, scope)          หนึ่งค่าต่อคนต่อ scope
```

Poseidon คือ Poseidon(2) ของ circomlib (BN254, t = 3, 8 รอบเต็ม + 57 รอบบางส่วน) ฟังก์ชันเดียวกันนี้มีอยู่สามที่
สร้างจากค่าคงที่ชุดเดียวกันและทดสอบเทียบกัน: ในวงจร (circomlib) ในเบราว์เซอร์ (`zkid-poseidon.js` ใช้ BigInt) และบนเชน
(`PoseidonT3.sol` เป็น EVM assembly แบบเส้นตรง ประมาณ 45 k gas ต่อการแฮชหนึ่งครั้ง)

**ต้นไม้** (`ZkIdentityRegistry`): Merkle tree แบบ Poseidon ความลึก 20 (ราว 1 ล้านสมาชิก) เก็บ**บนเชน**ทุกโหนด
จึงแก้หรือถอดใบออกได้ (ใบว่าง = 0, ต้นไม้ย่อยที่ว่าง = `zeros[h]`) `leavesRange(from, count)` คืนค่าใบทั้งหมด
เบราว์เซอร์สร้างต้นไม้ใหม่เองและหาใบของตัวเอง**ในเครื่อง** (โหนด RPC ถูกถามหาใบทั้งหมด ไม่เคยถูกถามหา commitment ใดตัวหนึ่ง)

**การลงทะเบียน** (`register(C)` จากบัญชีที่มีป้าย): ทะเบียนอ่าน `LabelRegistry.labelOf(sender) == HUMAN` และอ่านระดับจาก
`VouchRegistry.levelOf` (ถ้าไม่ได้ตั้งไว้ถือเป็น 1) กฎการผูก เพื่อกันการสร้างหลายตัวตนจากป้ายเดียว:

- **บัญชี** ผูกกับ commitment แรกตลอดไป (กลับมาด้วยตัวเดิมได้หลังถูกถอด แต่ใช้ตัวใหม่ไม่ได้)
- **passkey** (`credentialHash`) ผูกกับ commitment แรกที่ลงทะเบียนด้วย passkey นั้นตลอดไป ถ้าย้าย passkey ไปบัญชีอื่น
  บัญชีนั้นจะถือ commitment **ตัวเดิม** ได้ (nullifier เดิม) แต่สร้างตัวใหม่ไม่ได้
- **commitment** หนึ่งตัวใช้งานได้กับบัญชีเดียวในเวลาหนึ่ง (การคัดลอก commitment ของคนอื่นจะถูกปฏิเสธระหว่างที่เจ้าของยังเป็นสมาชิก)

**Sync** (`sync(account)` ใครเรียกก็ได้): ปรับใบให้ตรงกับระดับปัจจุบันของบัญชี: ขึ้นเมื่อได้รับการรับรอง ลงเมื่อถูกแบนหรือระงับ
และ**ถอดออก** (ใบ = 0) เมื่อป้ายหมดอายุ ถูกเพิกถอน หรือ passkey ย้ายไปหรือผูกกับตัวตนอื่น ผู้ดูแล (keeper) หรือผู้ใช้คนไหนก็เรียกได้
ระหว่างที่ยังไม่มีใครเรียก ใบเดิมยังพิสูจน์ได้

**ประวัติ root** ทุกการเปลี่ยนแปลงทำให้เกิด root ใหม่ root ที่ถูกแทนที่ยังใช้ได้อีก `rootTtl` (ตั้งโดย governance เช่น 1 ชั่วโมง)
หลักฐานที่กำลังส่งอยู่จึงไม่พังเมื่อมีคนลงทะเบียนเพิ่ม root ปัจจุบันไม่มีวันหมดอายุ

**Scope** แอปจอง scope ของตัวเองในทะเบียน (`registerScope` ใครมาก่อนได้ก่อน) สองแอปจึงไม่ใช้พื้นที่ nullifier ร่วมกันโดยบังเอิญ
`PrivateAirdrop` รับ scope ตอนสร้างสัญญา `PrivatePoll` ใช้หนึ่ง scope ต่อหนึ่งโพล

**วงจร** (public signal ตามลำดับ: `root, nullifier, scope, signalHash, minLevel`):

1. `C = Poseidon(secret, nullifierKey)`, `leaf = Poseidon(C, level)`
2. ใบกับเส้นทาง 20 ชั้น (ดัชนีเป็นบิต 0/1) แฮชได้ `root`
3. `nullifier = Poseidon(nullifierKey, scope)`
4. `level ≥ minLevel` (ตรวจช่วง 8 บิตทั้งคู่)
5. คำนวณ `signalHash²` เพื่อให้ signal เป็นส่วนหนึ่งของข้อความที่พิสูจน์

**การตรวจ** (`ZkIdentityRegistry.verify(root, nullifier, scope, signalHash, minLevel, proof[8])`): root ต้องเป็นตัวปัจจุบันหรือยังใหม่อยู่
`minLevel ≥ 1` จากนั้นจึงเข้า verifier ของ Groth16 **แอป**เป็นผู้ใส่ scope, signal และ minLevel จากสถานะของตัวเอง ผู้พิสูจน์เลือกเองไม่ได้สักค่า

**แอป**

- `PrivateAirdrop(registry, scope, minLevel, amount)`: `claim(recipient, fee, root, nullifier, proof)` จ่าย `amount − fee` ให้
  `recipient` และ `fee` ให้ผู้ส่งธุรกรรม หนึ่งครั้งต่อหนึ่ง nullifier `signal = keccak256(recipient, fee) >> 8` ใครจะส่งก็ได้
  (ตัวคนเองจากที่อยู่ใหม่ หรือผู้ส่งแทน) แต่ไม่มีใครเปลี่ยนปลายทางของเหรียญหรือค่าตอบแทนได้
- `PrivatePoll`: `createPoll(scope, questionHash, options, minLevel, endsAt)` และ `vote(scope, option, root, nullifier, proof)`
  โดย `signal = keccak256(scope, option) >> 8` ผลนับคะแนนเปิดเผยทันทีที่มีคนโหวต

**Hub (แท็บ Agent → "ตัวตนแบบส่วนตัว")** สร้างตัวตน → *ลงทะเบียนด้วยบัญชีของฉัน* (ธุรกรรมจากบัญชีที่มีป้าย ผ่านหน้าสรุปก่อนเซ็นของ hub)
→ *สร้างหลักฐาน* สำหรับแอร์ดรอปทดสอบ: อ่าน scope, minLevel และ signal ของผู้รับที่พิมพ์ไว้ สร้างต้นไม้ใหม่ ตรวจว่า nullifier ยังไม่ถูกใช้
ดาวน์โหลดไฟล์สร้างหลักฐาน (`zkid/identity.wasm` 1.8 MB, `zkid/identity.zkey` 3.3 MB) และปฏิเสธถ้า sha256 ไม่ตรงกับ
`zkid/manifest.json` สร้างหลักฐานใน **Web Worker** (`zkid-worker.js`) แล้วมีปุ่ม *ส่งคำขอรับจากกระเป๋าที่เชื่อมอยู่*
(พร้อมคำเตือนว่าจะโยงการรับเข้ากับบัญชีนั้น) และ calldata สำหรับผู้ส่งแทนรายใดก็ได้

**CSP** หน้าต่าง ๆ ของ hub ยังคง `script-src 'self'` โดยไม่มี WebAssembly มีแค่ `zkid-worker.js` ที่ได้ CSP ของตัวเอง
(`script-src 'self' 'wasm-unsafe-eval'; connect-src 'none'`) dedicated worker ใช้ CSP ของสคริปต์ตัวเอง ตัวสร้างหลักฐานแบบ
WebAssembly จึงรันได้แค่ในนั้น (ตรวจใน Chromium โดย `zkid.e2e.mjs`) snarkjs มาจาก `vendor/snarkjs.min.js` ที่ปักเวอร์ชันไว้
(0.7.6, sha256 อยู่ใน `vendor/snarkjs.json`) โหลดด้วย `importScripts` จาก origin เดียวกัน

## 2. สิ่งที่รับประกันเรื่องความเป็นส่วนตัว

หลักฐานหนึ่งชิ้นเปิดเผย: root (สถานะต้นไม้ไหน) nullifier ของ scope นี้ ตัว scope, signal และ `minLevel`

- **ใคร** ในบรรดาสมาชิกของ root นั้นที่มีระดับ ≥ minLevel เป็นคนสร้าง: ถูกซ่อน (zero-knowledge กลุ่มที่ซ่อนตัวอยู่คือสมาชิกกลุ่มนั้น)
- **การโยงข้าม scope**: nullifier ของต่าง scope เป็นผลลัพธ์ Poseidon ภายใต้กุญแจลับ ถ้าไม่มี `nullifierKey` ก็ดูไม่เกี่ยวกัน
  แอร์ดรอปกับโพลจึงบอกไม่ได้ว่าเจอคนเดียวกัน
- **การโยงกับป้าย**: commitment เป็นแฮชของค่าลับสองตัว การลงทะเบียนแสดงแค่ว่าบัญชีหนึ่ง*เข้าร่วม* ไม่ได้บอกว่าหลักฐานไหนในภายหลังเป็นของบัญชีนั้น

## 3. สิ่งที่ระบบนี้ไม่ได้ป้องกัน

- **ข้อมูลเครือข่าย** โหนด RPC และผู้ส่งแทนเห็นที่อยู่ IP และจังหวะเวลาของคำขอและธุรกรรม ใช้เส้นทางเครือข่ายอื่น (Tor, VPN)
  และอย่ารับทันทีหลังลงทะเบียน
- **ผู้ส่งธุรกรรม** ถ้ารับจากบัญชีที่ใช้ลงทะเบียน (หรือบัญชีที่ได้เงินค่าแก๊สจากบัญชีนั้น) ทั้งสองจะถูกโยงกัน ให้ใช้ที่อยู่ใหม่ที่ได้เงินจากที่อื่น
  หรือใช้ผู้ส่งแทน (ค่าตอบแทนผูกอยู่ในหลักฐาน)
- **กลุ่มที่เล็ก** ถ้าสมาชิกน้อย หรือมีระดับ 2 น้อย "หนึ่งในนั้น" ก็แทบไม่ช่วย `minLevel 2` ยังบอกด้วยว่าคุณอยู่ระดับ 2 และจังหวะของ `sync`
  (ระดับเปลี่ยน) ตามด้วยหลักฐานก็ช่วยให้แคบลงได้อีก
- **ใช้ที่อยู่ผู้รับซ้ำ** ส่งหลายแอร์ดรอปไปที่ที่อยู่เดียวกันจะโยงกันผ่านที่อยู่นั้น
- **เบราว์เซอร์** ค่าลับเก็บใน `localStorage` แบบไม่เข้ารหัส มัลแวร์ ส่วนขยายเบราว์เซอร์ที่อ่านหน้าเว็บได้ หรือใครก็ตามที่ใช้โปรไฟล์เบราว์เซอร์นั้น
  คัดลอกไปแล้วทำแทนคุณได้ ไฟล์สำรองปลอดภัยเท่ากับรหัสผ่านของมัน
- **การโอนให้กันได้** ตัวตนคือค่าลับแบบ "ผู้ถือเป็นเจ้าของ" ให้หรือขายกันได้ และบอทก็ใช้ตัวตนของคนได้ ทะเบียนพิสูจน์แค่ว่าคนที่มีป้าย*เป็นผู้ลงทะเบียน*
  ไม่ได้พิสูจน์ว่าคนนั้นคือผู้ที่กำลังพิสูจน์อยู่
- **ข้อเท็จจริงที่เปิดเผยอยู่แล้ว** การที่บัญชีมีป้ายคน แฮชของ passkey ระดับ และการลงทะเบียน เป็นข้อมูลสาธารณะ
- **ผลนับระหว่างทาง** `PrivatePoll` แสดงคะแนนทันทีที่มีคนโหวต (ไม่มี commit-reveal ไม่กันการบังคับให้โหวต แนวทางแบบ MACI แก้เรื่องนี้)

## 4. วิเคราะห์การกันบัญชีปลอม (Sybil)

หลักฐานกัน Sybil ได้**เท่ากับกฎการรับเข้าพอดี** (ป้ายคน และการรับรองสำหรับระดับ 2) ชั้น zero-knowledge ไม่ได้เพิ่มความไม่ซ้ำ
และต้องไม่ทำให้ลดลง กฎการผูกทำให้ป้ายหนึ่งถือได้หนึ่งตัวตน:

| ถ้าจะได้ตัวตนเพิ่ม (nullifier เพิ่มต่อ scope) ผู้โจมตีต้องมี | ระดับ 1 | ระดับ 2 |
|---|---|---|
| บัญชีใหม่ | ต้อง | ต้อง |
| passkey ใหม่ (แฮชที่ไม่เคยลงทะเบียน) | ต้อง: ถูก (ใครก็สร้าง passkey ได้หลายอัน หรือใช้ attester) | ต้อง |
| การรับรองใหม่จากคนไม่ซ้ำ N คน (จำกัดอัตรา โดน strike เมื่อถูกแบน) | – | ต้อง: แพง และเห็นได้บนเชน |

- การย้าย passkey ไปบัญชีใหม่ หรือการลงทะเบียนใหม่หลังถูกถอด ได้ commitment **ตัวเดิม** (nullifier เดิม) หรือไม่ได้อะไรเลย
- การคัดลอก commitment สาธารณะของคนอื่นไปลงด้วยบัญชีที่มีป้ายอีกบัญชี ถูกปฏิเสธระหว่างที่เจ้าของยังเป็นสมาชิก หลังเจ้าของออกไป
  ผู้คัดลอกได้แค่ใบที่ตัวเองไม่รู้ค่าลับ (ไม่มีประโยชน์กับตัวเขา แต่ทำให้ใบนั้นยังอยู่ให้เจ้าของตัวจริงใช้ — คือกรณี "ให้ยืม" ด้านล่าง)
- **การโจมตีที่ยังเหลือ**: passkey หลายอัน + บัญชีหลายบัญชีที่ระดับ 1 (ระดับ 1 เป็นแค่เนินชะลอ แอปที่ใส่ใจควรใช้ `minLevel 2`)
  การรับรองที่ซื้อมาหรือสมรู้ร่วมคิดที่ระดับ 2 (มีขอบเขตและตามรอยได้ ดู agents.th.md ข้อ 25) การให้เช่าหรือขายตัวตน (มีในทุกระบบค่าลับ
  แบบผู้ถือเป็นเจ้าของ รวมถึง Semaphore และ World ID) สมาชิกที่ถูกถอดยังพิสูจน์ได้จนกว่าจะมีคนเรียก `sync` และผ่าน `rootTtl`
  และการชิงลงทะเบียนด้วย commitment เดียวกันก่อน (ก่อกวน: เหยื่อต้องสร้างตัวตนใหม่ ผู้โจมตีเสียบัญชีและ passkey ไปหนึ่งชุด)
  ถ้าตอนลงทะเบียนต้องแนบหลักฐานว่ารู้ค่าลับของ commitment และผูกกับ `msg.sender` ก็จะปิดข้อสุดท้ายได้ (งานในอนาคต)
- **Governance** เปลี่ยน VouchRegistry และ `rootTtl` ได้ และคุม attester กับการแบนในสัญญาป้าย: เปลี่ยนได้ว่าใครนับเป็นคน
  แต่ไม่มีทางรู้ว่าใครพิสูจน์อะไร

  จากนั้นสร้าง verifier ไฟล์ของ hub และ fixture ใหม่จาก zkey ตัวสุดท้าย

## 8. สถานะด้านควอนตัมและแผนต่อไป

**Groth16 บน BN254 ไม่ทนต่อคอมพิวเตอร์ควอนตัม** คอมพิวเตอร์ควอนตัมขนาดใหญ่ (อัลกอริทึมของ Shor) หา discrete log บน BN254 ได้
จึงกู้ trapdoor ของการตั้งค่ามาและ**ปลอมหลักฐาน**ได้ คือทำลายความถูกต้อง (soundness) (รับซ้ำ โหวตเกิน) ส่วนความเป็นส่วนตัวยังดีกว่า:
หลักฐาน Groth16 เป็น zero-knowledge แบบสมบูรณ์ และ commitment/nullifier เป็นแฮช Poseidon หลักฐานที่ถูกเก็บไว้จึงไม่กลายเป็น
โยงกันได้ภายหลัง (แนวคิด "เก็บไว้ก่อน ถอดตัวตนทีหลัง" ใช้กับตัวหลักฐานไม่ได้ แต่ยังใช้กับข้อมูลเครือข่ายได้)

**ทางไปสู่การทนควอนตัม: หลักฐานการเป็นสมาชิกแบบ STARK** (ใช้แฮชล้วน โปร่งใส ไม่ต้องมี trusted setup เลย)

- ข้อความที่พิสูจน์เหมือนเดิม (ใบอยู่ใน Merkle tree, nullifier, ระดับ, signal) แต่ใช้แฮชที่เหมาะกับ STARK และปลอดภัยต่อควอนตัม
  (Poseidon2 หรือ Rescue-Prime บนฟิลด์ของ STARK หรือ SHA-256/BLAKE3 ที่แพงกว่า) ทั้งสำหรับต้นไม้และ commitment ของ FRI
- ขนาดงานคำนวณ: permutation ของแฮช 23 ครั้ง (เส้นทาง 20 + commitment + ใบ + nullifier) — trace ไม่กี่ร้อยแถว เล็กกว่าข้อความ
  "บล็อกสิ้นสุดแล้ว" ของต้นแบบ STARK light client ใน repo นี้มาก (branch `worktree-agent-a638e15c9a3e64d32`,
  `docs/future/stark-light-client.md`) ซึ่งพิสูจน์ชุด validator n = 100 ด้วยหลักฐาน **44 KB** สร้าง 0.42 วินาที (JS)
  ตรวจราว 20 ms (node และเบราว์เซอร์)
- ประมาณจากตัวเลขเหล่านั้น: **หลักฐานราว 40–80 KB** ที่พารามิเตอร์ตั้งต้นของต้นแบบ (ราว 100 บิตตามข้อสันนิษฐาน
  เพิ่มราว 40 KB ถ้าใช้ชุด 60 query ที่เสริมความทนควอนตัม) **สร้างหลักฐานราว 1–3 วินาทีในเบราว์เซอร์**ด้วยตัวสร้างแบบ JS BigInt ของ repo
  (ราว 0.1–0.5 วินาทีถ้าใช้ Plonky3/Stwo แบบ WASM) **ตรวจราว 20–60 ms** นอกเชน และ**ราว 1.5–2.5 M gas** ถ้ามี verifier บน EVM
  (ในนั้นเป็น calldata ราว 0.6–1 M) เทียบกับราว 0.22 M ของ Groth16 ในตอนนี้ การห่อ STARK ด้วย SNARK แบบ pairing จะถูกกว่าบนเชน
  แต่ก็ไม่ทนควอนตัม
- การย้ายระบบ: ต้นไม้ใหม่ที่ใช้แฮชแบบเหมาะกับ STARK (ค่าลับของตัวตนใช้ต่อได้ สมาชิกแต่ละคนลงทะเบียน commitment ใหม่จาก
  `nullifierKey` เดิม และแอปสลับ verifier ที่รอยต่อของ scope เพื่อให้ nullifier ยังไม่ซ้ำภายใน scope) มีช่วงเปลี่ยนผ่านที่รับทั้งสองแบบ
  แล้วจึงเลิกใช้ verifier ของ Groth16 เมื่อความเสี่ยงจากควอนตัมใกล้ตัวจริง

## 10. ส่วนต่อขยาย (ยังไม่ได้สร้าง): ข้อมูลรับรองจาก issuer เช่น "อายุ ≥ 18"

- issuer (กุญแจที่ลงทะเบียนบนเชน เช่น ผู้ให้บริการ KYC หรือมหาวิทยาลัย) เซ็นด้วย **EdDSA-Poseidon บน BabyJubJub**
  บนข้อมูลรับรอง `cred = Poseidon(holderId, attributeType, value, expiry)` โดย `holderId = Poseidon(nullifierKey, 1)`
  ผูกไว้กับตัวตน (จึงให้ยืมแยกจากตัวตนไม่ได้)
- วงจรเพิ่ม `EdDSAPoseidonVerifier` ของ circomlib (ราว 5–7 k constraint) ตรวจกุญแจ issuer กับแฮชกุญแจที่เปิดเผย ตรวจ
  `value ≤ today − 18 ปี` โดย `today` เป็นค่าสาธารณะที่ตรวจช่วงแล้ว และ `expiry > today` การเพิกถอนทำผ่านต้นไม้การเพิกถอนของ issuer
  (เพิ่มเส้นทางพิสูจน์ว่าไม่อยู่ในต้นไม้) หรือให้หมดอายุเร็ว
- ขนาด: ราว 12–14 k constraint → zkey ราว 7–8 MB สร้างหลักฐานในเบราว์เซอร์ราว 5–6 วินาที แก๊สตรวจเท่าเดิม (public signal เพิ่มหนึ่งตัว)
- ข้อมูลส่วนบุคคล: วันเกิดอยู่กับ issuer และผู้ถือ เชนและแอปเห็นแค่ "≥ 18 ตาม issuer X" ที่ยังไม่สร้างเพราะต้องมีขั้นตอนของ issuer
  และตัวเซ็น EdDSA บน BabyJubJub ในเบราว์เซอร์ และ issuer ก็เป็นฝ่ายที่ถือข้อมูลส่วนบุคคลอยู่จริง

- พิธี phase 2 สาธารณะ (ข้อ 7) แล้วเอา `DEV_SETUP` ออก
